# 이메일 인증·비밀번호 찾기 인수인계 — 쉽게 읽는 설명

2026-11-16 기준입니다. **화면과 서버 코드는 준비됐고, 실제 메일 발송 서비스와 운영 서버 설정을 연결하는 일이 남아 있습니다.**
처음 읽는 분은 1~6번을 순서대로 읽어 주세요. 실제 연결 작업에 필요한 설정 이름과 API 주소는 7~8번에 모았습니다.
구현·시험 기록은 [계획 0089](../plans/completed/0089-email-recovery-social-link.md), 정확한 요청 규칙은 [계정 API 계약](../../contracts/accounts.md)을 참고해 주세요.

## 1. 이번에 무엇을 만들었나요?

사용자가 자기 이메일과 계정의 주인인지 확인하는 과정을 만들었습니다.

- **회원가입:** 메일로 받은 숫자 6개를 입력하면 가입을 계속할 수 있어요.
- **비밀번호 찾기:** 메일의 링크를 열어 본인을 확인한 뒤 새 비밀번호를 정할 수 있어요.
- **Discord 연결:** 기존 계정의 주인인지 확인하고 연결을 승인하면, 같은 계정에 Discord로도 들어갈 수 있어요.

계정을 **내 기록이 들어 있는 사물함**이라고 생각하면 쉬워요.
이메일 로그인과 Discord 로그인은 그 사물함을 여는 열쇠입니다. 기존 계정에 Discord를 연결하면 같은 사물함에 열쇠 하나를 더 붙이는 셈이에요.

## 2. 회원가입할 때는 어떤 일이 일어나나요?

이메일 인증은 “이 메일함을 실제로 열 수 있는 사람이 맞나요?”를 확인하는 과정이에요.

1. 사용자가 약관에 동의하고 이메일·비밀번호·이름 등을 입력해요.
2. 이메일 인증 화면에서 **인증 코드 받기**를 눌러요.
3. 화면이 백엔드에 “이 주소로 인증 코드를 보내 주세요”라고 요청해요.
4. 백엔드가 무작위 **6자리 숫자**를 만들어요.
5. 백엔드가 메일 발송 회사에 코드가 담긴 메일을 보내 달라고 요청해요. 현재 코드는 SMTP라는 메일 접수 방식을 사용해요.
6. 사용자가 같은 가입 화면에 코드를 입력하면 백엔드가 맞는지 확인해요.
7. 인증 완료 후 **회원가입 계속하기**를 눌러 계정 정보 화면으로 돌아가요. 다음을 누르면 최종 가입 요청을 보내요.
8. 백엔드는 **방금 인증한 이메일과 가입하려는 이메일이 같은지** 다시 확인한 뒤 계정을 만들어요.

인증 코드는 잠깐 쓰는 확인표라고 생각하면 돼요.
**15분** 안에 확인해야 하고, 한 확인표로 코드를 입력할 수 있는 횟수는 **최대 5회**예요.
새 코드를 요청하면 이전 코드와 이전 인증 완료 표시도 사용할 수 없어요. 같은 이메일로 다시 요청하려면 **60초**를 기다려야 해요.

확인표는 인증을 요청한 브라우저에 묶여 있어요. 휴대폰으로 메일을 읽더라도 **코드 입력은 가입하던 브라우저에서** 해 주세요.
서버를 재시작하면 가입 도중의 확인표가 사라져요. 이때는 코드를 다시 받아야 합니다.

## 3. 비밀번호를 잊었을 때는 어떻게 하나요?

로그인 화면의 이름은 **비밀번호 찾기**입니다. 새 비밀번호를 정하는 단계에 들어가면 **비밀번호 재설정**으로 보여요.

1. 사용자가 비밀번호 찾기에서 **가입한 이메일**을 입력해요.
2. 화면이 백엔드에 안내 메일을 요청해요.
3. 백엔드가 가입된 정상 계정을 확인하고, **30분 동안 한 번만 쓸 수 있는 링크**를 메일로 보내요.
4. 사용자가 링크를 열면 서버가 아직 사용할 수 있는지 확인해요.
5. 확인을 통과하면 새 비밀번호와 새 비밀번호 확인 칸이 나와요.
6. 두 입력이 같고, 길이 규칙에 맞고, **기존 비밀번호와 다른 값**이면 저장해요.
7. 완료 후 새 비밀번호로 다시 로그인해요.

링크를 열기 어려우면 메일에 함께 들어 있는 **긴 인증 코드**를 비밀번호 찾기 화면에 붙여 넣을 수 있어요.
이 값은 회원가입 때 받는 6자리 숫자와 용도가 달라요. 기존 비밀번호를 알아내는 기능은 없고, 본인 확인 후 새 비밀번호로 바꾸는 방식입니다.

**알아 두면 좋은 점:**

- 새 비밀번호 두 개가 다르면 화면에서 다시 입력하도록 안내해요.
- 기존 비밀번호와 같은 값을 넣으면 서버가 거절해요. 다른 비밀번호로 다시 시도할 수 있어요.
- 사용했거나 시간이 지난 링크는 새로 받아야 해요. 새 링크를 발급받으면 이전 링크도 사용할 수 없어요.
- 비밀번호 찾기에서 “안내를 요청했어요”가 나와도 메일 도착을 보장하는 뜻은 아니에요. 가입 여부를 다른 사람에게 알려 주지 않기 위해 요청 응답은 같게 보내고, 실제 발송은 뒤에서 처리해요.

재설정을 마치면 다른 기기의 **로그인을 계속 갱신하는 권한**과 열려 있는 측정 연결을 끊어요.
다만 이미 발급된 짧은 로그인 권한은 만료될 때까지 남습니다. 따라서 “모든 요청이 즉시 차단된다”고 설명하면 안 돼요.
개발 용어로는 refresh 토큰 철회, 기존 access JWT는 만료까지 유효하다는 뜻이에요([ADR 0031](../decisions/0031-jwt-access-refresh-login.md)).

## 4. Discord를 연결하면 계정이 두 개가 되나요?

**기존 계정에 연결하는 경우에는 계정 하나에 로그인 방법이 두 개가 됩니다.**

예를 들어 PoseGood 계정 번호가 `42`라면 DB에는 다음처럼 남아요. 아래 값은 설명용 예시입니다.

| 보관 장소 | 무엇을 보관하나요? | 연결 후 모습 |
| --- | --- | --- |
| `user_account` | PoseGood 계정 정보 | 기존 계정 42번 행을 그대로 유지 |
| `social_identity` | 어떤 소셜 회원이 어느 계정에 연결됐는지 | “Discord 회원 12345번은 PoseGood 계정 42번”이라는 행을 추가 |

두 번째 표가 첫 번째 표의 계정 번호를 가리키는 것을 **외래키(FK) 연결**이라고 불러요.
이메일로 들어오든 Discord로 들어오든 계정 42번을 사용하므로 같은 자세 기록을 보게 됩니다.

### 이메일이 같으면

이미 가입한 계정을 찾았다고 안내하고, **기존 계정 비밀번호 확인 → 연결 승인 → 로그인** 순서로 진행해요.
비밀번호 확인만 마친 상태에서는 아직 연결하지 않아요. 마지막 **연결 승인하고 로그인** 버튼을 눌러야 연결됩니다.
비밀번호가 기억나지 않으면 그 화면에서 비밀번호 찾기로 갈 수 있어요.

### 이메일이 다르면

먼저 **기존 PoseGood 계정으로 로그인한 뒤 프로필 설정에서 Discord 연결**을 진행하면 됩니다.
기존 가입 이메일은 유지하고, Discord의 고유 회원 번호를 그 계정에 붙여요. Discord 이메일은 현재 연결 표에 저장하지 않아요.
다음 Discord 로그인부터는 이메일을 비교하는 대신 **Discord 회원 번호로 연결된 PoseGood 계정**을 찾습니다.

로그인 화면에서 곧바로 다른 이메일의 Discord로 시작하면, 서버는 기존 계정과 같은 사람인지 알 수 없어 새 가입을 안내할 수 있어요.
기존 기록을 계속 쓰려면 위의 **기존 계정에 로그인 → 설정에서 연결** 순서로 안내해 주세요.
이미 별도의 PoseGood 계정을 만들어 연결한 Discord는 다른 계정에 중복 연결할 수 없고, 계정 두 개를 자동으로 합치는 기능도 없습니다.

Discord만으로 새 가입한 경우에는 Discord가 확인한 이메일을 사용해요. 이메일 비밀번호 로그인도 쓰고 싶으면 비밀번호 찾기 메일로 비밀번호를 정할 수 있습니다.
소셜 연결만 더 자세히 보고 싶으면 [소셜 로그인 쉽게 이해하기](social-login-eli5.md)를 읽어 주세요.

## 5. 각 파트에서 무엇을 이어받으면 되나요?

| 파트 | 이미 준비된 부분 | 이어서 확인할 일 |
| --- | --- | --- |
| 프론트 | 코드 입력, 비밀번호 재입력, Discord 연결 승인 화면과 서버 요청 | 배포할 화면에서 해당 기능을 켜고, 실제 서버 주소로 연결되는지 확인 |
| 백엔드 | 코드 생성·검사, 메일 발송 요청, 인증 후 가입, 비밀번호 재사용 거절, 소셜 연결 | 메일 회사 접속 정보와 기능 설정을 넣고 실제 메일 수신 확인 |
| DB | 기존 V2.7의 소셜 연결 표와 비밀번호 찾기 표를 사용하는 코드 | 운영 DB에 필요한 표가 있는지 확인. 이번 가입 코드 인증 때문에 새 표를 추가할 필요는 없음 |
| 운영·배포 | 설정 예시와 연결 순서 | 메일 발송 계정, HTTPS 주소, 웹·API 연결 설정을 준비하고 시험 환경에서 먼저 확인 |

가입 확인표와 Discord 연결 도중의 정보는 서버의 임시 기억 공간에 보관해요.
그래서 현재는 **API 서버 한 대**를 기준으로 동작합니다. 여러 대로 늘리려면 이 정보를 함께 쓰는 저장소로 옮겨야 해요.

비밀번호 찾기 링크는 `password_reset_token` 표에 보관해요. 링크 원문 대신 **대조용 지문값(해시)**만 저장해요.
서버는 사용자가 가져온 링크의 지문과 저장한 지문이 같은지 확인합니다. 한 번 쓴 확인표는 다시 쓰지 못하게 처리해요.

## 6. 어디까지 확인됐고, 무엇이 남았나요?

화면·서버 코드는 구현했고, 자동 시험과 시험용 MySQL 연결을 확인했습니다.
브라우저에서는 실제 화면에 **시험용 응답**을 넣어 회원가입 인증, 비밀번호 오류, Discord 최종 승인을 확인했어요.
라이트·다크 테마와 좁은 화면도 확인했습니다.

**실제 메일함으로 메일이 도착하는지, 실제 Discord 인증을 끝까지 마치는지, 운영 배포가 정상인지는 아직 별도로 확인해야 합니다.**
현재 기능 설정은 기본으로 꺼져 있어요. 코드 준비와 실제 서비스 개방을 구분해서 인계해 주세요.
전체 검사 명령은 기존 Python 연구 의존성이 빠져 중단됐습니다. 계정 기능의 프론트·백엔드·DB·브라우저 검사 결과는 [검증 기록](../plans/completed/0089-email-recovery-social-link.md#검증-결과와-남은-한계)에 따로 적었습니다.

시험할 화면은 **개발자 도구 → 화면·모션 → 계정 인증 흐름**의 접힌 항목에서 열 수 있어요.
이곳은 같은 화면을 시험용 응답으로 보여 주며 실제 메일 발송이나 계정 연결은 하지 않습니다.

## 7. 실제로 켜는 순서 — 연결 작업 담당자용

설정 이름은 코드와 정확히 맞아야 해서 아래에는 영문 이름을 그대로 적었습니다.
환경변수는 “이 서버가 어느 메일 회사와 어떤 기능을 사용할지 알려 주는 설정값”이라고 생각하면 됩니다.

1. **시험 서버와 DB를 준비해 주세요.** V2.7의 `social_identity`, `password_reset_token` 표를 확인합니다.
2. **메일 회사 접속 정보를 서버에 넣어 주세요.** 아래 표의 주소·계정·발신 주소와 비밀번호가 필요합니다.
3. **메일 링크가 돌아올 HTTPS 앱 주소를 정해 주세요.** 비밀번호 찾기에 사용합니다.
4. **서버와 프론트의 해당 기능을 함께 켜고 배포해 주세요.** 프론트 설정은 빌드할 때 적용됩니다.
5. **시험 이메일로 가입·재발송·만료·재설정을 확인해 주세요.** Discord도 실제 시험 계정으로 연결·취소·재로그인을 확인합니다.
6. 확인한 뒤 운영에 같은 설정을 적용합니다. 실행 방법과 자세한 점검 명령은 [품질 기준](../quality.md)을 참고해 주세요.

| 서버 설정 | 뜻 |
| --- | --- |
| `POSEGOOD_MAIL_HOST`, `POSEGOOD_MAIL_PORT` | 메일 회사의 접수 주소와 접속 포트 |
| `POSEGOOD_MAIL_USERNAME` | 메일 발송용 로그인 계정 |
| `POSEGOOD_MAIL_FROM` | 사용자가 메일에서 보게 될 발신 주소 |
| `POSEGOOD_MAIL_PASSWORD` 또는 서버 비밀 파일 `spring.mail.password` | 메일 회사 접속 비밀번호. 서버에만 보관 |
| `POSEGOOD_APP_URL` | 비밀번호 찾기 링크가 열릴 HTTPS 앱 주소 |

| 기능 | 서버에서 켜기 | 프론트 빌드에서 켜기 |
| --- | --- | --- |
| 회원가입 이메일 인증 | `POSEGOOD_EMAIL_VERIFICATION_ENABLED=true` | `VITE_EMAIL_VERIFICATION_ENABLED=true` |
| 비밀번호 찾기 | `POSEGOOD_PASSWORD_RESET_ENABLED=true` | `VITE_PASSWORD_RESET_ENABLED=true` |

기존 `VITE_ACCOUNT_MAIL_API_ENABLED=true`는 프론트의 두 메일 기능을 한꺼번에 켜는 설정입니다.
메일 접속 비밀번호를 `VITE_` 설정이나 프론트 코드에 넣지 마세요. 프론트 빌드 내용은 사용자가 볼 수 있어요.
메일 접속에는 기존 STARTTLS 암호화와 연결·읽기·쓰기 시간 제한을 사용합니다.

서버의 가입 인증 기능이 켜져 있으면 화면을 우회해 직접 가입을 요청해도 인증을 확인합니다.
이 설정을 끄면 기존의 미인증 가입 경로가 다시 열리므로 운영 중 임의로 끄지 마세요.

웹과 API는 같은 사이트의 HTTPS·쿠키 설정이 필요합니다. 주소가 다른 경우 허용된 웹 주소를 서버의 CORS 설정에 등록해야 해요.
사용자 IP 제한을 정확히 세려면 gateway가 전달 IP 헤더를 덮어쓰는 환경에서만 `POSEGOOD_TRUST_FORWARDED_FOR=true`를 사용합니다.
요청 출처별 메일 발송 제한은 15분에 5회입니다.

현재 데스크톱 앱은 웹 배포·API 연결을 따릅니다. **외부 브라우저의 Discord 인증 후 데스크톱 앱으로 돌아오는 연결은 후속 작업**이에요.
비밀번호 찾기는 웹에서 완료하거나 메일의 긴 코드를 입력할 수 있습니다.
Discord 앱 설정 자체는 [소셜 로그인 기술 인계](social-login-password-reset-handoff.md)를 참고해 주세요.

## 8. API 주소 빠르게 찾기 — 구현 담당자용

API는 화면과 서버가 주고받는 요청 주소예요. 웹에서 부를 때는 `/api`가 앞에 붙고, 서버 내부에서는 아무것도 붙지 않습니다(주소에 버전 없음).
아래 표는 그 뒷부분입니다. 요청은 JSON 형식이며 인증 쿠키를 함께 보내고(`credentials: include`), 응답은 캐시하지 않습니다.

| 경로 | 보내는 값과 결과 |
| --- | --- |
| POST `/auth/email-verification/requests` | `{email}` → 202와 HttpOnly 인증 대기 쿠키. 발송 요청 실패 503, 제한 429 |
| POST `/auth/email-verification/confirm` | 같은 브라우저 쿠키 + `{token: "6자리 코드"}` → 204. 잘못된 코드·만료·한도 초과는 410 `EMAIL_VERIFICATION_REQUIRED` |
| POST `/auth/register` | 기존 가입 본문 + 인증 쿠키. 같은 이메일의 인증을 확인하고 가입 성공 때 한 번 소비. 인증 없으면 410 |
| POST `/auth/password-reset/requests` | `{email}` → 가입 여부와 관계없이 202. 발송 요청 접수이며 실제 발송 완료 확인은 아님 |
| POST `/auth/password-reset/validate` | `{token}` → 204. 링크 확인만 하고 아직 사용 처리하지 않음 |
| POST `/auth/password-reset/confirm` | `{token,new_password}` → 204. 기존 비밀번호 재사용 400 `PASSWORD_REUSED`, 비밀번호 규칙 오류 400 `INVALID_PASSWORD`, 무효 링크 410 `RESET_TOKEN_INVALID` |

쿠키는 브라우저가 보관하고 서버 요청에 붙이는 작은 확인표입니다. HttpOnly 쿠키는 화면의 JavaScript에서 읽을 수 없어요.
서버는 이 확인표를 통해 “이 브라우저에서 시작한 가입 인증”인지 구분합니다.

비밀번호는 12자 이상이며 UTF-8로 72바이트 이하여야 해요. 한글·이모지는 한 글자가 여러 바이트일 수 있습니다.
가입 이메일은 앞뒤 공백을 없애고 소문자로 맞춰 비교합니다.
가입 인증은 계정 생성 성공 때만 소비하므로 계정 생성 실패 시에는 다시 시도할 수 있어요.
비밀번호 재사용을 거절했을 때도 링크 사용 처리를 되돌려 다른 비밀번호로 다시 시도할 수 있습니다.

관련 구현은 `EmailVerificationService`, `PasswordResetService`, `SocialLoginService`,
프론트의 `MailAccessPage`, `SocialAccountLinkPage`입니다.
실제 HTTP·쿠키·DB 검사는 `AccountMailIntegrationTest`에서 수행하며 메일 발송 업체 부분은 시험용 응답으로 바꿉니다.
원본 링크는 React 메모리에만 보관하고 진입 시 주소창에서 제거해요. 저장소·로그에 코드나 비밀번호를 남기지 않습니다.

[Spring Boot 메일 연결](https://docs.spring.io/spring-boot/reference/io/email.html).
