# 판정 불가(어깨·얼굴이 안 보일 때) 처리: 앱 기준과 DevOps 판정에 필요한 변경

- 대상: 홍규(DevOps 판정 엔진 `platform/api-server` CEP)
- 작성: 동욱 요청, Claude 작성 (2026-10-08)
- 기준 코드: 앱 `lee_app1` `c9b472d`(develop PR #22), DevOps `origin/DevOps` `63490ea`
- 관련: [ADR 0012 세션 시간 정책](../decisions/0012-session-timing-policy.md), [실시간 계약 v1](../../contracts/realtime/README.md),
  [계획 0022](../plans/active/0022-kafka-realtime-pipeline.md), DevOps 작업 D-23(세션 정책·`phase`/`poor` 제외 구간)

이 문서는 세 가지를 맞추기 위한 것이다. 앱이 어떤 프레임을 "판정 불가"로 보는지,
판정 불가 동안 시간을 어떻게 다루기로 했는지, 그리고 지금 DevOps 판정 엔진이 그와 어떻게 다른지.
**2번 "확정된 변경"은 앱에도 아직 구현되지 않았다.** 앱과 서버를 같은 규칙으로 함께 바꾸려고 먼저 공유한다.

## 1. 앱의 현재 기준과 동작

### 판정 불가 기준 (프레임마다)

[pose.ts `features()`](../../model/prototype/pose.ts)에서 아래 중 하나라도 해당하면 그 프레임은 판정 불가다.

| 조건 | 값 |
|---|---|
| 코·왼어깨·오른어깨 중 하나라도 visibility가 낮음 | < 0.65 |
| 셋 중 하나라도 화면 가장자리에 걸림 | x 또는 y가 0.02 미만, 0.98 초과 |
| 어깨 폭이 너무 좁음(멀리 앉음, 옆으로 돌아앉음) | 화면 폭의 10% 미만 |

세 특징(`head_gap`, `lateral_offset`, `shoulder_tilt`)은 모두 어깨 폭으로 나눈 값이라, 어깨가 안 보이면 셋 다 계산할 수 없다.
"어깨만 빼고 고개만 판정"하는 부분 판정은 없다.

### 판정 불가일 때 지금 앱이 하는 일

[machine.ts `step()`](../../frontend/src/features/session/engine/machine.ts) 기준이다.

- 판정 불가 프레임이 **한 장만** 나와도 진행 중인 이탈 사건을 "끊김"(`recovered=false`, 사유 `unknown`)으로 닫는다.
- 붕괴 지속 시간(`hold`)과 시작 시각을 0으로 돌린다.
- 판정 불가 시간은 측정 유효 시간에서 뺀다.
- 카메라 입력이 1.5초 넘게 끊기면 측정을 멈추고, 사용자가 직접 재개해야 한다. 판정 불가와는 별개다.

### 앱이 보내는 값 (입력 v2 구간)

- 인접한 두 프레임 사이가 구간 1개다(지금은 약 33ms, 0.5초마다 묶어서 전송).
- 구간 양 끝 프레임 중 하나라도 판정 불가면 `measurement_quality: "poor"`, `features: null`이다. 판정 가능하면 `good`과 세 특징 변화량을 보낸다.
- `phase`는 지금 `running`만 보낸다. 멈춤 동안은 구간을 보내지 않는다.
- 이름 참고: 앱 화면과 내부 상태는 `unknown`(판정 불가)이고, 전송 값은 같은 뜻으로 `poor`다. 계약 버전을 지키려고 이름은 바꾸지 않는다.

## 2. 확정된 변경 (2026-10-08 동욱 결정, 앱도 구현 전)

| 상황 | 처리 |
|---|---|
| 판정 불가가 **3초 미만** | 판정 시계를 **그 자리에 멈춘다.** 붕괴 지속 시간과 복귀 시간을 0으로 돌리지 않고, 다시 보이면 이어서 센다. 안 보인 시간은 어느 쪽에도 넣지 않는다. 진행 중인 사건도 닫지 않는다. |
| 판정 불가가 **3초 연속** | 측정을 **멈춘다.** 진행 중인 사건은 "끊김"으로 닫고 시계는 0으로 돌린다. 화면에는 "측정 멈춤 – 어깨가 보이게 앉아 주세요"를 띄운다. |
| 멈춘 뒤 다시 보임 | 0.5초 연속으로 판정 가능하면 **자동 재개**한다. 버튼을 누를 필요가 없다. 새 시작으로 본다. |
| 카메라 입력 1.5초 넘게 끊김 | 지금처럼 멈추고 직접 재개한다(변경 없음). |

예: 구부정 2초 → 손이 어깨를 가려 1초 → 다시 구부정 1초.
지금 앱은 6초째에 경고하고(0으로 돌아갔다 다시 3초), 바뀐 규칙은 실제로 본 시간이 3초가 되는 4초째에 경고한다.
안 보인 1초를 붕괴로 셈하지는 않는다. 복귀 3초도 같은 방식이다.

### 복귀 대기 3초, 고개 돌림 뒤 1초 (2026-10-08 추가, 구현됨)

판정 불가였다가 다시 보이기 시작하면 **3초 동안은 판정하지 않고 `unknown`으로 둔다.**
사람이 화면에 돌아와 자세를 다시 잡는 중인데 바로 점수를 매기면 불쾌하다는 실제 사용 의견에 따른 것이다.
측정 화면(점수 표시 없음, "자세를 다시 잡는 중이에요" 안내), 서버로 보내는 구간(`poor`, `features: null`),
내보내기 txt·csv가 같은 규칙(`frontend/src/lib/returnSettle.ts`)을 쓴다.
고개 돌림(`head_turn`) 뒤에는 1초만 보류한다. 고개를 되돌리는 데는 오래 걸리지 않아서다.

위 3초 규칙을 구현할 때 주의한다. 복귀 대기 구간은 "안 보임"이 아니므로 **판정 불가 3초 연속에 세지 않아야 한다.**
**고개 돌림(`head_turn`) 구간도 세지 않아야 한다.** 옆 모니터를 3초 넘게 보는 것은 정상 행동인데, 세면 측정이 멈춘다.
세면 손이 어깨를 잠깐만 가려도 대기 3초가 더해져 측정이 멈춘다.
처음에는 2초로 넣었으나, 실제 촬영에서 2초가 지난 뒤에도 약 0.7초 동안 자리를 잡는 중이라 붕괴가 찍혀 3초로 늘렸다.

### 서버로 보내는 방식 (0.5초 구간 1개)

DevOps가 요청한 대로 약 0.5초를 구간 1개(`end_ms - start_ms ≈ 500`)로 합친다.

- 판정 가능한 프레임이 **절반 이상**이면 그 프레임들의 세 특징 변화량을 **평균**해서 `good`으로 보낸다.
- 절반 미만이면 `poor`, `features: null`로 보낸다. **절반 기준은 임시이며 다시 정한다.**
- 3초 규칙은 **앱이 판단한다.** 측정이 멈추면 앱은 그 사이 구간을 `phase: "rest"`로 보내고, 재개하면 `running`으로 돌아간다.
  서버는 `poor` 6개를 세어 같은 규칙을 다시 만들 필요가 없다. 같은 규칙을 두 곳에서 따로 만들면 앱과 서버 판정이 어긋난다.
- 서버 처리량 영향은 없다. 상태와 관계없이 1명당 0.5초에 1건으로 고정이고, 멈춤과 재개도 별도 메시지 없이 `phase` 값만 바뀐다.

## 3. DevOps 판정 엔진의 현재 동작과 차이

[PostureCepEngine.java](https://github.com/Jeon-Seho/sitting-posture-corrector/blob/DevOps/platform/api-server/src/main/java/com/posture/api/posture/cep/PostureCepEngine.java),
[inference-service consumer.py](https://github.com/Jeon-Seho/sitting-posture-corrector/blob/DevOps/platform/inference-service/app/consumer.py) 기준이다.
판정 불가를 따로 처리하는 함수가 아직 없어서 생기는 차이다.

| # | 지금 DevOps | 결과 | 앱 기준 |
|---|---|---|---|
| 1 | `UNKNOWN`이 정상과 같은 `handleNormal()`로 들어간다(`isCandidate`가 `NORMAL`·`UNKNOWN`이 아닐 때만 참) | 어깨가 3초 안 보이면 **복귀로 확정**된다. 붕괴 후보(`candidateSince`)도 지워진다 | 판정 불가는 정상도 붕괴도 아니다. 시계를 멈춘다 |
| 2 | 시계가 "언제부터" 시각(`candidateSince`, `recoverySince`)과 지금 `capturedAt`의 차이다 | 중간에 안 보인 시간까지 흐른 시간에 들어간다. 멈췄다 이어 셀 방법이 없다 | 판정 가능한 구간의 길이만 더한다 |
| 3 | 붕괴 후보가 `NORMAL`이 아닌 모든 상태다. 규칙 폴백은 `deviationScore ≥ 0.4`가 `WARNING`, `≥ 0.7`이 `BAD`다 | 0.4~0.7 점수도 붕괴 지속 시간에 들어간다 | 붕괴 후보는 세션 정책 `threshold`(현재 0.7) 이상만이다 |
| 4 | `phase`를 받지 않는다 | 멈춤 구간을 구별할 수 없다 | `rest`면 사건을 끊김으로 닫고 시계를 0으로 돌린다 |

복귀 3초, 재알림 60초는 이미 같다. 어깨 기울기 기준(0.13 → 0.03, ADR 0019)은 앱이 보내는 점수에 이미 반영되므로 서버에서 바꿀 것이 없다.

## 4. 요청하는 변경 (D-23에 포함)

1. **판정 불가 전용 처리를 추가한다.** `poor`(또는 추론 결과 `UNKNOWN`)는 `handleCandidate`도 `handleNormal`도 부르지 않는다.
   `candidateSince`, `recoverySince`, 진행 중인 사건을 그대로 둔다.
2. **시계를 누적 시간으로 바꾼다.** "언제부터" 시각 대신 판정 가능한 구간의 길이(`end_ms - start_ms`)를 더한 붕괴 누적 시간과 복귀 누적 시간을 둔다.
   지속 3초, 복귀 3초, 재알림 60초를 이 누적 시간으로 비교한다. 서버 시계를 통일한 것과 별개로,
   멈춘 동안의 시간을 빼려면 시각 차이가 아니라 누적이 필요하다.
3. **붕괴 후보 기준을 세션 정책에 맞춘다.** `session_started`의 `policy.threshold` 이상만 붕괴 후보로 본다. `WARNING`은 화면 표시용으로만 쓴다.
4. **`phase: "rest"`를 받으면** 진행 중인 사건을 끊김(`recovered=false`)으로 닫고 누적 시간을 0으로 돌린다. `rest` 구간은 판정에 넣지 않는다.
   `running`으로 돌아온 첫 구간부터 새로 센다.
5. 판정 불가 3초 판단은 서버에서 다시 하지 않는다. 앱이 보낸 `phase`를 믿는다.

### 확인용 예시 (구간 0.5초, 정책 3·3·60·0.7)

| 입력 | 기대 결과 |
|---|---|
| 붕괴 4개(2초) → `poor` 2개(1초) → 붕괴 2개(1초) | 마지막 구간에서 사건 확정(누적 3초). 실제 시각으로는 4초째 |
| 사건 진행 중 → `poor` 6개 미만 → 정상 6개 | 정상 6개째에 복귀 확정. `poor`는 복귀 시간에 안 들어감 |
| 사건 진행 중 → `poor`만 계속 | 앱이 3초째부터 `rest`를 보낸다 → 사건 끊김, 복귀로 기록되지 않음 |
| 점수 0.5 구간 10개 | 사건 없음(0.7 미만) |
| `rest` 구간 뒤 `running` 붕괴 6개 | 6개째에 새 사건 확정. 멈춤 전 누적은 이어지지 않음 |

## 5. 아직 정하지 않은 것

- 0.5초 구간의 절반 기준(임시).
- 판정 불가에 들어가고 나오는 기준을 다르게 두는 방법(예: 0.65 아래로 떨어지면 판정 불가, 0.70 이상이어야 다시 판정). 실제 visibility 기록을 보고 정한다.
- 보정 때 어깨가 화면 아래 끝에서 충분히 떨어져 있는지 확인하기. 구부정해지면 어깨가 내려가 화면 밖으로 밀려서,
  잡아야 할 자세가 판정 불가가 되는 문제가 있다. 앱에서 먼저 확인한다.
- Kafka 메시지 형식은 아직 DevOps가 기존 `/summary`(camelCase)다. 위 변경은 계약 v1 전환(D-21~D-23) 때 함께 반영하면 된다.
