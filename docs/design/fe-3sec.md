# FE 계획: 서버 3초 묶음 판정(`observation` 4.0)에 앱 맞추기

> 작성자: klaod-tech(FE) · 작성: 2026-10-30 · 상태: **계획**(코드 수정 전)
> 관련: BE 공지 「서버 3초 묶음·프레임마다 판정 · 실시간 `observation` 4.0」(김유진, 10/30, 저장소 밖), BE 브랜치 `feature/repo-server-frame-batch-inference`의 계획 0064·[API 명세](api-spec.md) 9·11장, [연동 명세](api-ws-spec.md) 5장, [FE 제안서](fe-server-proposal.md) BE-5 ②·BE-8, [ADR 0021](../decisions/0021-app-sends-information-server-judges.md)(판정은 서버)

## 1. BE가 바꾼 것과 이유

BE 브랜치 `feature/repo-server-frame-batch-inference`(김유진, 10/30, PR 전). 아래 이유는 BE 계획 0064 「정한 것」에서 옮겼다.

| # | 변경 | BE가 든 이유 |
| --- | --- | --- |
| 1 | 서버가 받은 좌표를 세션별로 **서버 시계 3초씩 묶어** 추론 서버에 넘긴다 | 10/27부터 앱이 프레임마다 보내는데(BE-8), 서버는 「자체적으로 묶겠다」고 답만 하고 코드가 없었다 |
| 2 | **프레임마다 판정**한다. 추론 서버 새 API `POST /v3/infer`가 프레임마다 결과를 낸다 | 구간 평균으로 판정하면 판정이 흐려진다(BE-8 팀장 결정 이유) |
| 3 | `valid_ms`는 판별 가능한 프레임 시간만 센다 | FE 요청 BE-5 ② 해결 |
| 4 | `observation`이 **4.0**: `valid`·`posture`(새로)·`collapse_probability`·`invalid_reason`만 남는다 | 앱이 측정 중 화면에 쓰는 값만 남긴다. 처리 위치·상태·누적 시간은 `ack`·`progress`·`summary`에 이미 있다 |
| 5 | `observation`은 묶음마다 1개, 묶음의 **마지막 판정 가능 프레임** 값이다 | 화면은 마지막 `observation` 하나로 「지금 자세」를 그리므로 같은 화면이 나온다 |
| 6 | `model_version`을 뺀다 | DB에 저장하지 않고, 앱은 기록 비교 경고에만 쓴다. 지난 기록도 서버가 지금 값으로 채워 경고가 의미 없다 |
| 7 | `ack`는 받는 즉시, `observation`·`decision`·`alert`·`progress`는 묶음 처리 뒤(최대 3초 늦게) | 판정 결과는 묶음 단위로만 생긴다 |
| 8 | 새 사건은 `decision`을 보내기 전에 DB에 쓴다 | `ack`가 판정보다 먼저 가게 되어 「저장됨」 신호가 바뀐다 |

**바뀌지 않는 것:** 앱이 보내는 것(`hello`·`features`·`phase`·`end`), `ready`·`decision`·`alert`·`closed` 형식, REST API, DB. `invalid_reason` 값 목록(`unmeasurable`·`head_turn`·`settling`)도 같다.

`posture`는 `collapse_probability`를 대신하지 않는다. 둘 다 같은 프레임의 값이고, `posture`는 서버가 그 확률에 세션 기준선(`threshold`, 기본 0.7)을 적용한 **그 순간의 좋음(`good`)·나쁨(`bad`) 판정**이다. 3초 확정은 지금처럼 `decision`·`alert`다.

## 4. 3초 묶음이 화면에 주는 영향

판정 기준 시각은 그대로 앱 시계(`t_ms`)다. 늦어지는 것은 **결과를 보내는 시각**이다 — 서버가 프레임을 3초 모았다가 한 번에 판정하고 그때 결과를 몰아서 보낸다.

예시(묶음이 0·3·6초에 처리된다고 가정, 무너짐 확정 기준 3초):

| 시각 | 일어나는 일 |
| --- | --- |
| 0.5초 | 자세 무너짐(점수 30점 미만) |
| 0.5~3.5초 | 그 프레임이 든 묶음이 처리되면 ① 화면 알림 시작 |
| 3.5초 | 서버 기준(`t_ms`)으로 3초 이어짐 → 확정. 결과는 다음 묶음 처리 때 |
| 확정 뒤 0~3초 | ② 강한 경고 + 알림 |

①·② 순서는 지켜지지만 둘 다 묶음 처리 시각에 맞춰 최대 3초씩 늦다(평균 약 1.5초).

| 항목 | 늦어지나 | 내용 |
| --- | --- | --- |
| ① 화면 알림, ② 강한 경고·알림 | 예, 0~3초 | 위 예시 |
| 바로 앉았을 때 경고가 꺼지는 것 | 예, 0~3초 | 회복도 `decision`, `posture`도 묶음마다 |
| 점수 | 약 3초마다 한 번 바뀜 | 지금은 부드럽게 바뀐다 |
| 측정 시작 직후 | 첫 0~3초 서버 값 없음 | 3장 3번 |
| `head_turn` 안내 | 예, 0~3초 | 서버가 판정하는 이유 |
| 어깨가 안 보일 때 「확인할 수 없어요」 | **아니요** | 앱이 바로 표시(`placeable`) |
| 쉬기·자리 비움·측정 종료 | **아니요** | 서버가 3초를 기다리지 않는다 |
| 기록 숫자(유지율·시간) | **아니요** | 판정은 `t_ms` 기준. `valid_ms`는 더 정확해진다 |

줄이는 방법: 서버 설정 `POSEGOOD_REALTIME_BATCH_WINDOW`(기본 `3s`). 대가는 추론 호출 수다(동시 50명 기준 어림값).

| 설정 | 최대 지연 | 추론 호출 |
| --- | --- | --- |
| `3s` | 약 3초 | 1초에 약 17번 |
| `1s` | 약 1초 | 1초에 약 50번 |
| `0s` | 거의 없음 | 프레임마다(10fps면 1초에 약 500번) |

## 7. 위험과 확인할 것

- **배포 순서:** BE만 먼저면 운영 측정 화면에 점수가 안 나온다. FE만 먼저면 지금 서버의 3.0 메시지를 버린다. **두 PR을 같은 날 넣는다.** 3.0·4.0을 둘 다 받게 만들 수도 있지만, BE가 옛 앱을 따로 지원하지 않기로 정해(계획 0064 8번) 맞추지 않는다.
- **서버 재배포와 포크 최신화 시점:** 운영 서버(DevOps)와 Vercel(FE, 포크) 반영을 같은 때로.
- **계획 번호 충돌:** develop에는 #81이 `docs/plans/completed/0064-frontend-camera-resilience.md`를 이미 썼고, BE 브랜치도 `docs/plans/active/0064-server-3s-frame-batch-inference.md`를 쓴다. 김유진님께 BE 계획 번호를 바꿔 달라고 알린다.
- **`posture` 값 이름:** `good`·`bad`는 ML 확인 전이다(ADR 0043, 제안). 바뀌면 3장 2번 조건도 맞춘다.
- **① 깜빡임:** `posture`는 묶음의 마지막 프레임 하나의 값이라, 기준선 근처에서는 3초마다 켜졌다 꺼질 수 있다. 화면 확인 때 보고 필요하면 화면 담당과 표시 방식을 정한다.
