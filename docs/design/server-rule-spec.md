> 시험 데이터: [`contracts/examples/frames/reference-rule-cases.json`](../../contracts/examples/frames/reference-rule-cases.json)

앱은 판정하지 않고 관절 좌표만 보낸다(ADR 0021). 판단은 전부 서버가 한다. 앱에서 판정하면 규칙·모델을 고칠 때 과거 자료를 다시 계산할 수 없기 때문이다.
이 문서는 ① 앱이 보내는 입력, ② 지금 앱이 하는 판정을 서버가 같은 결과로 만들기 위한 규칙, ③ 판정 불가 시간 처리, ④ 서버가 앱에 돌려줄 것을 정리한다.
값은 실험으로 정한 임시값이며 의학적 기준이 아니다. 자세 유형(머리·좌우 기울임)은 앱이 표시하지 않으므로 적지 않는다.

## 0. 같은 결과인지 확인하는 방법

- 시험 데이터의 `frame_cases`·`sequence_cases`·`calibration_case`를 서버 구현에 넣고 `expected`와 비교한다.
- 실수는 **절대 오차 1e-9 이내**로 비교한다. 같은 크기의 변화도 연산 때문에 마지막 자리가 다르다(예: `head_drop` 0.7159090909090908, `head_rise` …0915).
- 경계 비교(`> 0.15`, `>= 0.65`)는 **아래 식과 같은 연산 순서**로 계산한다. 순서가 다르면 경계 사례 `head_turn_float_boundary`의 결과가 바뀐다.
- 시험 데이터는 앱 코드로 만들었다. 앱 시험(`referenceRuleCases.test.ts`)이 매번 코드와 파일이 같은지 확인한다.

## 1. 입력: 좌표 프레임 메시지 (FE 초안 `posture.frames.v1`)

**관절·형식은 BE·ML 요구를 따른다.** 아래는 FE 초안이며 정해지면 계약 스키마로 만든다([제안서](devops-integration-proposal.md) Q2).

**0.5초에 1건. 그 안에 찍힌 프레임을 가공하지 않고 그대로 담는다.** 메시지는 게이트웨이를 거쳐 Kafka로 간다(키 `session_id`).

```json
{
  "sequence": 42,
  "start_ms": 21000,
  "end_ms": 21500,
  "phase": "running",
  "frames": [
    { "t_ms": 21012, "p": [[0.51234, 0.40211, 0.99], [0.52011, 0.38120, 0.98], "... 9개"] },
    { "t_ms": 21075, "p": null }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `sequence` | 세션 안 순번. 0부터 1씩 증가. 중복 제거·재전송에 쓴다 |
| `start_ms`, `end_ms` | 구간 `[start, end)`. 세션 시작 기준 ms, 보통 500ms 간격 |
| `phase` | `running` / `calibration`(보정) / `rest`(일시정지) / `away`(카메라 끊김) |
| `frames[].t_ms` | 프레임이 찍힌 시각. 세션 시작 기준 ms |
| `frames[].p` | 관절 9개의 `[x, y, visibility]`(아래 순서). 사람이 안 잡힌 프레임은 `null` |

| 순서 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| 관절 | 코 | 왼눈 | 오른눈 | 왼귀 | 오른귀 | 입 왼쪽 | 입 오른쪽 | 왼어깨 | 오른어깨 |
| MediaPipe 번호 | 0 | 2 | 5 | 7 | 8 | 9 | 10 | 11 | 12 |

- **좌표**: x, y는 영상 크기에 대한 0~1 비율(소수 5자리), visibility는 소수 2자리. y는 아래로 커진다.
- **영상 크기**(`width`, `height`)는 세션 시작 메시지에 한 번만 넣는다. 거리 계산에 필요하다. 팀 카메라 전제로 640×480을 요청한다.
- **좌우**: 영상은 반전하지 않는다. 관절 이름의 좌우는 사용자 몸 기준이라 사용자 왼어깨가 화면 오른쪽(큰 x)에 있다.
- **visibility가 낮은 관절도 좌표는 온다.** MediaPipe는 가려진 관절 위치도 추정해 준다. 판정 가능 여부는 visibility로 정한다(2장).
- **프레임 수는 일정하지 않다.** 보통 0.5초에 약 8개(초당 약 16)지만 느린 PC는 3~5개, 빠른 PC는 15개까지 나온다. 상한 30개.
  시간 계산은 프레임 개수가 아니라 `t_ms`로 한다.
- **시각은 앱 시계 기준이다.** 지속 시간·3초 규칙·복귀 시간은 서버 수신 시각이 아니라 `t_ms`·`start_ms`·`end_ms`로 계산한다. 네트워크 지연이 판정에 섞이지 않는다.
- 앱은 표시용으로만 좌표를 부드럽게 만들고, 보내는 좌표는 MediaPipe 원본이다.
- **양**: 1건 약 2KB, 1명 1시간 약 10~15MB. 좌표는 HDFS에 적재한다. 좌표 전송은 가입 때 동의한 사용자만 한다.

### 앱이 알리는 사실: `rest`·`away`

판단이 아니라 사실이라 앱이 알린다. 메시지가 안 오는 것만으로는 서버가 네트워크 끊김과 구별할 수 없다.

| 상황 | 앱이 보내는 것 | DB 제외 사유 |
|---|---|---|
| 사용자가 일시정지 | `phase: "rest"`, `frames: []` | `PAUSE` |
| 카메라 입력이 끊김 | `phase: "away"`, `frames: []` | `MISSING` |

다시 시작하면 `running`으로 돌아간다. 카메라 끊김 뒤에는 사용자가 직접 재개한다. 판정 불가 때문에 `rest`를 보내는 일은 없다(`rest`는 일시정지 전용).
카메라 끊김 기준은 지금 앱에 두 가지가 있다(프레임 간격 1000ms, 카메라 입력 없음 1500ms). 서버와 하나로 맞춘다(10장).

## 2. 프레임 특징값

코 N, 왼어깨 L, 오른어깨 R 중 하나라도 아래에 해당하면 **판정 불가**(특징값 없음)다.

| 조건 | 값 |
|---|---|
| 좌표나 visibility가 유한수가 아님 | |
| visibility | `< 0.65` 또는 `> 1` |
| 가장자리 | x 또는 y가 `< 0.02` 또는 `> 0.98` |
| 어깨 폭 `span = hypot((L.x − R.x)·W, (L.y − R.y)·H)` | `span < W · 0.1` |

판정 가능하면 (px 단위를 어깨 폭으로 나눈다):

```
cx = (L.x + R.x) / 2
cy = (L.y + R.y) / 2
head_x = (왼귀.x + 오른귀.x) / 2        # 두 귀 x가 유한수일 때. 아니면 N.x
head_gap         = (cy − N.y) · H / span
lateral_offset   = (head_x − cx) · W / span
shoulder_tilt    = (L.y − R.y) · H / span
quality          = min(N.vis, L.vis, R.vis)
head_turn_offset = (N.x − head_x) · W / span
```

- 귀는 **visibility를 보지 않는다**(사례 `ears_low_visibility_still_used`).
- 특징값이 있어도 `quality`가 0.65 미만이면 판정에 쓰지 않는다(5장).

## 3. 기준 자세 (보정)

| 규칙 | 값 |
|---|---|
| 연속 시간 | 첫 프레임부터 3000ms 이상 |
| 최소 표본 | 판정 가능한 프레임 15개 이상 |
| 끊김 | 판정 불가 프레임이 하나라도 나오거나 프레임 간격이 1000ms를 넘으면 처음부터 다시 |
| 기준값 | **프레임마다 계산한 특징값 5개의 평균**(`head_turn_offset` 포함) |

보정마다 앱이 새 `calibration_uuid`를 만들고 `calibration_sec`(3.0)·`sample_count`와 함께 입구 API로 보낸다. 재보정하면 새 ID다.
세션 행에는 DB의 기준 자세 값이 복사된다(DB C-2). 보정 프레임 원본은 `phase: "calibration"`으로 Kafka→HDFS에 보내며 판정에는 쓰지 않는다.

**정해야 할 것 — 기준값 계산 방식.** v4 회신은 "앱이 좌표 9개의 x·y 평균 18개를 보낸다"였다.
서버가 그 평균 좌표로 특징값을 다시 계산하면 앱(특징값의 평균)과 값이 조금 다르다. `calibration_case`에서
`head_gap` 0.75395 vs 0.75376, `shoulder_tilt` 0.00402 vs 0.00377이다(어깨 기울기 허용 폭 0.03 대비 약 0.8%).
또 평균 18개에는 visibility가 없어서 기준의 `quality`를 알 수 없다. FE 제안: 서버가 보정 프레임 원본(`calibration`)으로
앱과 같은 방식(특징값 평균)을 계산하거나, 앱이 특징값 평균 5개와 `quality`를 함께 보낸다. 평균 좌표 18개는 저장용으로만 둔다.

## 4. 고개 돌림

```
head_turned = |current.head_turn_offset − baseline.head_turn_offset| > 0.15
```

- 현재·기준 특징값이 모두 유효(5장 조건)할 때만 검사한다.
- 고개 돌림 프레임은 **판정하지 않는다**(`head_turn`). 판정 불가와 구분한다. 복귀 대기 시간이 다르다(6장).
- 0.15 이하는 그대로 판정한다(`slight_head_turn`). 실제 촬영(10/08)에서 자세 변화는 최대 0.06, 끝까지 돌린 고개는 0.15~0.4였다.

## 5. 변화량과 점수

현재·기준이 모두 유효해야 한다: 특징값 4개(`head_gap`·`lateral_offset`·`shoulder_tilt`·`quality`)가 유한수이고 `0.65 ≤ quality ≤ 1`.

```
d_head  = current.head_gap       − baseline.head_gap
d_side  = current.lateral_offset − baseline.lateral_offset
d_tilt  = current.shoulder_tilt  − baseline.shoulder_tilt
score   = min(1, max(|d_head| / 0.22, |d_side| / 0.2, |d_tilt| / 0.03) · 0.7)
```

- `score ≥ threshold`(기본 0.7, 사용자 0.5~0.95)이면 붕괴 후보다. 세 변화 중 하나가 허용 폭만큼이면 0.7이 된다.
- 이 식은 DevOps `inference-service/app/realtime.py`의 `score_feature_deltas`와 같다.
- `pose.ts`의 `classify()`는 예전 식(`amount / 2`)이고 앱 시험에서만 쓴다. 서버 기준이 아니다.

## 6. 복귀 대기

판정 불가나 고개 돌림 뒤에는 사용자가 자세를 다시 잡는 중이라 잠시 판정하지 않는다(실사용 의견: 돌아오자마자 점수가 매겨지면 불쾌하다).

```
hold_until = −∞
프레임마다 (시간 순서대로):
  판정 가능          → judged = (t ≥ hold_until)
  판정 불가          → hold_until = max(hold_until, t + 3000); judged = false
  고개 돌림          → hold_until = max(hold_until, t + 1000); judged = false
```

- 보류는 **늘어나기만 한다**. 판정 불가 보류 중 고개를 돌려도 짧아지지 않는다(`turn_inside_unmeasurable_hold`).
- 보류 중 프레임은 바른 자세도 붕괴도 아니다.
- 3초인 이유: 처음 2초로 넣었으나 실제 촬영에서 2초 뒤에도 약 0.7초 동안 자리를 잡는 중이라 붕괴가 찍혔다.

## 7. 판정 불가 시간 처리 (2026-10-08 결정, 서버가 처음 구현)

**앱에도 구현되지 않은 규칙이다.** 시험 데이터에 기대값이 없고, 아래 예시로 확인한다.

| 상황 | 서버 처리 |
|---|---|
| 판정 불가 **3초 미만** | 붕괴·복귀 시계를 **그 자리에 멈춘다.** 0으로 돌리지 않고 진행 중인 사건도 닫지 않는다. 안 보인 시간은 어느 쪽에도 넣지 않는다 |
| 판정 불가 **3초 연속** | 측정을 멈추고 진행 중인 사건을 "끊김"(`recovered=false`)으로 닫는다. 시계는 0. 앱에 멈춤 상태를 알린다("측정 멈춤 – 어깨가 보이게 앉아 주세요") |
| 멈춘 뒤 **0.5초 연속 판정 가능** | 자동 재개하고 새로 센다(새 사건). 사용자가 버튼을 누르지 않는다 |
| `rest`·`away` | 진행 중인 사건을 끊김으로 닫고 시계를 0으로. 그 구간은 판정에 넣지 않는다 |

**꼭 지킬 점**

- **고개 돌림(4장)과 복귀 대기(6장) 구간은 3초 연속에 세지 않는다.** 옆 모니터를 3초 넘게 보는 건 정상 행동이라, 세면 측정이 계속 멈춘다.
  복귀 대기를 세면 손이 어깨를 잠깐 가린 것만으로 대기 3초가 더해져 측정이 멈춘다.
- 이 구간들은 붕괴 시간에도 복귀 시간에도 넣지 않는다.
- 붕괴 후보는 세션 정책 `threshold` 이상만이다. 반대 상태 구간이 하나라도 오면 그쪽 누적은 0이다(정상 1구간이면 붕괴 누적 0).
- 같은 세션의 같은 `sequence`는 한 번만 반영한다(재연결 때 앱이 같은 순번을 다시 보낸다).

**확인용 예시** (구간 0.5초, 정책 3·3·60·0.7)

| 입력 | 기대 결과 |
|---|---|
| 붕괴 4개(2초) → 판정 불가 2개(1초) → 붕괴 2개(1초) | 마지막 구간에서 사건 확정(누적 3초). 실제 시각으로는 4초째 |
| 사건 진행 중 → 판정 불가 6개 미만 → 정상 6개 | 정상 6개째에 복귀 확정. 판정 불가는 복귀 시간에 안 들어감 |
| 사건 진행 중 → 판정 불가만 계속 | 3초째에 측정 멈춤, 사건 끊김. 복귀로 기록하지 않음 |
| 점수 0.5 구간 10개 | 사건 없음(0.7 미만) |
| `rest` 구간 뒤 `running` 붕괴 6개 | 6개째에 새 사건 확정. 멈춤 전 누적은 이어지지 않음 |

**지금 DevOps v1 판정기(`f27f778`)와 다른 점.** 판정 가능한 구간 길이 누적, 정책 `threshold`, `rest`·`away`, 같은 순번 무시, 반대 상태 누적 0은 이미 맞다.
다른 점은 판정 불가(`valid=false`) 구간이 하나만 와도 **바로** 사건을 끊고 누적을 0으로 돌리는 것이다. 코드 주석에 "`invalid_reason`이 생긴 뒤 D-23에서 바꾼다"고 되어 있다.

## 8. 서버가 앱에 돌려줄 것

화면은 서버 결과로만 바뀐다. WebSocket 메시지(`hello`·`ack`·`observation`·`progress`·`decision`·`alert`·`stalled`·`closed`)는 [실시간 계약 v1](../../contracts/realtime/README.md)을 따른다.

| 항목 | 내용 |
|---|---|
| `observation.invalid_reason` | `valid=false`일 때만 채운다. `unmeasurable`("자세를 확인할 수 없어요") / `head_turn`("고개를 돌린 동안은 판정하지 않아요") / `settling`("자세를 다시 잡는 중이에요"). 없으면 앱이 안내를 못 띄운다 |
| 측정 멈춤·재개 | 7장의 3초 연속 멈춤과 자동 재개를 앱이 알 수 있어야 한다 |
| `excluded_started`·`excluded_ended` | 제외 구간 경계 사건(DB `excluded_interval`). 앱은 받기만 하고 화면에 표시하지 않는다. 사유는 DB 4개(`PAUSE`·`MISSING`·`ABSENCE`·`UNMEASURABLE`), 고개 돌림·복귀 대기는 `UNMEASURABLE` |
| `alert` | 알림 켜기·끄기와 시간당 상한은 서버가 판단한다. 앱은 `alert`가 오면 띄우기만 한다 |
| DLQ | 처리 못 한 메시지는 `posture.dlq`로 넘기고 다음 메시지를 처리한다 |

화면 반응은 0.5초 묶음에 처리 시간이 더해져 약 0.5~1초 늦다. 판정이 3초 지속 기준이라 큰 문제는 없다.

## 9. 지금 앱의 구간 만들기 (참고)

지금 앱은 좌표가 아니라 특징 변화량을 보내며, **이웃한 두 프레임 사이 `[이전 t, 현재 t)`를 구간 하나**로 보낸다(약 60ms). 시험 데이터의 `sequence_cases`가 이 규칙이다.

| 규칙 | 값 |
|---|---|
| 첫 프레임 | 다음 구간의 시작점으로만 쓴다 |
| 구간 품질 | 두 끝 프레임이 모두 `judged`면 `good`, 아니면 `poor` |
| 구간 점수 | `good`이면 **현재(끝) 프레임**의 변화량·점수 |
| 프레임 간격 > 1000ms | 구간을 보내지 않고 측정을 멈춘다. 사용자가 직접 재개한다 |
| 카메라 입력 없음 > 1500ms | 측정을 멈춘다(화면 쪽 감시). 직접 재개 |
| 일시정지 | `phase: "rest"`, `poor`, 특징값 없음 |

서버가 좌표 프레임을 받으면 2~6장을 프레임마다 적용하고, 판정 단위(프레임 / 0.5초 구간)를 정한다(10장 #2).

## 10. 서버로 옮기면서 정할 것

| # | 항목 | 지금 상태 |
|---|---|---|
| 1 | 기준값 계산 방식 | 3장 |
| 2 | 판정 단위 | 프레임마다 판정하면 9장 규칙을 그대로 쓸 수 있다. 0.5초 구간 하나로 줄이려면 "판정 가능 프레임이 절반 이상이면 평균, 아니면 판정 불가"(임시)를 정해야 한다 |
| 3 | 판정 불가 3초 연속 규칙과 시계 멈춤 | 7장. DevOps D-23 |
| 4 | 판정 불가 진입·해제 기준을 다르게 둘지 | 예: 0.65 아래로 떨어지면 판정 불가, 0.70 이상이어야 다시 판정. 실제 visibility 기록을 보고 정한다 |
| 5 | 카메라 끊김 기준 | 1000ms / 1500ms 중 하나로 맞춘다 |
| 6 | 보정 때 어깨가 화면 아래 끝에서 충분히 떨어져 있는지 | 구부정해지면 어깨가 화면 밖으로 밀려 판정 불가가 되는 문제. 앱의 구도 확인에서 먼저 본다 |

## 11. 서버 부담 (동시 50명, 하루 8시간 추정)

| 항목 | 특징값 전송(지금) | 좌표 전송(바뀐 뒤) |
|---|---|---|
| 메시지 수 | 0.5초에 1건 | 같다 |
| 메시지 크기 | 수백 바이트 | 약 2KB |
| Kafka 유입량 | 수십 KB/s | 약 200KB/s |
| 서버 계산 | 0.5초당 점수 1번 | 프레임마다 검사·특징값·고개 돌림, 초당 약 800프레임(계산은 가볍다) |
| 저장 | MySQL에 결과만 | HDFS에 좌표 약 5GB/일 추가 |

실제 부담은 구현·운영이다: 새 처리 단계(2~6장), 세션별 상태 보관(기준값·복귀 대기·판정 불가 연속 시간, 재시작 뒤에도 이어지게 Redis 등),
보정 처리, 3초 규칙과 자동 재개, `invalid_reason`, HDFS 적재·동의 철회 삭제·보존, 임계값 변경 시 재처리(좌표가 남아 있어 가능), 서버 장애 시 화면 판정 정지.

## 12. 시험 데이터 구조

| 키 | 내용 |
|---|---|
| `constants` | 이 문서의 값 |
| `baseline` | 기준 자세 좌표 한 장과 그 특징값. `frame_cases`는 이 기준과 비교한다 |
| `frame_cases[]` | 좌표 한 장 → `features`, `observed`(`measurable`·`unmeasurable`·`head_turn`), `deltas`, `score` |
| `sequence_cases[]` | 시간 순서 프레임(이름은 `frame_cases` 참조) → 프레임별 `judged`, 구간(`good`/`poor`, 점수), `paused_at_ms` |
| `calibration_case` | 보정 16장 → 앱 기준값과 평균 좌표로 계산한 값(3장 비교용) |

다시 만들기: `frontend`에서 `UPDATE_RULE_CASES=1 npx vitest run referenceRuleCases`. 앱 규칙을 바꾸면 이 파일도 다시 만든다.
