# 측정 종료·저장 확인 계획

> 작성자: klaod-tech(FE) · 작성: 2026-11-11
> **이 문서의 역할:** 「측정 종료」부터 기록이 서버에 저장됐다고 확인될 때까지 앱이 무엇을 보여 주는지 정리하고, 아직 정하지 않은 것과 BE에 요청할 것을 모은다. 계기는 DevOps/BE의 D-57 Kafka 경로 통신 시험 보고서 검수다. 메시지·API 형식은 [연동 명세](api-ws-spec.md), 화면 동작 규칙은 [FE 기능 명세](fe-feature-spec.md)다.

## 1. 전제

- **kafka 모드는 아직 개발 중이다.** 코드는 `feat/ws-kafka-pipeline`(D-57) 브랜치에만 있고 develop에는 없다. 보고서 기준 「회의 → 수정 → FE 포함 통신 시험 통과 → develop 병합」 순서이고, 병합 뒤에도 서버 기본값은 local이다.
- **운영 서버는 local 모드다.** io-api 한 곳에서 판정·저장하고, `end` 뒤 `closed`는 1초 안에 온다.
- **웹과 데스크톱 앱은 같게 동작한다.** 한쪽에서만 되는 처리(예: 데스크톱에서 닫기를 붙잡고 저장을 기다린 뒤 닫기)는 만들지 않는다.

```
local 모드 (운영):  앱 → io-api(판정·저장) → 앱
kafka 모드 (D-57):  앱 → io-api → Kafka → 추론 → 판정 → 저장(DB) → io-api → 앱
```

## 2. 지금 앱이 하는 일

### 2.1 「측정 종료」를 누른 뒤

| 순서 | 앱 동작 | 코드 |
|---|---|---|
| 1 | `end`를 보내고 화면 전체를 덮는 「측정 결과를 저장하고 있어요」 창을 띄운다. Esc로 닫히지 않는다 | `LiveSessionPage` `EndingDialog` |
| 2 | `closed`가 오면 창을 닫고 결과 화면 | `LiveSession.handle` |
| 3 | **5초** 안에 `closed`가 없으면 S4로 결과를 한 번 읽는다. `end` 뒤 연결이 먼저 끊기면 바로 읽는다 | `END_TIMEOUT_MS`, `fetchResult` |
| 4 | S4가 화면에 보이던 것보다 적게 측정했다고 답하면(`summary.total_ms`가 작음, kafka 모드의 빈 메모리 엔진) 그 응답은 버리고 마지막 `progress` 결과로 끝낸다. `last_sequence`로 비교하지 않는 것은 DB로 다시 만든 응답이 -1을 주기 때문이다 | `fetchResult` |
| 5 | 5초를 넘겨 넘어왔고 서버가 종료를 확인해 주지 않았으면(`session_ended` 없음) 결과 화면 맨 위에 안내를 띄운다(아래) | `lateResult` |
| 6 | 기록은 이 기기의 대기 기록으로 남고, 측정 중이 아닐 때 15초마다 R1로 확인한다 | `useSessionPersistence.syncRecords` |

5번 안내:

> **서버 응답이 늦어 결과를 먼저 보여 드려요**
> 사용자 잘못이 아니에요. 측정 기록은 서버에 저장되고 있고, 저장이 확인되면 기록에 자동으로 반영돼요.

5초로 정한 근거: local 모드는 1초 미만, kafka 모드 정상은 1~3초로 본다(서비스 4~5단계, 단계마다 Kafka가 최대 0.5초 모음, **실측 없음** — 7장 시험에서 잰다). 5초를 넘는 건 서비스 재시작·Kafka 소비자 재배치·DB 지연 같은 장애 때뿐이고, 그때는 기다려도 안 올 수 있다.

### 2.2 kafka 모드 대비 (local에서는 해당 상황이 생기지 않음)

| 상황 | 앱 처리 |
|---|---|
| S4가 「0분 측정」을 돌려줌(io-api가 판정을 안 함) | 2.1의 4번 |
| `alert`가 저장 서비스를 거쳐 따로 와서 회복 뒤나 「측정 종료」 뒤에 도착 | 울리지 않는다. 그 사건이 이미 `recovery_confirmed`·`interrupted`·`session_ended`로 닫혔는지 `event_id`로 본다(서버에서 `event_id`는 세션마다 1씩 커지고 `alert`는 그 사건 번호를 쓴다) |
| 종료 뒤 5~6초에 `stalled`가 옴 | 보이지 않는다. 앱이 5초에 이미 넘어가 2.1의 5번 안내로 알린다 |
| `ack`가 판정 결과보다 먼저, `progress`가 약 1초마다 옴 | 앱은 순서에 기대지 않는다(`decision`·`progress`는 같은 토픽·같은 키라 서로 순서는 지켜진다) |

### 2.3 측정 중 강제 종료 (웹 탭 닫기, 데스크톱 X·Alt+F4)

| 단계 | 웹 | 데스크톱 앱 |
|---|---|---|
| 닫으려 할 때 | 브라우저 기본 창 「사이트에서 나가시겠습니까?」(`beforeunload`, 문구는 브라우저가 정함) | 앱 본체가 「측정 중이에요. 정말 닫을까요? [닫기] [계속 측정]」(`main.cjs` `will-prevent-unload`). Electron은 `beforeunload`가 막으면 아무것도 묻지 않고 닫기를 무시해서 따로 묻는다 |
| 그래도 닫으면 | 서버가 연결 끊김을 보고 마지막으로 받은 구간까지 세션을 끝내 저장한다. 끊김 신호가 없어도 120초 동안 메시지가 없으면 같은 처리 | 같음 |
| 다음에 열 때 | 1초마다 남긴 대기 기록을 R1과 맞춰 본다 | 같음 |
| 못 막는 것 | 작업 관리자 종료, 전원 꺼짐(서버 저장·대기 기록은 그대로 동작) | 같음 |

데스크톱 확인 창은 지금 OS 기본 대화상자다. 앱은 PiP 창처럼 앱 디자인에 맞춘 창을 띄울 수 있으므로 5.3에서 정한다. 앱 본체를 고친 것이라 설치 파일을 다시 배포해야 반영된다.

### 2.4 측정을 시작할 때 서버 이상

kafka 경로의 io-api는 `hello`를 받으면 `session_started`를 Kafka에 쓰고, 못 쓰면 `ready` 전에 `closed(session_lost)`를 보낸다(`KafkaPipeline.open` → 503 → `RealtimeHandlerV2.refusal`). WS로 Kafka 상태가 따로 오지는 않지만 이 첫 응답이 시작 시점의 확인 역할을 한다.

| 받은 것 | 앱 동작 |
|---|---|
| `ready` 전 `closed(session_lost)`, S1 5xx | 측정 화면 자리에 오류 화면(500 그림) 「지금은 측정을 시작할 수 없어요 — 사용자 잘못이 아니에요. 서버의 측정 기능에 문제가 있어요. 잠시 뒤 다시 시작해 주세요」, 버튼 「다시 준비하기」. 기록은 남기지 않는다 (`LiveState.serverDown`, `ERROR_PAGES.measure`) |

전에는 이 경우 「서버에서 측정이 끝났어요. 확인된 시간까지 저장됐어요」가 떴다. 측정한 것이 없는데 저장됐다고 말하던 것을 고쳤다(2026-11-11).

## 3. 끝내 저장되지 않는 경우

> **2026-11-11 kafka 코드 대조 뒤 결정:** 추론·판정·저장 서비스나 Kafka가 멈추는 경우는 쿠버네티스 재시작으로 복구되고(BE), 기록은 Kafka가 들고 있다가 처리되고 Hadoop에도 남는다. 그보다 큰 장애(데이터 유실)는 FE가 대비하지 않는다. 아래 표와 4장은 local 모드 「측정 중 서버 재시작」 같은 남은 경우에만 해당한다.

| 모드 | 늦지만 결국 저장됨 | 끝내 저장 안 됨(R1에 끝난 기록으로 안 나옴) |
|---|---|---|
| kafka | 대부분. 앱에 `ack`를 보내기 전에 Kafka가 디스크에 보관하므로 서비스가 살아나면 이어서 처리 | 메시지가 처리 불가로 DLQ에 빠짐, Kafka 보관 기간보다 긴 장애 |
| local | 서버 잠깐 지연 | **측정 중 서버 재시작**(메모리 세션이 사라지고 DB 행은 `ended_at` NULL로 남음, [연동 명세](api-ws-spec.md) 4장 S4 「남는 틈」), 종료 순간 DB 장애 |

그때 지금 앱의 불편한 점:

1. **기록 목록에 안 보인다.** 기록·달력은 R1만 보여 주고, 대기 기록은 홈의 「서버 저장 확인을 기다리는 기록 n개 · 이 기기에 임시 보관 중」 띠에 개수로만 나온다.
2. **영원히 기다린다.** 대기 기록에 끝이 없어 이 띠가 사라지지 않는다.
3. **로그아웃이 막힌다.** 대기 기록이 있으면 「결과 저장을 완료한 뒤 나가 주세요」로 로그아웃을 막고 계정 화면도 잠근다(`LocalServiceApp.logout`). 저장이 끝내 안 되면 빠져나갈 길이 없다. 가장 큰 문제다.

## 4. 제안 (FE, 웹·앱 공통)

| # | 할 일 | 효과 |
|---|---|---|
| 1 | 대기 기록을 기록 목록에 「서버 확인 중」 표시와 함께 보여 준다 | 방금 측정이 사라진 것처럼 보이지 않는다 |
| 2 | 일정 시간(안: 하루)이 지나도 확인되지 않으면 「서버에 저장되지 못했어요」로 바꾸고, 사용자가 지울 수 있게 한다 | 끝없는 대기가 끝난다 |
| 3 | 로그아웃을 막지 않고 「이 기기에 확인 대기 기록이 남아 있어요. 다시 로그인하면 이어서 확인해요」를 묻고 보낸다. 대기 기록은 계정별 키라 다시 로그인하면 이어진다 | 빠져나갈 길이 생긴다 |

## 5. 정할 것

### 5.1 끝내 저장되지 않을 때 (4장)

- 1~3을 모두 할지, 3번(로그아웃 막힘)부터 할지
- 2번의 기준 시간(안: 하루)

### 5.2 「서버 응답이 늦다」를 실제 서버 상태로 판단하기 (D-57 병합 뒤)

피드백: 5초 타이머만 보고 판단하지 말고 실제 Kafka 상태를 확인한 뒤 문구를 띄워야 한다.

- 앱은 Kafka를 직접 볼 수 없다(서버 내부, 외부에 열면 안 됨). `/health`는 API·DB만 확인한다.
- 대신 WS `stalled`가 이 세션의 실제 처리 상태다. kafka 브랜치의 io-api는 1초마다 「`end` 뒤 5초 넘게 이 세션의 결과가 없나」를 보고 `stalled`를 보낸다(`RealtimeHandlerV2.checkStalled` `waitingEnd`). **develop(local)에는 종료 뒤 `stalled`가 없다.** 측정 중 추론·DB 실패 때만 보낸다.

병합 뒤 안:

| 받은 것 | 실제 상태 | 동작·문구 |
|---|---|---|
| `closed` | 정상 저장 | 결과 화면, 문구 없음 |
| `stalled` | 서버가 처리 지연을 확인 | 바로 결과 화면, 「서버 처리가 늦어지고 있어요. 사용자 잘못이 아니에요. 저장이 확인되면 기록에 자동으로 반영돼요」 |
| 상한까지 둘 다 없음 | 서버 소식이 없음(연결 문제 가능) | S4 → 결과 화면, 「서버와 연결이 원활하지 않아 결과를 먼저 보여 드려요. 저장이 확인되면 기록에 자동으로 반영돼요」 |

대기 시간: 서버 `stalled`가 빨라야 5~6초라 앱 상한이 약 7초로 늘어난다.
- **A(추천):** BE에 종료 뒤 `stalled` 기준을 3초로 요청 → 앱은 약 4초에 판단, 상한 5초 유지
- **B:** 앱 상한 7초

그때까지는 지금의 「5초 + 2.1의 안내」를 쓴다. 문구가 「서버 응답이 늦다」라 두 모드 모두에서 사실이다.

### 5.3 데스크톱 측정 중 닫기 창 디자인

지금은 OS 기본 대화상자. 앱 디자인에 맞춘 창(PiP 창처럼)으로 바꿀지, 바꾼다면 lellon0403과 모양을 정한다. 역할은 웹의 확인 창과 같게 유지한다(저장을 기다리지 않음).

## 6. BE에 요청할 것 (D-57 회의)

| # | 요청 | 이유 |
|---|---|---|
| 1 | S4를 DB에서 답하는 안(보고서 안건 1 A안)으로 갈 때: `summary.total_ms`는 DB에 저장된 실제 측정 시간, 저장이 끝난 세션이면 `ended: true`와 `events`에 `session_ended`. `last_sequence`는 -1이어도 된다 | 앱은 `total_ms`로 응답을 쓸지 정하고, `session_ended`가 있어야 기록을 「저장 확인됨」으로 둔다. 없으면 고장은 아니지만 매번 R1 확인까지 늦어진다. **받아들여짐(D-85).** BE `c98074d`(DB 값, 요청대로 `ended`·`session_ended`·저장된 `total_ms`), DevOps `f36d4fb`(kafka 메모리 값, D-57 ⑧). 둘 다 develop 병합 전. 앱은 사건이 적은 응답이면 화면 사건을 둔다([연동 명세](api-ws-spec.md) S4) |
| 2 | 판정기가 `session_started` 없이 관측부터 받으면 서버 기본값(확정 3초·재알림 60초·기준 0.7) 대신 DB `monitor_session.threshold_policy_id`로 그 세션 설정을 읽기 | 지금은 로그만 남기고 기본값으로 판정한다(`V1JudgeRegistry.observation`). 사용자 설정이 서버(W1/W2)로 옮겨진 실제 데이터라 조용히 틀리면 안 된다 |
| 3 | 종료 뒤 `stalled`를 계약에 「`end` 뒤 저장 지연」으로 명시하고, 기준을 5초 → 3초 | 5.2. **반영(D-57 ⑧ `f36d4fb`, develop 병합 전):** `end` 뒤 3초, 측정 중 5초. 계약·BE 명세 설명도 고침 |
| 4 | 서버가 시작할 때 `ended_at` NULL로 남은 세션을 마지막 구간 기준으로 닫기 | 3장 local 「측정 중 서버 재시작」이 R1에 나오게 된다. FE 제안서 요구 8 |
| 5 | Kafka 경로 서버 상태 확인(BE-14~17: liveness에 자기 Kafka 스레드 포함, 다른 서버 상태 빼기, 건너뛴 메시지 알림, 구독 그룹 이름 고정) | [FE 제안서](fe-server-proposal.md) 요구 1 |
| 6 | **kafka 모드 자정 넘김을 어떻게 할지 정하기.** kafka 브랜치는 자정 넘김을 local에서만 켠다(`RealtimeHandlerV2` 생성자 `midnightRollover && pipeline.local()`, 주석 「가이드 11장 #3」). 그래서 kafka 모드에서는 측정이 자정을 넘어 하나로 이어진다. [ADR 0029](../../decisions/0029-midnight-cut-and-server-time.md) 결과의 BE 줄은 「Kafka 모드(`ws`, 계획 0031)도 같은 규칙」이다 | ADR 0029와 코드가 다르다. 이대로면 kafka 모드를 운영에 켤 때 자정 넘김(`POSEGOOD_MIDNIGHT_ROLLOVER=true`)이 꺼진 것과 같다. 앱은 `session_rollover`가 안 와도 동작하지만, ADR 0029의 「측정 하나는 하루 안」이 깨지고 앱 날짜 나누기(ADR 0027)를 지울 수 없다. kafka에서도 넘길지(언제), ADR을 고칠지 D-57 회의에서 정한다. 안과 FE 의견(먼저 「자정에 끝내기」)은 [FE 제안서](fe-server-proposal.md) 요구 2(BE-18) |

## 7. FE 포함 통신 시험에 넣을 것 (보고서 안건 4)

1. **설정이 판정까지 가는지:** 설정에서 확정 시간 3초 → 5초, 재알림 60초 → 30초로 저장(W2) → 측정하며 구부정하게 → 확정 약 5초, 재알림 약 30초 뒤인지. DevOps/BE는 판정기 로그 「v1 세션 시작 (policy=…)」에 `hold 5000`. 다른 브라우저에서 설정을 바꾼 뒤 원래 브라우저로 측정을 시작해 409 없이 되는지.
2. **`end` → `closed` 시간:** 개발자 도구 Network › WS에서 보낸 `end`와 받은 `closed`의 시각 차를 5번 잰다. S4(`GET /v2/sessions/{id}`) 호출이 생기면 안 된다. 대부분 3초 안이면 5초 상한 유지, 넘는 경우가 있으면 5.2를 앞당긴다.
3. **늦은 `alert`:** 확정 경고가 뜨자마자 바르게 앉아, 회복 뒤 경고음·토스트가 다시 나오지 않는지. 종료 버튼 직후에도 나지 않는지.
4. **결과 안내:** 저장 서비스를 잠깐 멈추고 종료 → 5초 뒤 결과 화면 맨 위 안내, 서비스를 되살린 뒤 15초 안에 대기 기록이 확인되는지.
