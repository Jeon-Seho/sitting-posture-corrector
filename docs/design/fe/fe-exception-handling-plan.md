# FE 예외 처리 방안

> 작성자: klaod-tech(FE) · 작성: 2026-11-11
> **이 문서의 역할:** 측정 종료부터 기록이 서버에 저장됐다고 확인될 때까지, 서버가 늦거나 결과를 잃었을 때 앱이 무엇을 보여 주고 이 기기의 기록을 어떻게 다룰지 정한다. 해결할 문제는 0장, 지금 동작은 2장, BE 요청은 6장이다. 계기는 DevOps/BE의 D-57 Kafka 경로 통신 시험 보고서 검수다. 메시지·API 형식은 [연동 명세](api-ws-spec.md), 화면 동작 규칙은 [FE 기능 명세](fe-feature-spec.md), 이미 정한 오류 화면·문구 전체는 [FE 예외 처리 모음](fe-exception-log.md)이다.

## 0. 해결할 문제

남은 문제는 「측정 결과가 이 기기의 대기 기록에만 남고 서버에서는 확인되지 않는」 경우다. 측정 시작 때 연결이 안 열리는 경우는 시작 실패 화면으로 정했고(2.4), S4 404는 오류 화면을 보이고 이 기기에 남기지 않기로 정했다(2.1 4번). 대기 기록은 측정 중 1초마다, 끝날 때 한 번 이 기기에 남기는 결과이고, R1에서 같은 측정이 끝난 기록으로 확인되면 지운다(`serverRecords.ts`). 앱에는 기록을 서버에 올리는 API가 없다(판정은 서버만, [ADR 0021](../../decisions/0021-app-sends-information-server-judges.md)).

### 끝내 저장되지 않는 기록 (3·4장, 5.1)

- **언제:** 서버가 측정을 끝까지 저장하지 못해 R1에 끝난 기록으로 나오지 않을 때(3장 표).
- **지금 앱:** 대기 기록이 ① 기록 목록에 안 보이고 ② 끝없이 「임시 보관 중」으로 남고 ③ 로그아웃과 계정 화면을 막고 ④ **새 측정 시작도 막는다**(「이전 결과를 서버에서 확인하고 있어요. 확인 후 새 측정을 시작해 주세요」, `useSessionPersistence.start`). 그 기록이 끝내 확인되지 않으면 사용자는 다시는 측정할 수 없다. 대기 기록이 손상돼도 「새 측정을 중단합니다」로 막힌다. 사용자가 풀 방법이 없다([FE 예외 처리 모음](fe-exception-log.md) C-2).
- **정할 것:** 4장 제안(목록에 「서버 확인 중」 표시, 기준 시간 뒤 「저장되지 못했어요」, 로그아웃은 묻고 보내기)을 할지, 기준 시간.

## 1. 전제

- **kafka 모드는 아직 개발 중이다.** 코드는 `feat/ws-kafka-pipeline`(D-57) 브랜치에만 있고 develop에는 없다. 보고서 기준 「회의 → 수정 → FE 포함 통신 시험 통과 → develop 병합」 순서이고, 병합 뒤에도 서버 기본값은 local이다.
- **운영 서버는 local 모드다.** io-api 한 곳에서 판정·저장하고, `end` 뒤 `closed`는 1초 안에 온다.
- **웹과 데스크톱 앱은 같게 동작한다.** 한쪽에서만 되는 처리(예: 데스크톱에서 닫기를 붙잡고 저장을 기다린 뒤 닫기)는 만들지 않는다.

```
local 모드 (운영):  앱 → io-api(판정·저장) → 앱
kafka 모드 (D-57):  앱 → io-api → Kafka → 추론 → 판정 → 저장(DB) → io-api → 앱
```

## 2. 지금 앱이 하는 일

### 2.1 「측정 종료」를 누른 뒤

| 순서 | 앱 동작 | 코드 |
|---|---|---|
| 1 | `end`를 보내고 카메라 칸 안에 돌아가는 표시와 「측정 결과를 저장하고 있어요」를 띄운다. 카메라 칸 안 버튼은 눌리지 않고, 나머지 화면은 그대로 둔다 | `LiveSessionPage` `EndingNotice` |
| 2 | `closed`가 오면 창을 닫고 결과 화면 | `LiveSession.handle` |
| 3 | **5초** 안에 `closed`가 없으면 S4로 결과를 한 번 읽는다. `end` 뒤 `stalled`(kafka 3초)가 오거나 연결이 먼저 끊기면 바로 읽는다 | `END_TIMEOUT_MS`, `fetchResult` |
| 4 | S4가 화면에 보이던 것보다 적게 측정했다고 답하면(`summary.total_ms`가 작음) 그 응답은 버리고 마지막 `progress` 결과로 끝낸다. `ended: true` 응답은 사건까지 그대로 쓴다. `last_sequence`로 비교하지 않는 것은 DB로 다시 만든 응답이 -1을 주기 때문이다. 404면 「서버에서 이번 측정을 찾지 못했어요 — 사용자 잘못이 아니에요. 서버 문제로 이번 측정 결과를 확인하지 못했어요. 다시 측정해 주세요」 오류 화면(500 그림)를 보이고 이 기기에는 남기지 않는다(대기 기록도 지움) | `fetchResult`, `ErrorPage` `result`, `forgetResult` |
| 5 | `closed` 없이 넘어왔고(5초 또는 `stalled`) 서버가 종료를 확인해 주지 않았으면(`session_ended` 없음) 결과 화면 맨 위에 안내를 띄운다(아래) | `lateResult` |
| 6 | 기록은 이 기기의 대기 기록으로 남고, 측정 중이 아닐 때 15초마다 R1로 확인한다 | `useSessionPersistence.syncRecords` |

5번 안내:

> **서버 응답이 늦어 결과를 먼저 보여 드려요**
> 사용자 잘못이 아니에요. 측정 기록은 서버에 저장되고 있고, 저장이 확인되면 기록에 자동으로 반영돼요.

5초로 정한 근거: local 모드는 1초 미만, kafka 모드 정상은 1~3초로 본다(서비스 4~5단계, 단계마다 Kafka가 최대 0.5초 모음, **실측 없음** — 7장 시험에서 잰다). 5초를 넘는 건 서비스 재시작·Kafka 소비자 재배치·DB 지연 같은 장애 때뿐이고, 그때는 기다려도 안 올 수 있다.

### 2.2 kafka 모드 대비 (local에서는 해당 상황이 생기지 않음)

| 상황 | 앱 처리 |
|---|---|
| S4가 진행 중 메모리 값(io-api가 받은 마지막 결과, `ended: false`)으로 답함(D-57 ⑧) | 2.1의 4번. 측정 시간이 짧으면 버리고, 사건이 적으면 화면 사건을 둔다 |
| `alert`가 저장 서비스를 거쳐 따로 와서 회복 뒤나 「측정 종료」 뒤에 도착 | 울리지 않는다. 그 사건이 이미 `recovery_confirmed`·`interrupted`·`session_ended`로 닫혔는지 `event_id`로 본다(서버에서 `event_id`는 세션마다 1씩 커지고 `alert`는 그 사건 번호를 쓴다) |
| 종료 뒤 3초에 `stalled`가 옴(D-57 ⑧) | 문구로 보이지 않고 바로 S4를 읽어 결과로 넘어간다. 2.1의 5번 안내로 알린다 |
| `ack`가 판정 결과보다 먼저, `progress`가 약 1초마다 옴 | 앱은 `ack`를 쓰지 않는다. 받으면 버린다(`LiveSession.ts` `case 'ack': return`, 재전송을 없앤 [ADR 0024](../../decisions/0024-session-ends-on-lost-connection.md) 뒤부터). 그래서 `ack`가 먼저 와도 동작이 같다. `decision`·`progress`는 같은 토픽·같은 키라 서로 순서가 지켜지고, 따로 오는 `alert`는 위 줄처럼 막는다 |

### 2.3 측정 중 강제 종료 (웹 탭 닫기, 데스크톱 X·Alt+F4)

| 단계 | 웹 | 데스크톱 앱 |
|---|---|---|
| 닫으려 할 때 | 브라우저 기본 창 「사이트에서 나가시겠습니까?」(`beforeunload`, 문구는 브라우저가 정함) | 앱 본체가 「측정 중이에요. 정말 닫을까요? [닫기] [계속 측정]」(`main.cjs` `will-prevent-unload`). Electron은 `beforeunload`가 막으면 아무것도 묻지 않고 닫기를 무시해서 따로 묻는다 |
| 그래도 닫으면 | 서버가 연결 끊김을 보고 마지막으로 받은 구간까지 세션을 끝내 저장한다. 끊김 신호가 없어도 120초 동안 메시지가 없으면 같은 처리 | 같음 |
| 다음에 열 때 | 1초마다 남긴 대기 기록을 R1과 맞춰 본다 | 같음 |
| 못 막는 것 | 작업 관리자 종료, 전원 꺼짐(서버 저장·대기 기록은 그대로 동작) | 같음 |

데스크톱 확인 창은 지금 OS 기본 대화상자다. 앱은 PiP 창처럼 앱 디자인에 맞춘 창을 띄울 수 있으므로 5.3에서 정한다. 앱 본체를 고친 것이라 설치 파일을 다시 배포해야 반영된다.

### 2.4 측정을 시작할 때 서버 이상

kafka 경로의 io-api는 `hello`를 받으면 `session_started`를 Kafka에 쓰고, 못 쓰면 `ready` 전에 `closed(session_lost)`를 보낸다(`KafkaPipeline.open` → 503 → `RealtimeHandlerV2.refusal`). WS로 Kafka 상태가 따로 오지는 않지만 이 첫 응답이 시작 시점의 확인 역할을 한다.

| 받은 것 | 앱 동작 |
|---|---|
| S1 5xx, `ready` 전 `closed(session_lost)`, S1 뒤 연결 실패(WS가 안 열림·`ready` 전 끊김·`ready` 5초 넘김·토큰 받기 네트워크 실패) | 측정 화면 자리에 오류 화면(500 그림) 「지금은 측정을 시작할 수 없어요 — 서버와 연결하지 못해 측정을 시작하지 못했어요. 인터넷 연결을 확인하고 잠시 뒤 다시 시작해 주세요」, 버튼 「다시 준비하기」. 측정한 것이 없어 기록은 남기지 않는다(`LiveState.serverDown`, `ERROR_PAGES.measure`). 서버에 열린 채 남는 빈 세션은 BE가 닫는다([FE 제안서](fe-server-proposal.md) 요구 8) |

전에는 이 경우 「서버에서 측정이 끝났어요. 확인된 시간까지 저장됐어요」가 떴다. 측정한 것이 없는데 저장됐다고 말하던 것을 고쳤다(2026-11-11).

## 3. 끝내 저장되지 않는 경우

> **2026-11-11 kafka 코드 대조 뒤 결정:** 추론·판정·저장 서비스나 Kafka가 멈추는 경우는 쿠버네티스 재시작으로 복구되고(BE), 기록은 Kafka가 들고 있다가 처리되고 Hadoop에도 남는다. 그보다 큰 장애(데이터 유실)는 FE가 대비하지 않는다. 아래 표와 4장은 local 모드 「측정 중 서버 재시작」 같은 남은 경우에만 해당한다.

| 모드 | 늦지만 결국 저장됨 | 끝내 저장 안 됨(R1에 끝난 기록으로 안 나옴) |
|---|---|---|
| kafka | 대부분. 앱에 `ack`를 보내기 전에 Kafka가 디스크에 보관하므로 서비스가 살아나면 이어서 처리 | 메시지가 처리 불가로 DLQ에 빠짐, Kafka 보관 기간보다 긴 장애 |
| local | 서버 잠깐 지연 | **측정 중 서버 재시작**(메모리 세션이 사라지고 DB 행은 `ended_at` NULL로 남음, [연동 명세](api-ws-spec.md) 4장 S4 「남는 틈」), 종료 순간 DB 장애 |

그때 지금 앱의 불편한 점:

1. **기록 목록에 안 보인다.** 기록·달력은 R1만 보여 주고, 대기 기록은 홈의 「서버 저장 확인을 기다리는 기록 n개 · 이 기기에 임시 보관 중」 띠에 개수로만 나온다.
2. **영원히 기다린다.** 대기 기록에 끝이 없어 이 띠가 사라지지 않는다.
3. **로그아웃이 막힌다.** 대기 기록이 있으면 「결과 저장을 완료한 뒤 나가 주세요」로 로그아웃을 막고 계정 화면도 잠근다(`LocalServiceApp.logout`). 저장이 끝내 안 되면 빠져나갈 길이 없다. 가장 큰 문제다.

## 4. 제안 (FE, 웹·앱 공통)

| # | 할 일 | 효과 |
|---|---|---|
| 1 | 대기 기록을 기록 목록에 「서버 확인 중」 표시와 함께 보여 준다 | 방금 측정이 사라진 것처럼 보이지 않는다 |
| 2 | 일정 시간(안: 하루)이 지나도 확인되지 않으면 「서버에 저장되지 못했어요」로 바꾸고, 사용자가 지울 수 있게 한다 | 끝없는 대기가 끝난다 |
| 3 | 로그아웃을 막지 않고 「이 기기에 확인 대기 기록이 남아 있어요. 다시 로그인하면 이어서 확인해요」를 묻고 보낸다. 대기 기록은 계정별 키라 다시 로그인하면 이어진다 | 빠져나갈 길이 생긴다 |

## 5. 정할 것

### 5.1 끝내 저장되지 않을 때 (4장, 0장)

- 1~3을 모두 할지, 3번(로그아웃 막힘)부터 할지
- 2번의 기준 시간(안: 하루)

### 5.2 「서버 응답이 늦다」를 실제 서버 상태로 판단하기

피드백: 5초 타이머만 보고 판단하지 말고 실제 Kafka 상태를 확인한 뒤 문구를 띄워야 한다.

- 앱은 Kafka를 직접 볼 수 없다(서버 내부, 외부에 열면 안 됨). `/health`는 API·DB만 확인한다.
- 대신 WS `stalled`가 이 세션의 실제 처리 상태다. kafka 브랜치의 io-api는 1초마다 「`end` 뒤 **3초** 넘게 저장 완료가 없나」를 보고 `stalled`를 보낸다(측정 중은 5초, D-57 ⑧ `f36d4fb`, 6장 3번 요청 반영). develop(local)에는 종료 뒤 `stalled`가 없다.

**반영됨(11/12, 우리 브랜치):** 종료 뒤 `stalled`가 오면 5초를 기다리지 않고 바로 S4를 읽어 결과로 넘어간다. 앱 상한은 5초 그대로라 local 모드는 지금처럼 동작한다.

**남은 것 — 문구 나누기(D-57 병합 뒤 정함):** 지금은 두 경우 모두 「서버 응답이 늦어 결과를 먼저 보여 드려요…」 하나다. 문구가 「늦다」라 두 경우 모두 사실이다. 나눈다면:

| 받은 것 | 실제 상태 | 문구 안 |
|---|---|---|
| `stalled` | 서버가 저장 지연을 확인 | 「서버 처리가 늦어지고 있어요. 사용자 잘못이 아니에요. 저장이 확인되면 기록에 자동으로 반영돼요」 |
| 5초까지 둘 다 없음 | 서버 소식이 없음(연결 문제 가능) | 「서버와 연결이 원활하지 않아 결과를 먼저 보여 드려요. 저장이 확인되면 기록에 자동으로 반영돼요」 |

### 5.3 데스크톱 측정 중 닫기 창 디자인

지금은 OS 기본 대화상자. 앱 디자인에 맞춘 창(PiP 창처럼)으로 바꿀지, 바꾼다면 lellon0403과 모양을 정한다. 역할은 웹의 확인 창과 같게 유지한다(저장을 기다리지 않음).

## 6. BE에 요청할 것 (D-57 회의)

## 7. FE 포함 통신 시험에 넣을 것 (보고서 안건 4)

1. **설정이 판정까지 가는지:** 설정에서 확정 시간 3초 → 5초, 재알림 60초 → 30초로 저장(W2) → 측정하며 구부정하게 → 확정 약 5초, 재알림 약 30초 뒤인지. DevOps/BE는 판정기 로그 「v1 세션 시작 (policy=…)」에 `hold 5000`. 다른 브라우저에서 설정을 바꾼 뒤 원래 브라우저로 측정을 시작해 409 없이 되는지.
2. **`end` → `closed` 시간:** 개발자 도구 Network › WS에서 보낸 `end`와 받은 `closed`의 시각 차를 5번 잰다. S4(`GET /sessions/{id}`) 호출이 생기면 안 된다. 3초를 넘으면 서버가 `stalled`를 보내 앱이 바로 결과로 넘어가므로, 3초를 넘는 경우가 얼마나 되는지 본다.
3. **늦은 `alert`:** 확정 경고가 뜨자마자 바르게 앉아, 회복 뒤 경고음·토스트가 다시 나오지 않는지. 종료 버튼 직후에도 나지 않는지.
4. **결과 안내:** 저장 서비스를 잠깐 멈추고 종료 → 약 3초 뒤(`stalled`) 결과 화면 맨 위 안내, 서비스를 되살린 뒤 15초 안에 대기 기록이 확인되는지.
