# FE 제안서: 서버 판정 이전과 연동

> 작성: 2026-10-11 · 최신화: 2026-10-13(BE 답변 반영) · FE · 대상: DevOps/BE(홍규), DB(유진), ML(지성)
> 확인 기준: `DevOps` 브랜치 `f27f778`(10/12에도 변경 없음), `feature/repo-backend-db-v2` `0fcde59`(미병합), [실시간 계약 v1](../../contracts/realtime/README.md), DevOps/BE 회신(10/11), 아키텍처 v5.1(10/12), BE 답변(10/13)
> FE 검증(10/12): 프론트 303개·브라우저 75개, 이 저장소의 Java 서버 시험(`check-backend`)·Python 시험 통과
> 관련: [ADR 0021](../decisions/0021-app-sends-information-server-judges.md), [계획 0023](../plans/active/0023-frontend-server-only.md)·[0024](../plans/active/0024-posture-registration-tab.md), [FE 작업 명령과 검사](fe-commands-and-checks.md), [API 명세 초안](api-ws-spec.md)

이 문서는 FE가 팀에 보내는 제안과 합의를 한곳에 모은 것이다. 판정 규칙의 계산 방법은 서버가 맡으므로 여기에 적지 않는다(6장).
FE는 **앱이 보내는 것(2장)**과 **앱이 받는 것(3장)**의 이름과 기능만 정의한다.
정해진 것은 본문에 반영하고 질문 목록에서 뺐다. 정해진 과정(BE 회신 확인표, 회의 결정)은 git 이력에 있다.

## 1. 전제와 현재 구조

1. **판정과 라벨링은 서버가 한다.** 점수·상태·유형·판정 가능 여부·고개 돌림·복귀 대기와 학습용 정답 라벨은 서버(추론·판정·ML)가 만든다.
   앱은 판정하지 않고 라벨도 붙이지 않는다. 서버 없이 쓰는 로컬 모드도 없앤다(ADR 0021).
   예외: 사용자 위치를 판별할 수 없는 순간(어깨선이 안 보이는 등)은 앱이 "판정 불가"로 표시해 보낸다(2.2).
2. **앱은 입출구 서버 하나와만 통신한다**(아키텍처 v5, 10/11). 입출구 서버(`auth`·`api`·`ws`)는 BE가 만든다. FE는 앱 쪽 연결과 API 명세를 함께 쓴다.
3. **좌표 수집 동의는 가입의 필수 조건이다.** 로컬 모드가 없어 동의 없이는 측정할 수 없다. 실제 서비스에서는 학습용 데이터를 받지 않는다([동의 제안서](consent-proposal.md)).
4. **통계는 전부 백엔드가 계산한다.** 측정 결과·기록·대시보드의 숫자(유효 측정 시간, 바른 자세 비율, 이탈 수, 간격, 회복 시간 등)는 서버가 계산해 보내고, 앱은 받아서 표시만 한다.
   - **당일은 세션 단위로 보인다.** 같은 날 다시 측정해도 앞서 한 측정과 합치지 않고, 그 세션의 결과만 보인다.
   - **날짜별 합산은 그날 24시(KST)가 지나야 반영된다.** 일별 통계(`daily_stat`)는 지난 날짜만 보인다. 아키텍처 v5.1의 집계 잡 J3은 매일 03:00에 돌아, 00:00~03:00에는 전날 합산이 아직 없다(N20).
   - **5분 미만 세션은 저장하지 않는다(10/12 회의 결정).** 측정 시간(시작~종료)이 5분이 안 되면 종료 화면에 결과는 보여 주지만 DB에 남기지 않는다. 당일 기록 목록과 날짜별 합산에도 들어가지 않는다(N22).

FE가 정한 것(앱 쪽 동작):

| 항목 | 결정 |
|---|---|
| 민감도 | 화면 3단계(느긋하게 0.80 · 보통 0.70 · 꼼꼼하게 0.60)와 세밀 조정(0.5~0.95). 기본은 0.7이고 LSTM으로 바뀌어도 그대로 쓴다. DB에는 threshold 값 하나로 저장한다. 단계 칸은 필요 없다 |
| 소리 | 저장하지 않는다. 측정마다 꺼진 채 시작하고 측정 화면에서 켠다(브라우저는 사용자 동작 없이 소리를 켤 수 없다). 「자세 알림」 켜기·끄기만 서버에 저장한다. V2.1에는 저장 칸이 없다(N16) |
| 영상 크기 | 팀 카메라 전제로 640×480을 요청한다 |
| 네트워크 끊김 | ~~"연결 끊김"을 화면을 막지 않게 띄우고, 좌표는 쌓아 두었다가 재연결 후 다시 보낸다~~ → 2026-10-13 [ADR 0022](../decisions/0022-session-ends-on-lost-connection.md): 세션을 끝내고 화면을 막는 팝업을 띄운다. 재연결·재전송하지 않는다 |

```
앱 ──HTTP /api──▶ 입출구 서버 (auth·api·ws, BE) ──▶ MySQL(계정·설정·세션 행·기록)
앱 ──WebSocket /ws──▶ ws ──▶ posture.features.v1 ─▶ 추론(GPU PC) ─▶ 판정(api-server)
   ▲                   │ ◀── posture.inference.v1 (관측: 화면 실시간 상태)
   └──── push ─────────┘ ◀── posture.episodes.v1 (decision·progress → alert)
```

`ws`가 하는 일(BE): 로그인 세션 확인, 묶음 검사, 순번 중복 제거, Kafka 기록 뒤 `ack`, 세션 시작 때 저장된 기준값 첨부,
재연결 때 놓친 `decision` 먼저·최신 `progress` 마지막, 첫 `hello`에만 `session_started` 발행, `end`에 최종 결과 뒤 `closed(ended)`.
로그인 세션이 측정 중에 만료돼도 그 측정은 끝까지 이어 가고, 다음 연결 때 다시 확인한다.

## 2. 앱이 보내는 것

### 2.1 좌표 프레임 (본문 `posture.frames.v1`, 토픽 `posture.features.v1`)

**0.5초에 1건. 그 안에 찍힌 프레임을 평균 내지 않고 그대로 담는다.** 키는 `session_id`.
본문 `schema_version: "3.0"`, `feature_version: "keypoints-9-v1"`. 계약 스키마(`posture.frames.v1`)는 BE가 초안을 만들어 FE와 맞춘다.
서버 쪽 좌표 입력(추론의 판정 가능 검사·특징값·점수, 합성 시험 데이터 통과)은 10/15 서버 확인이 목표다(D-34).

```json
{
  "sequence": 42,
  "start_ms": 21000,
  "end_ms": 21500,
  "phase": "running",
  "width": 640,
  "height": 480,
  "frames": [
    { "t_ms": 21012, "p": [[0.51234, 0.40211, 0.99], [0.52011, 0.38120, 0.98], "... 9개"] },
    { "t_ms": 21075, "p": null },
    { "t_ms": 21138, "p": [[0.50112, 0.41020, 0.31], "... 9개"], "flag": "position_unknown" }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `sequence` | 세션 안 순번. 0부터 1씩 증가. 중복 제거·재전송에 쓴다 |
| `start_ms`, `end_ms` | 구간 `[start, end)`. 세션 시작 기준 ms, 보통 500ms 간격 |
| `phase` | `running` / `calibration`(자세 등록) / `rest`(일시정지) / `away`(자리 비움: 카메라 끊김 포함) |
| `width`, `height` | 영상 크기(px). 팀 카메라 전제로 640×480을 요청한다 |
| `frames[].t_ms` | 프레임이 찍힌 시각. 세션 시작 기준 ms, 구간 안에서 증가 |
| `frames[].p` | 관절 9개의 `[x, y, visibility]`(아래 순서). 사람이 안 잡힌 프레임은 `null`. 0~30개 |
| `frames[].flag` | 선택. 판정 불가 표시. 지금 값은 `"position_unknown"` 하나(2.2). 있으면 서버는 그 프레임을 판정 불가(`invalid_reason: unmeasurable`)로 보고 시간·점수에서 빼며 `p`는 쓰지 않는다. 모르는 값도 판정 불가로 처리한다 |

| 순서 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| 관절 | 코 | 왼눈 | 오른눈 | 왼귀 | 오른귀 | 입 왼쪽 | 입 오른쪽 | 왼어깨 | 오른어깨 |
| MediaPipe 번호 | 0 | 2 | 5 | 7 | 8 | 9 | 10 | 11 | 12 |

- **좌표:** MediaPipe 원본. x, y는 영상 크기에 대한 0~1 비율(소수 5자리), visibility는 소수 2자리. y는 아래로 커진다.
- **좌우:** 영상은 반전하지 않는다. 관절 좌우는 사용자 몸 기준이라 사용자 왼어깨가 화면 오른쪽(큰 x)에 있다.
- **가려진 관절도 좌표는 온다.** MediaPipe가 위치를 추정해서 준다. 쓸지 말지는 서버가 정한다.
- **프레임 수는 일정하지 않다.** 보통 0.5초에 약 8개, 느린 PC는 3~5개. 시간은 개수가 아니라 `t_ms`로 센다.
- **시각은 앱 시계 기준이다.** 서버 수신 시각이 아니라 `t_ms`·`start_ms`·`end_ms`로 계산한다.
- **세션 시작 시각은 WebSocket 연결 기준이다.** `monitor_session.started_at`은 측정 WebSocket이 연결된 시각(`hello`를 받은 때)이고, 앱은 그 연결 시점을 `t_ms` 0으로 둔다. 차이는 네트워크 지연 정도다. DB 명세서에도 이 뜻을 적는다.
- **왜 평균을 내지 않나:** 0.5초 안에 고개를 돌린 장·손에 가려진 장이 섞이면 평균이 가짜 치우침을 만든다. 어느 장을 뺄지도 판단이라 서버 몫이다.

### 2.2 일시정지·카메라 끊김·판정 불가·종료

일시정지·카메라 끊김·종료는 판단이 아니라 사실이라 앱이 알린다. 메시지가 안 오는 것만으로는 네트워크 끊김과 구별할 수 없다.

| 상황 | 앱이 보내는 것 | DB 제외 사유 |
|---|---|---|
| 사용자가 일시정지 | `phase: "rest"`, `frames: []` | `PAUSE` |
| 카메라 입력이 끊김(자리 비움으로 묶음) | `phase: "away"`, `frames: []` | `ABSENCE` |
| 측정이 안 됨(귀·어깨가 안 보임, 사용자 자체가 안 보임 등 측정이 안 되는 모든 경우) | `phase: "running"` 그대로, 해당 프레임에 `flag: "position_unknown"`(2.1) | `UNMEASURABLE` |
| 측정 종료 | WebSocket `end`. 연결이 이미 끊겼으면 `api`로 종료 요청(서버 안에서 `ws`가 `session_ended`를 낸다. 이미 끝난 세션이면 200) | — |

다시 시작하면 `running`으로 돌아간다. 카메라 끊김 뒤에는 사용자가 직접 재개한다.
`away`는 카메라 끊김을 포함해 자리 비움(`ABSENCE`) 하나로 묶는다. 앱은 `MISSING`(누락)을 보내지 않는다.
판정 불가는 범위를 넓게 잡아 모두 `UNMEASURABLE` 하나로 저장한다. 판정을 세분화할 때 `exclusion_reason`의 CHECK 선택지를 늘린다.
판정 불가 시간을 측정 시간·점수에서 빼는 것과 3초 연속 시 멈춤 같은 시간 규칙은 서버가 정한다. 앱은 서버가 알려 주는 상태를 표시만 한다.
서버는 프레임 간격 1000ms로 끊김을 보고, 앱은 화면 감시를 1500ms로 한다.
네트워크가 끊기면 앱은 "연결 끊김"을 화면을 막지 않게 띄우고, 좌표를 쌓아 두었다가 다시 연결되면 같은 순번으로 다시 보낸다.
(2026-10-13 [ADR 0022](../decisions/0022-session-ends-on-lost-connection.md)로 변경: 끊기면 그 세션을 끝내고 다시 연결하지 않는다.)

DB 규칙(V2.1)에 맞춰 앱이 지킬 것:

- 제외 사유는 하나만 붙는다(우선순위 일시정지 → 누락 → 자리 비움 → 판정 불가). 앱은 `rest`와 `away`를 겹쳐 보내지 않는다. 일시정지 중 카메라가 끊겨도 `rest`만 보낸다.
- 제외 구간의 시작·끝은 서버가 0.5초 경계에 맞춘다. 앱은 `rest`·`away`로 바뀐 시각을 `t_ms` 그대로 보낸다.
- 짧은 끊김은 같은 사건으로 이어질 수 있다(`EVENT_BREAK_SEC`, N15). 앱은 끊김마다 사건을 나눠 보이지 않는다.
- 세션 종료 때 열린 제외 구간은 서버가 종료 시각으로 닫는다. 앱은 종료 전에 `excluded_ended`를 기다리지 않는다.

종료 뒤: 앱은 `end`를 보낸 뒤 최종 `decision`과 `closed(ended)`를 받을 때까지 연결을 유지한다.
서버는 10초 안에 최종 결과가 없으면 `closed`만 보낸다. 그때나 연결이 끊겨 최종 `decision`을 놓쳤을 때, `api`로 종료한 뒤에는 앱이 기록 조회(`GET /api/records/{id}`)로 종료 화면을 그린다.

### 2.3 자세 등록 (측정 시작과 분리)

자세 등록은 "이 사람의 바른 자세"를 한 번 정해 두는 일이다. 서버는 측정 중 좌표를 이 기준과 비교한다.
앱은 「자세 등록」 탭에서만 등록한다. 얼굴·어깨가 보이면 3·2·1 뒤 3초 동안 프레임을 `phase: "calibration"`으로 보낸다(이미 등록했으면 「다시 등록」을 누를 때만).
측정을 시작할 때는 등록하지 않고 저장된 기준을 쓴다(앱 화면은 [계획 0024](../plans/active/0024-posture-registration-tab.md)에서 이미 나눴다).
기준값은 서버가 등록 프레임으로 계산한다. 평균은 등록에서만 낸다.

등록 흐름(BE 답변 10/13):

| # | 단계 | 방식 |
|---|---|---|
| ① | 등록만 하는 연결 | 같은 `/ws`에 `hello`의 `purpose: "calibration"`으로 연결한다. 측정 세션 행과 `session_started`를 만들지 않고, 판정기는 이 연결을 무시해 사건·기록이 생기지 않는다. 앱은 `phase: "calibration"` 프레임만 보낸다. Kafka 키는 등록마다 새 UUID |
| ② | 등록 결과 | 추론이 등록 프레임으로 기준값(특징값 5개 + `quality`)과 평균 좌표 18개를 함께 계산한다(ML 확인). `ws`가 저장한 뒤 앱에 `calibration_result`(`status: ok/failed`, 실패 사유, 새 `baseline_id`, 등록 시각)를 보내고 `closed(ended)`로 닫는다 |
| ③ | 저장된 기준 조회 | `GET /api/baseline`. 있으면 `baseline_id`·등록 시각, 없으면 404 |
| ④ | 측정 시작 | 측정 `hello` 때 `ws`가 저장된 기준을 붙인다. 기준이 없으면 `closed(no_baseline)`로 거절한다 |

- 실패: 3000ms 안에 판정 가능 프레임 15장 미만이거나 중간에 끊기면 `failed`.
- 기준값을 저장할 DB 칸(N8)이 정해지기 전에는 서버가 ①~④를 먼저 만들고 저장만 비워 둔다.
- 지금 앱은 등록한 자세를 앱이 켜져 있는 동안만 기억한다. 위가 생기면 서버 등록·조회를 붙인다(F2).

## 3. 앱이 받는 것 (이름과 기능)

화면은 서버 결과로만 바뀐다. 메시지 이름은 [실시간 계약 v1](../../contracts/realtime/README.md)을 따르고, 새로 필요한 것은 **추가**로 표시했다.

### 3.1 WebSocket (서버 → 앱)

| 이름 | 언제 오나 | 앱이 하는 일 |
|---|---|---|
| `ack` | `last_sequence`까지 Kafka에 넣었을 때 | 재전송 대기열에서 지운다 |
| `observation` | 0.5초 구간마다 | 실시간 상태 알약과 안내 문구를 바꾼다(3.2). 재연결 때 다시 오지 않는다 |
| `progress` | 약 1초마다 | 측정 시간·바른 자세 비율 등 숫자를 바꾼다. 측정 멈춤 상태도 여기서 안다. 재연결 때는 최신 것 하나만 |
| `decision` | 사건이 확정됐을 때 | 사건 기록과 숫자를 바꾼다(3.3). 재연결 때 놓친 것을 다시 받는다 |
| `alert` | 흐트러진 자세 확정·재알림일 때 | 토스트와 소리를 띄운다. 앱은 따로 거르지 않는다. 표시·억제는 판정 결과 저장이 `alert_enabled`·시간당 상한으로 판단하고(`posture.alerts.v1`) `ws`가 전달한다. 오래된 사건(제안 10초)에는 오지 않는다 |
| `calibration_result` (**추가**) | 등록 연결에서 기준을 계산·저장했을 때(2.3 ②) | 등록 완료/실패를 보이고 기준 조회를 다시 한다 |
| `stalled` | 5초 동안 판정 진행이 없을 때 | "분석이 잠시 멈췄어요"를 보인다 |
| `closed` | 채널이 끝날 때 | 이유별로 처리: `ended`(정상 종료), `unauthorized`(다시 로그인), `not_owner`, `session_lost`, `server_shutdown`, `no_baseline`(등록한 자세 없음, **추가**) |

### 3.2 `observation`에서 쓰는 값

| 값 | 기능 |
|---|---|
| `valid` | 이 구간을 판정했는지 |
| `collapse_probability` | 판정 점수. 화면 점수는 `100 × (1 − 점수)` |
| `invalid_reason` (**추가**) | `valid=false`일 때만. 화면 안내 문구를 고른다(아래) |
| `valid_ms` (**추가**) | 구간 안 판정 가능 시간. 앱은 표시에 쓰지 않는다(판정기 시간 누적용) |

| `invalid_reason` | 뜻 | 앱 안내 |
|---|---|---|
| `unmeasurable` | 가림·화면 밖·사람 없음 | "자세를 확인할 수 없어요" |
| `head_turn` | 고개를 돌림 | "고개를 돌린 동안은 판정하지 않아요" |
| `settling` | 돌아온 직후 자세를 다시 잡는 중 | "자세를 다시 잡는 중이에요" |

지금은 판정 불가를 넓게 잡아 `unmeasurable` 하나만 쓴다(앱의 `flag`가 붙은 프레임도 이것). `head_turn`·`settling`은 판정을 세분화할 때 쓰고, 언제 나오는지는 서버가 정한다. 앱은 이 값을 받아 문구만 고른다.

### 3.3 `decision`의 사건 종류

| 종류 | 앱이 하는 일 |
|---|---|
| `collapse_confirmed` | 사건 시작 기록 |
| `reminder` | 재알림 기록 |
| `recovery_confirmed` | 사건을 복귀로 닫는다 |
| `interrupted` | 사건을 끊김으로 닫는다. 사유가 판정 불가면 "측정 멈춤 – 어깨가 보이게 앉아 주세요"를 띄운다 |
| `session_ended` | 결과 화면으로 간다 |
| `excluded_started`·`excluded_ended` (**추가**) | 제외 구간 경계(DB 저장용). 앱은 받기만 하고 표시하지 않는다 |

## 5. 서버 부담 (동시 50명, 하루 8시간 추정)

| 항목 | 특징값 전송(예전) | 좌표 전송(지금) |
|---|---|---|
| 메시지 | 0.5초에 1건, 수백 바이트 | 0.5초에 1건, 약 2KB |
| Kafka 유입량 | 수십 KB/s | 약 200KB/s |
| 서버 계산 | 0.5초당 점수 1번 | 초당 약 800프레임(계산은 가볍다) |

메시지 수가 같아서 처리량은 거의 같다(10/01 측정 기준 약 40~50명, DevOps 재측정 예정).
실제 부담은 구현·운영이다: 좌표 처리 단계, 세션별 상태, 3초 규칙과 자동 재개, HDFS 적재·동의 철회 삭제, 서버 장애 시 화면 판정 정지.

## 6. 넘겨준 판정 규칙과 시험 데이터

판정 규칙(판정 가능 검사, 특징값, 고개 돌림, 점수, 복귀 대기, 보정, 판정 불가 시간 처리)은 10/11에 BE에 넘겼고 서버가 구현한다(D-34·D-35·D-23).
이 문서에서는 계산 방법을 뺐다. 원문은 이 파일의 git 이력 `d69b22c`(BE 회신 S2·S3 반영본)에 있다.

- [합성 시험 데이터](../../contracts/examples/frames/reference-rule-cases.json): 좌표 → 기대 결과(프레임 17·시간 순서 4·보정 1). 서버 구현이 같은 결과를 내는지 확인용이다.

- 규칙을 바꾸자는 제안은 BE·ML이 정하고, FE는 시험 데이터를 맞춰 다시 만든다. 두 귀가 모두 있어야 판정한다는 규칙(`one_ear_missing`)과 float64 계산도 ML 결정에 따라 바뀔 수 있다.
