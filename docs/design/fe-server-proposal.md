## 1. 남은 질문과 요청

**남은 질문은 DevOps의 HTTPS(아래) 하나다(2026-10-19).** BE가 `/v2/realtime`(좌표 스트림, 계약 v2)을 구현했다(10/17, BE 브랜치 `a0d99a3`. 우리 브랜치에는 아직 받지 않음).
`/v1/realtime`과 BE ADR 0022의 「실시간 v1 유지, 좌표 스트림 제외」는 서버를 먼저 돌려 보려고 섞어 둔 임시 상태였고, 앱이 v2로 넘어간 뒤 BE가 지운다.

BE 공유(10/16, 「실시간 `/v1` → `/v2` 전환」)에 대한 FE 답: 전환 기간(`/v1`·`/v2` 함께)은 앱의 v2 전환(F1~F3)이 끝날 때까지로 동의. 개발 서버 `/api` 중계에 `ws: true`를 넣었다(`frontend/vite.config.ts`).

BE 피드백 반영·정정(10/17, 기준 `faed2bd`)에 대한 FE 확인(10/19):

- BE가 `/v2/realtime`을 모두 구현했다(`RealtimeHandlerV2`, BE 명세 `docs/design/api-spec.md` 11장). F1~F4는 이제 막힌 것이 없다. F3(`ws: true`)는 `48f5e9b`에서 했다.
- 「새로 확인」(HTTP 측정 경로가 `/api/v1/sessions`): 맞다. BE에는 `/v1/sessions`가 없어 지금 서버와 맞지 않는다. **HTTP 경로를 v2로 고치지 않고 측정을 WebSocket v2로 옮기면서 지운다**(S2·R2도 전환 뒤 지울 예정이라). 7.1 참고.
- 로그인 만료: BE 의도는 **무엇을 하든 30분이 지나면 로그인을 버린다**(WS 메시지는 만료를 늘리지 않음). 측정은 연결 때 인증했으므로 끝까지 가고, 30분 넘게 측정하면 끝난 뒤 HTTP가 401일 수 있다. 앱은 기록이 저장됐음을 알리고 로그인 화면으로 보낸다. 연동 명세 0장의 「WS가 열려 있는 동안 갱신」은 이에 맞춰 고쳤다.
- 최대 측정 시간: 아직 정하지 않았다(사용자가 몇 시간 측정할지 모름, 지금 기본 5,000초). 앱은 값을 두지 않고 `closed(limit_reached)`만 처리하므로 값이 정해져도 바꿀 것이 없다.

DevOps에 물을 것(10/19, 방식은 [배포 구상](fe-domain-idea.md)으로 정함: 도메인 + Cloudflare 이름 있는 터널): **공개 배포는 HTTPS로 한다.** 브라우저·Electron 모두 `https://`나 `localhost`에서만 카메라를 켜고, 로그인 쿠키(Secure)·`wss://`도 HTTPS가 전제다. 공개 도메인을 쓰는지, 서버가 외부에서 접속되는지, 인증서(Let's Encrypt 등)를 nginx에 붙일 수 있는지 확인한다. 자체 서명 인증서는 사용자마다 경고를 넘겨야 해서 공개용으로 쓰지 않는다.

BE가 진행 중인 것(합의대로, 확인만):

아키텍처 v5.2 전환 공지(DB·BE, 10/15)의 ④ 「오늘 통계를 화면에 바로 보여줄지」는 2장 4의 10/14 결정이 답이다: 보여주지 않는다(통계는 어제까지, 목록에는 오늘 세션, 앱이 따로 계산하지 않음). ①(`PROCESSING` 뒤 철회 거부)은 A8 409 `WITHDRAWAL_NOT_CANCELLABLE`로 이미 맞고, ②·③·⑤는 앱 동작이 달라지지 않는다.

서버·모델 내부의 정할 것(0.5초 구간 점수 합치기, 자세 유형을 낼지, 짧은 끊김을 같은 사건으로 이어 볼 시간 `EVENT_BREAK_SEC`, 팀 저장소 반영 현황)은 BE·ML·DevOps가 정한다. 앱은 서버가 보낸 결과를 그대로 보이므로 어느 쪽이든 영향이 없다.
일별 집계는 **매일 00:00**에 돈다(10/14 확정, 아키텍처 v5.2의 J2).

## 2. 전제와 현재 구조

1. **판정은 서버가 한다.** 점수·상태·유형·판정 가능 여부·고개 돌림·복귀 대기는 서버(추론·판정)가 만든다.
   측정 앱은 판정하지 않고 판정 결과를 라벨로 붙이지 않는다. 서버 없이 쓰는 로컬 모드도 없앤다(ADR 0021).
   학습용 정답 라벨은 **학습용 수집 화면**(다른 담당)에서 참여자에게 준 과제와 참여자의 자기 보고로 정해진다(ML 답 10/14). 필요한 라벨 열과 형식은 ML이 수집 화면 담당에게 요청한다.
   예외: 사용자 위치를 판별할 수 없는 순간(어깨선이 안 보이는 등)은 앱이 "판정 불가"로 표시해 보낸다(3.2).
2. **앱은 입출구 서버 하나와만 통신한다**(아키텍처 v5, 10/11). 입출구 서버(`auth`·`api`·`ws`)는 BE가 만든다. FE는 앱 쪽 연결과 API 명세를 함께 쓴다.
3. **좌표 수집 동의는 가입의 필수 조건이다.** 로컬 모드가 없어 동의 없이는 측정할 수 없다. 실제 서비스에서는 학습용 데이터를 받지 않는다([동의 제안서](consent-proposal.md)).
4. **통계는 전부 백엔드가 계산한다.** 측정 결과·기록·대시보드의 숫자(유효 측정 시간, 바른 자세 비율, 이탈 수, 간격, 회복 시간 등)는 서버가 계산해 보내고, 앱은 받아서 표시만 한다.
   - **오늘 측정은 방금 끝난 세션의 결과로만 보인다(10/13 결정).** 예: 12시에 3시간, 6시에 2시간을 측정했으면 6시 측정이 끝났을 때 결과 화면에는 그 2시간만 반영한다. 앞서 한 측정과 합치지 않는다.
   - **기록 화면: 목록에는 오늘 끝난 세션도 하나씩 보이고, 합산·그래프 같은 통계는 어제까지만 그린다(10/14 결정, DevOps 검토 C5).** 그날 합산은 24시(KST)가 지난 뒤 일별 집계가 만든 값을 쓴다(일별 집계는 매일 00:00, 10/14 확정).
   - **5분 미만 세션(10/14 정정).** 5분(`STAT_MIN_SESSION_SEC`) 미만 세션도 저장하고 기록 목록·일별 통계에 넣는다. "붕괴까지 걸린 시간" 최소·최대에서만 뺀다(DB V2.3, 10/14 정정). 처음에 "저장하지 않는다"로 적은 것은 회의 내용을 잘못 이해한 것이다.

| 탈퇴 | 되돌릴 수 없다(BE 10/15, A8 없어짐). 탈퇴 확인창에 「되돌릴 수 없고 30일 뒤 완전히 삭제, 그 전에는 같은 이메일로 다시 가입할 수 없음」을 보이고 비밀번호를 받는다. 탈퇴한 계정으로 로그인하면(403 `ACCOUNT_CLOSED`) 「자세한 사항을 아래 번호 또는 이메일로 남겨주세요. 010 - 1234 - 5678 / klaod@naver.com」를 보인다(10/16). 따로 「30일 이내인가」를 묻는 API는 두지 않는다([연동 명세](api-ws-spec.md) 0.7) |

```
앱 ──HTTP /api/v2──▶ 입출구 서버 (BE `backend/api`) ──▶ MySQL(계정·설정·세션 행·기록)
앱 ──WebSocket /api/v2/realtime──▶ 같은 서버: 좌표 → 특징 계산(FrameFeatures) → 추론 POST /v2/infer → 판정
   ▲                                   │
   └──── push: observation·decision·alert·ack·progress·stalled·closed ─┘
```

지금(BE 10/17, `FrameFeatures` 안): 입출구 서버가 연결마다 로그인과 세션 주인을 확인하고(`hello` → `ready`), 좌표 구간으로 특징을 계산해 추론·판정하고, 결과를 같은 연결로 보낸다(BE 명세 11장).
나중에 Kafka 경로(`posture.features.v1` → 추론 → `posture.inference.v1` → 판정 → `posture.episodes.v1`·`posture.alerts.v1`, BE 계획 0031)로 옮겨도 앱 쪽 계약(WebSocket v2)은 바뀌지 않는다.
재연결은 없다(ADR 0024). 연결이 끊기면 서버가 마지막으로 받은 구간 끝에서 세션을 끝낸다(BE 명세 11.3).
로그인은 측정 연결을 열 때 확인하므로 측정은 끝까지 간다. 로그인은 30분이 지나면 버려지므로(BE 의도, 10/19) 긴 측정 뒤 HTTP가 401이면 로그인 화면으로 보낸다.

## 3. 앱이 보내는 것

### 3.1 좌표 구간 (`posture.frames.v1`)

**0.5초에 구간 1개. 그 안에 찍힌 프레임을 평균 내지 않고 그대로 담는다.** 필드와 예시는 [좌표 구간 계약](../../contracts/realtime/frames/posture-frames.v1.schema.json)과 [연동 명세](api-ws-spec.md) 5.2에 있다.
서버 쪽 좌표 입력(추론의 판정 가능 검사·특징값·점수, 합성 시험 데이터 통과)은 10/15 서버 확인이 목표다(D-34).

- **좌표:** MediaPipe 원본. x, y는 영상 크기에 대한 0~1 비율(소수 5자리), visibility는 소수 2자리. y는 아래로 커진다.
- **좌우:** 영상은 반전하지 않는다. 관절 좌우는 사용자 몸 기준이라 사용자 왼어깨가 화면 오른쪽(큰 x)에 있다.
- **가려진 관절도 좌표는 온다.** MediaPipe가 위치를 추정해서 준다. 쓸지 말지는 서버가 정한다.
- **프레임 수는 일정하지 않다.** 보통 0.5초에 약 8개, 느린 PC는 3~5개. 시간은 개수가 아니라 `t_ms`로 센다.
- **시각은 앱 시계 기준이다.** 서버 수신 시각이 아니라 `t_ms`·`start_ms`·`end_ms`로 계산한다.
- **세션 시작 시각은 서버가 `PUT /v2/sessions/{id}`를 받은 시각이다(BE 명세, 10/13 결정).** `monitor_session.started_at`이고 앱의 `t_ms` 0이다.
- **판정 불가 프레임에는 `valid: false`를 붙인다(3.2).**
- **왜 평균을 내지 않나:** 0.5초 안에 고개를 돌린 장·손에 가려진 장이 섞이면 평균이 가짜 치우침을 만든다. 어느 장을 뺄지도 판단이라 서버 몫이다.

### 3.2 일시정지·카메라 끊김·판정 불가·종료

일시정지·카메라 끊김·종료는 판단이 아니라 사실이라 앱이 알린다. 메시지가 안 오는 것만으로는 네트워크 끊김과 구별할 수 없다.

| 상황 | 앱이 보내는 것 | DB 제외 사유 |
|---|---|---|
| 사용자가 일시정지 | `phase: "rest"`, `frames: []` | `PAUSE` |
| 카메라 영상이 멈춤(연결은 그대로, 예: 측정 중 다른 USB 카메라를 꽂음. 앱은 1.5초 넘게 프레임이 없으면 멈춤) | `phase: "away"`, `frames: []` | `ABSENCE` |
| **쓰던 카메라가 빠짐**(USB 연결 끊김, 10/16) | 측정을 끝낸다: WebSocket `end`(아래 「측정 종료」와 같음). 다른 카메라로 넘어가지 않는다 | — |
| 측정이 안 됨(귀·어깨가 안 보임, 사용자 자체가 안 보임 등 측정이 안 되는 모든 경우) | `phase: "running"` 그대로, 해당 프레임에 `valid: false`(3.1) | `UNMEASURABLE` |
| 측정 종료 | WebSocket `end`. 연결이 이미 끊겼으면 `api`로 종료 요청(서버 안에서 `ws`가 `session_ended`를 낸다. 이미 끝난 세션이면 200) | — |

원인별 처리를 한곳에 모으면 세 가지다(10/16 정리). 원인은 여럿이어도 처리는 이 셋뿐이다.

| 처리 | 원인 | 서버·DB |
|---|---|---|
| ① 계속 측정, 그 구간만 판정 불가(저절로 이어 감) | 어깨가 안 보임, 얼굴·양쪽 어깨를 못 찾음, 추적 품질이 낮음 | 프레임 `valid:false` → `UNMEASURABLE` |
| ② 일시정지, 「측정 재개」로 이어 감 | 사용자 「잠시 쉬기」 | `rest` → `PAUSE` |
| | 영상이 1.5초 넘게 안 들어옴(연결은 그대로, 예: 다른 USB를 꽂음, `useSessionScreen`) | `away` → `ABSENCE` |
| | 앱 처리가 1.5초 넘게 멈춤(PC가 바쁘거나 절전에서 깨어남, `useSession`) | `away` → `ABSENCE` |
| | 위 두 경우(앱이 스스로 멈춘 일시정지)의 안내: 「인식 중입니다. 3초 후에 측정 재개 버튼을 눌러주세요.」 「측정 재개」는 사람을 다시 알아볼 때까지 잠겨 있어 저절로 이어지는 줄 오해하기 쉬웠다(10/16) | — |
| ③ 측정 종료, 그때까지 기록 저장 | 사용자 「측정 종료」 | `end` |
| | 쓰던 카메라가 빠짐(USB 연결 끊김, 10/16) | `end` |
| | 작은 카메라 창(PiP)의 X(측정 중, 10/20) | `end` |
| | 일시정지가 10분 이어짐(휴식·앱이 스스로 멈춘 것 모두, 10/20) | 서버가 종료(서버 시계 기준, BE). 앱은 받은 종료를 처리 |
| | 측정 중 앱을 닫거나 새로 고침 → 다음 로그인 때 저장(10/16) | WS가 끊겨 서버가 끝냄 |
| | 서버 연결 끊김 → 화면을 막는 팝업(ADR 0024) | 앱이 끝냄, 다시 연결하지 않음 |
| | 서버가 닫음 `closed(...)`: 측정 길이 한도 `limit_reached`, 로그아웃·비밀번호 변경·탈퇴 `unauthorized`, 세션 유실, 서버 종료 | 서버 메시지로 종료 화면 |

다시 시작하면 `running`으로 돌아간다. 영상이 멈췄던 뒤에는 사용자가 직접 재개한다. 쓰던 카메라가 빠지면 재개하지 않고 측정을 끝내 그때까지를 기록으로 남긴다([계획 0053](../plans/active/0053-multiple-cameras.md) 결정 3).
`away`는 영상 멈춤을 포함해 자리 비움(`ABSENCE`) 하나로 묶는다. 앱은 `MISSING`(누락)을 보내지 않는다. 서버가 구간이 빠진 것을 찾으면(`event.reason` `missing`·`missing_sequence`) 서버가 `MISSING`으로 저장한다.
판정 불가는 범위를 넓게 잡아 모두 `UNMEASURABLE` 하나로 저장한다. 판정을 세분화할 때 `exclusion_reason`의 CHECK 선택지를 늘린다.
판정 불가 시간을 측정 시간·점수에서 빼는 것과 3초 연속 시 멈춤 같은 시간 규칙은 서버가 정한다. 앱은 서버가 알려 주는 상태를 표시만 한다.
서버는 프레임 간격 1000ms로 끊김을 보고, 앱은 화면 감시를 1500ms로 한다.
네트워크가 끊기면 그 세션을 끝내고 다시 연결하지 않는다([ADR 0024](../decisions/0024-session-ends-on-lost-connection.md)).

DB 규칙(V2.3)에 맞춰 앱이 지킬 것:

- 제외 사유는 하나만 붙는다(V2.3 우선순위 자리 비움 `ABSENCE` → 일시정지 `PAUSE` → 누락 `MISSING` → 판정 불가 `UNMEASURABLE`). 앱은 `rest`와 `away`를 겹쳐 보내지 않는다. 일시정지 중 카메라가 끊기면 우선순위에 맞춰 `away`를 보낸다(V2.1 때는 `rest`).
- 제외 구간의 시작·끝은 서버가 0.5초 경계에 맞춘다. 앱은 `rest`·`away`로 바뀐 시각을 `t_ms` 그대로 보낸다.
- 짧은 끊김은 같은 사건으로 이어질 수 있다(`EVENT_BREAK_SEC`, 값은 서버가 정함). 앱은 끊김마다 사건을 나눠 보이지 않는다.
- 세션 종료 때 열린 제외 구간은 서버가 종료 시각으로 닫는다. 앱은 종료 전에 `excluded_ended`를 기다리지 않는다.

종료 뒤의 처리(최종 `decision`·`closed(ended)` 대기, 10초 뒤 조회)는 [연동 명세](api-ws-spec.md) 6.1·6.4에 있다.

### 3.3 자세 등록 (측정 시작과 분리)

자세 등록은 "이 사람의 바른 자세"를 한 번 정해 두는 일이다. 서버는 측정 중 좌표를 이 기준과 비교한다.
앱은 측정하기(등록한 자세가 없을 때 3·2·1 뒤 3초), 설정의 「다시 등록」, 회원가입 3단계(선택)에서 등록한다. 측정을 시작할 때는 저장된 기준을 쓴다.
기준값은 서버가 등록 프레임으로 계산한다. 평균은 등록에서만 낸다. 등록 흐름(`hello` `purpose:"calibration"` → `calibration_result`)은 [연동 명세](api-ws-spec.md) 6.2다.

- DB V2.3: 다시 등록할 때마다 `baseline_posture`에 새 행을 넣는다(이력 보존, 세션은 그때 가장 큰 ID를 쓴다). `registered_at`은 앱이 보정을 끝낸 시각이다.
- 실패 기준은 BE 명세대로 3초 안에 판정 가능 프레임 15장 미만이거나 중간에 끊긴 경우다. DB의 최소 표본 20은 예전 앱 계산 등록(`POST /v2/baselines`)용이다.
- 기준 특징값은 저장하지 않고 판정 때 좌표에서 계산한다(BE 명세). 그래서 N8은 ML이 확인만 하면 된다.
- 지금 앱은 등록한 자세를 이 PC에 하나 저장한다(카메라와 상관없이, 10/16. 2장 카메라). 서버가 생기면 등록·조회를 서버로 바꾼다(F2).

## 4. 앱이 받는 것

화면은 서버 결과로만 바뀐다. 메시지별 앱 동작(`ready`·`observation`·`progress`·`decision`·`alert`·`stalled`·`calibration_result`·`closed`)은 [연동 명세](api-ws-spec.md) 5.3과 [WebSocket v2 계약](../../contracts/realtime/realtime-ws.v2.schema.json)에 있다.
판정 불가 사유 `invalid_reason`은 서버가 정한다. 지금 BE는 쓸 프레임이 없으면 `unmeasurable`, 고개 돌림만 있었으면 `head_turn`을 보낸다(BE 명세 11.3). `settling`은 계약에만 있다. 앱은 셋 다 연동 명세 5.3의 문구로 보인다.

### 4.1 화면 상태와 서버 메시지

`features/session/liveView.ts`가 판정 상태를 아래로 바꾸고, 화면은 이것만 본다. 서버를 붙이면 오른쪽 칸의 메시지로 같은 상태를 만든다. 서버가 남은 시간(확정·복귀까지)을 주지 않으면 진행 막대는 숨긴다.

| 상태 | 뜻 | 알약 문구 | 카메라 위 카드 | 서버에서 오는 것 |
|---|---|---|---|---|
| `normal` | 기준과 비슷 | 바른 자세예요 | 없음 | `observation` |
| `suspect` | 변화가 이어지는 중(지속 시간 채우는 중) | 자세가 조금 달라졌어요 | 진행 막대 + "N초 넘게 이어지면 알려드릴게요" | `observation`(남은 시간은 없음) |
| `bad` | 알림 확정 | 몸이 한쪽으로 기울었어요 등 | 교정 안내 + 복귀 진행 막대, 카메라 테두리 로즈 | `decision`(`collapse_confirmed`·`reminder`), `alert` |
| `recovering` | 바른 자세로 돌아오는 중 | 좋아요, 돌아오고 있어요 | 복귀 진행 막대 | `decision`(`recovery_confirmed` 전까지) |
| `unmeasurable` | 측정 품질 부족 | 자세를 확인할 수 없어요 | "이 시간은 기록에서 빠져요" | `observation.valid:false`, `progress.paused_reason:"unmeasurable"` |
| `paused` | 사용자가 쉬는 중 | 쉬는 중 | 없음 | 앱의 `rest` 구간, `progress.paused_reason:"rest"` |
| `analysisPaused` | 서버 판정이 5초간 없음(서버 연결 때) | 분석이 잠시 멈췄어요 | 측정 불가와 같은 회갈색 | `stalled` |

최근 30분 흐름은 화면 표시용으로 5초마다 상태를 샘플링한다. 저장 기록은 판정 합계를 그대로 쓴다.

### 7.0 v2를 다시 할 때 정할 것 (10/19)

10/19에 앱을 v2로 바꿨다가 전략을 바꾸며 되돌렸다(코드는 `48f5e9b` 상태). 그때 정하지 못한 것:

- **서버 결과를 앱이 다시 검사할지:** 되돌린 코드는 서버가 보낸 요약이 이전보다 줄면(되감김) 측정을 멈추고, 2초 넘은 관측은 화면에서 숨겼다. 「서버에서 받은 것만 처리한다」(ADR 0021)에 맞추려면 형식 검사만 남기고 둘 다 빼는 쪽을 권한다(멈춤은 서버 `stalled`가 알려 준다).
- **서버 측정 화면의 카메라 빠짐:** 결정 3(쓰던 카메라가 빠지면 종료·저장, 계획 0053)은 기본 측정 화면(`useSessionScreen.ts`)에만 있다. 서버 측정 화면(`useServerSessionScreen.ts`)은 빠져도 「영상 1초 넘게 없음」으로 일시정지(`away`)만 된다. v2 때 같은 규칙(`end`로 종료·저장)을 넣는다.
- **측정 중 들어오는 영상의 장치·크기가 시작 때와 다르면:** 측정 중에는 카메라 선택이 잠겨 드물다(같은 카메라가 다른 해상도로 다시 켜지는 정도). 지금 서버 측정은 멈추고 재개를 막는다. 위와 같이 종료·저장으로 맞추면 단순하다.
- 그대로 둘 것: 순번 중복 막기(서버 `bad_message` 방지), 좌표를 계약 범위(-1~2)로 자르기, `ready` 5초·`end` 뒤 10초 대기(연동 명세 1.1).
