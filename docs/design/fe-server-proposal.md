# FE 제안서: 서버 판정 이전과 연동

> 작성: 2026-10-11 · 최신화: 2026-10-12(BE 회신 반영, 구조 정리) · FE · 대상: DevOps/BE(홍규), DB(유진), ML(지성)
> 확인 기준: `DevOps` 브랜치 `f27f778`(10/12에도 변경 없음), `feature/repo-backend-db-v2` `0fcde59`(미병합), [실시간 계약 v1](../../contracts/realtime/README.md), DevOps/BE 회신(10/11, 아키텍처 v5)
> FE 검증(10/12): 프론트 303개·브라우저 75개, 이 저장소의 Java 서버 시험(`check-backend`)·Python 시험 통과
> 관련: [ADR 0021](../decisions/0021-app-sends-information-server-judges.md), [FE 검토](fe-review.md), [계획 0023](../plans/active/0023-frontend-server-only.md)·[0024](../plans/active/0024-posture-registration-tab.md)

이 문서는 FE가 팀에 보내는 제안과 합의를 한곳에 모은 것이다. 판정 규칙의 계산 방법은 서버가 맡으므로 여기에 적지 않는다(7장).
FE는 **앱이 보내는 것(2장)**과 **앱이 받는 것(3장)**의 이름과 기능만 정의한다.

## 1. 전제와 현재 구조

1. **판정과 라벨링은 서버가 한다.** 점수·상태·유형·판정 가능 여부·고개 돌림·복귀 대기와 학습용 정답 라벨은 서버(추론·판정·ML)가 만든다.
   앱은 판정하지 않고 라벨도 붙이지 않는다. 서버 없이 쓰는 로컬 모드도 없앤다(ADR 0021).
2. **앱은 입출구 서버 하나와만 통신한다**(아키텍처 v5, 10/11). 입출구 서버(`auth`·`api`·`ws`)는 BE가 만든다. FE는 앱 쪽 연결과 API 명세를 함께 쓴다.
3. **좌표 수집 동의는 가입의 필수 조건이다.** 로컬 모드가 없어 동의 없이는 측정할 수 없다. 가입 동의와 학습 동의는 별개다.

```
앱 ──HTTP /api──▶ 입출구 서버 (auth·api·ws, BE) ──▶ MySQL(계정·설정·세션 행·기록)
앱 ──WebSocket /ws──▶ ws ──▶ posture.features.v1 ─▶ 추론(GPU PC) ─▶ 판정(api-server)
   ▲                   │ ◀── posture.inference.v1 (관측: 화면 실시간 상태)
   └──── push ─────────┘ ◀── posture.episodes.v1 (decision·progress → alert)
```

`ws`가 하는 일(BE): 로그인 세션 확인, 묶음 검사, 순번 중복 제거, Kafka 기록 뒤 `ack`, 세션 시작 때 저장된 기준값 첨부,
재연결 때 놓친 `decision` 먼저·최신 `progress` 마지막, 첫 `hello`에만 `session_started` 발행, `end`에 최종 결과 뒤 `closed(ended)`.
로그인 세션이 측정 중에 만료돼도 그 측정은 끝까지 이어 가고, 다음 연결 때 다시 확인한다.

## 2. 앱이 보내는 것

### 2.1 좌표 프레임 (본문 `posture.frames.v1`, 토픽 `posture.features.v1`)

**0.5초에 1건. 그 안에 찍힌 프레임을 평균 내지 않고 그대로 담는다.** 키는 `session_id`.
본문 `schema_version: "3.0"`, `feature_version: "keypoints-9-v1"`(BE 회신). 계약 스키마는 BE와 함께 만든다.

```json
{
  "sequence": 42,
  "start_ms": 21000,
  "end_ms": 21500,
  "phase": "running",
  "width": 640,
  "height": 480,
  "frames": [
    { "t_ms": 21012, "p": [[0.51234, 0.40211, 0.99], [0.52011, 0.38120, 0.98], "... 9개"] },
    { "t_ms": 21075, "p": null }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `sequence` | 세션 안 순번. 0부터 1씩 증가. 중복 제거·재전송에 쓴다 |
| `start_ms`, `end_ms` | 구간 `[start, end)`. 세션 시작 기준 ms, 보통 500ms 간격 |
| `phase` | `running` / `calibration`(자세 등록) / `rest`(일시정지) / `away`(카메라 끊김) |
| `width`, `height` | 영상 크기(px). 팀 카메라 전제로 640×480을 요청한다 |
| `frames[].t_ms` | 프레임이 찍힌 시각. 세션 시작 기준 ms, 구간 안에서 증가 |
| `frames[].p` | 관절 9개의 `[x, y, visibility]`(아래 순서). 사람이 안 잡힌 프레임은 `null`. 0~30개 |

| 순서 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| 관절 | 코 | 왼눈 | 오른눈 | 왼귀 | 오른귀 | 입 왼쪽 | 입 오른쪽 | 왼어깨 | 오른어깨 |
| MediaPipe 번호 | 0 | 2 | 5 | 7 | 8 | 9 | 10 | 11 | 12 |

- **좌표:** MediaPipe 원본. x, y는 영상 크기에 대한 0~1 비율(소수 5자리), visibility는 소수 2자리. y는 아래로 커진다.
- **좌우:** 영상은 반전하지 않는다. 관절 좌우는 사용자 몸 기준이라 사용자 왼어깨가 화면 오른쪽(큰 x)에 있다.
- **가려진 관절도 좌표는 온다.** MediaPipe가 위치를 추정해서 준다. 쓸지 말지는 서버가 정한다.
- **프레임 수는 일정하지 않다.** 보통 0.5초에 약 8개, 느린 PC는 3~5개. 시간은 개수가 아니라 `t_ms`로 센다.
- **시각은 앱 시계 기준이다.** 서버 수신 시각이 아니라 `t_ms`·`start_ms`·`end_ms`로 계산한다.
- **왜 평균을 내지 않나:** 0.5초 안에 고개를 돌린 장·손에 가려진 장이 섞이면 평균이 가짜 치우침을 만든다. 어느 장을 뺄지도 판단이라 서버 몫이다.

### 2.2 일시정지·카메라 끊김·종료

판단이 아니라 사실이라 앱이 알린다. 메시지가 안 오는 것만으로는 네트워크 끊김과 구별할 수 없다.

| 상황 | 앱이 보내는 것 | DB 제외 사유 |
|---|---|---|
| 사용자가 일시정지 | `phase: "rest"`, `frames: []` | `PAUSE` |
| 카메라 입력이 끊김 | `phase: "away"`, `frames: []` | `MISSING` |
| 측정 종료 | WebSocket `end` | — |

다시 시작하면 `running`으로 돌아간다. 카메라 끊김 뒤에는 사용자가 직접 재개한다.
서버는 프레임 간격 1000ms로 끊김을 보고, 앱은 화면 감시를 1500ms로 한다(BE 회신).
네트워크가 끊기면 앱은 "연결 끊김"을 화면을 막지 않게 띄우고, 좌표를 쌓아 두었다가 다시 연결되면 같은 순번으로 다시 보낸다.

### 2.3 자세 등록 (측정 시작과 분리, 10/12 FE 결정)

자세 등록은 "이 사람의 바른 자세"를 한 번 정해 두는 일이다. 서버는 측정 중 좌표를 이 기준과 비교한다.
앱은 「자세 등록」 탭에서 사용자가 「자세 등록 시작」을 누를 때만 3초 동안 프레임을 `phase: "calibration"`으로 보낸다.
측정을 시작할 때는 등록하지 않고 저장된 기준을 쓴다(앱 화면은 [계획 0024](../plans/active/0024-posture-registration-tab.md)에서 이미 나눴다).
기준값은 서버가 등록 프레임으로 계산한다(BE 회신). 평균은 등록에서만 낸다.

BE 회신(10/11)은 등록을 측정 세션 안에서 하는 것을 전제로 했다. 등록을 측정과 나누려면 아래가 필요하다(5장 N1).

| # | 필요한 것 | 기능 |
|---|---|---|
| ① | 등록만 하는 연결 | 측정 세션 없이 `calibration` 프레임만 보낸다(예: 등록용 세션 종류, `hello`에 목적 표시). 판정·사건·기록은 만들지 않는다 |
| ② | 등록 결과 | 서버가 저장한 뒤 앱에 완료/실패와 새 `baseline_id`·등록 시각을 알린다 |
| ③ | 저장된 기준 조회 | 측정하기 화면이 "등록한 자세가 있는지" 안다. 없으면 404 |
| ④ | 측정 시작 | 측정 세션에는 등록 프레임을 보내지 않는다. `ws`가 저장된 기준을 붙인다. 기준이 없으면 시작을 거절한다 |
| ⑤ | 평균 좌표 18개(DB 저장용) | 서버가 등록 프레임으로 함께 계산하는 쪽을 제안한다. 같은 프레임을 두 곳에서 따로 계산하지 않도록 |

이름과 경로는 BE가 정해도 된다. 지금 앱은 등록한 자세를 앱이 켜져 있는 동안만 기억한다. 위가 생기면 서버 등록·조회를 붙인다.

## 3. 앱이 받는 것 (이름과 기능)

화면은 서버 결과로만 바뀐다. 메시지 이름은 [실시간 계약 v1](../../contracts/realtime/README.md)을 따르고, 새로 필요한 것은 **추가**로 표시했다.

### 3.1 WebSocket (서버 → 앱)

| 이름 | 언제 오나 | 앱이 하는 일 |
|---|---|---|
| `ack` | `last_sequence`까지 Kafka에 넣었을 때 | 재전송 대기열에서 지운다 |
| `observation` | 0.5초 구간마다 | 실시간 상태 알약과 안내 문구를 바꾼다(3.2). 재연결 때 다시 오지 않는다 |
| `progress` | 약 1초마다 | 측정 시간·바른 자세 비율 등 숫자를 바꾼다. 측정 멈춤 상태도 여기서 안다. 재연결 때는 최신 것 하나만 |
| `decision` | 사건이 확정됐을 때 | 사건 기록과 숫자를 바꾼다(3.3). 재연결 때 놓친 것을 다시 받는다 |
| `alert` | 흐트러진 자세 확정·재알림일 때 | 토스트와 소리를 띄운다. 앱은 따로 거르지 않는다. 오래된 사건(제안 10초)에는 오지 않는다 |
| `stalled` | 5초 동안 판정 진행이 없을 때 | "분석이 잠시 멈췄어요"를 보인다 |
| `closed` | 채널이 끝날 때 | 이유별로 처리: `ended`(정상 종료), `unauthorized`(다시 로그인), `not_owner`, `session_lost`, `server_shutdown` |

### 3.2 `observation`에서 쓰는 값

| 값 | 기능 |
|---|---|
| `valid` | 이 구간을 판정했는지 |
| `collapse_probability` | 판정 점수. 화면 점수는 `100 × (1 − 점수)` |
| `invalid_reason` (**추가**, BE 동의) | `valid=false`일 때만. 화면 안내 문구를 고른다(아래) |
| `valid_ms` (**추가**, BE 회신 P1) | 구간 안 판정 가능 시간. 앱은 표시에 쓰지 않는다(판정기 시간 누적용) |

| `invalid_reason` | 뜻 | 앱 안내 |
|---|---|---|
| `unmeasurable` | 가림·화면 밖·사람 없음 | "자세를 확인할 수 없어요" |
| `head_turn` | 고개를 돌림 | "고개를 돌린 동안은 판정하지 않아요" |
| `settling` | 돌아온 직후 자세를 다시 잡는 중 | "자세를 다시 잡는 중이에요" |

`head_turn`·`settling`이 언제 나오는지는 서버가 정한다. 앱은 이 값을 받아 문구만 고른다.

### 3.3 `decision`의 사건 종류

| 종류 | 앱이 하는 일 |
|---|---|
| `collapse_confirmed` | 사건 시작 기록 |
| `reminder` | 재알림 기록 |
| `recovery_confirmed` | 사건을 복귀로 닫는다 |
| `interrupted` | 사건을 끊김으로 닫는다. 사유가 판정 불가면 "측정 멈춤 – 어깨가 보이게 앉아 주세요"를 띄운다 |
| `session_ended` | 결과 화면으로 간다 |
| `excluded_started`·`excluded_ended` (**추가**) | 제외 구간 경계(DB 저장용). 앱은 받기만 하고 표시하지 않는다 |

## 4. BE 제안에 대한 FE 확인

BE 회신(10/11)의 제안을 FE가 확인한 결과다. **정한 쪽**이 FE가 아닌 항목은 FE가 받아들인 것이다(10/12 사용자 확인).

| BE 번호 | 내용 | 정한 쪽 | FE 확인 |
|---|---|---|---|
| S1 | 민감도 범위 | 기존 앱 동작 | 서버 검증 범위는 0.5~0.95. 0.80·0.70·0.60은 화면 3단계 버튼 값. 기본 정책 시드는 DB V2.2에서 이미 0.700 |
| S2 | 부동소수는 float64 | BE 제안 수용 | 넘겨준 규칙 자료에 반영(7장) |
| S3 | 두 귀가 모두 있어야 판정 가능 | BE 제안 수용 | 앱 규칙·시험 데이터(`one_ear_missing`)에 반영 |
| S4 | 상수를 서버 설정 한곳에 | BE 제안 수용 | — |
| S5 | 카메라 끊김: 서버 1000ms, 앱 화면 1500ms | BE 제안 수용 | 2.2 |
| S6·P2 | 기준값은 서버가 등록 프레임으로 계산 | BE 결정 | 2.3. 등록 경로는 N1 |
| P1 | 관측에 `valid_ms`와 점수 | BE 제안, 점수 방식은 ML 결정 | 3.2. 점수 방식은 N3 |
| P3 | 기준값(특징값) DB 칸 추가 | DB 결정 | N8 |
| P4 | 측정 멈춤은 `interrupted` + `progress` | BE 제안 수용 | 3.1·3.3 |
| C3 | 시간은 `t_ms` 기준 | BE 제안 수용 | 2.1 |
| C4 | 재전송된 과거 사건에는 `alert` 안 보냄(제안 10초) | BE 제안 수용 | 3.1 |
| R-4 | 측정 종료는 WebSocket `end` | BE 제안, 회의 확정 | FE 동의(N4) |

## 5. 남은 질문과 요청

번호를 하나로 합쳤다. 괄호는 예전 문서·BE 회신의 번호다.

| # | 내용 | 대상 |
|---|---|---|
| N1 | **자세 등록을 측정과 나누는 흐름**(2.3 ①~⑤) (Q11·M4) | BE·DB |
| N2 | **학습 라벨 경로**: v5 학습은 앱 CSV로 수동이고 서버 판정 결과와 이어지지 않는다. 앱은 라벨을 만들지 않는다(수집 CSV v3에도 판정 열 없음). ML이 CSV에 직접 붙일지, 서버 판정 결과를 내보낼 경로를 만들지 (C1·M1) | ML·PM |
| N3 | 0.5초 관측의 점수 방식: 최댓값 또는 마지막 판정 프레임 값 (P1·M3). 정해지면 FE가 0.5초 단위 시험 데이터를 더한다. FE 의견(미확정): 최댓값은 튀는 프레임 하나에 끌려가므로 마지막 값이 덜 흔들린다 | ML |
| N4 | 측정 종료 `end` 확정 (R-4·M2) | 회의 |
| N5 | 추론의 좌표 입력 완료 목표일 (Q2) | DevOps/BE |
| N6 | 알림 표시·억제를 서버 어디서 판단하나 (Q8). 앱은 받은 `alert`만 띄운다 | BE |
| N7 | 유형 값 `deviation_type`을 남길지 (Q9). N2와 함께 | ML |
| N8 | 기준값(특징값 5개 + `quality`) DB 칸 (P3) | DB |
| N9 | 좌표 수집 동의 저장(`user_consent` 보류 해제). 가입 동의와 학습 동의 분리 (C2). 가입 동의문은 FE가 만든다 | DB |
| N10 | `feature_archive`를 "특징값 적재"에서 좌표 프레임 기준으로 | DB |
| N11 | 자세 데이터 수집 화면의 새 요구 | BE·ML |
| N12 | 팀 저장소 push 현황 (Q10) | BE |

FE가 할 일(질문 아님): 등록 전에 어깨가 화면 아래 끝에서 충분히 떨어져 있는지 앱 구도 확인에서 본다.

## 6. 서버 부담 (동시 50명, 하루 8시간 추정)

| 항목 | 특징값 전송(예전) | 좌표 전송(지금) |
|---|---|---|
| 메시지 | 0.5초에 1건, 수백 바이트 | 0.5초에 1건, 약 2KB |
| Kafka 유입량 | 수십 KB/s | 약 200KB/s |
| 서버 계산 | 0.5초당 점수 1번 | 초당 약 800프레임(계산은 가볍다) |
| 저장 | MySQL에 결과만 | HDFS에 좌표 약 5GB/일 추가 |

메시지 수가 같아서 처리량은 거의 같다(10/01 측정 기준 약 40~50명, DevOps 재측정 예정).
실제 부담은 구현·운영이다: 좌표 처리 단계, 세션별 상태, 3초 규칙과 자동 재개, HDFS 적재·동의 철회 삭제, 서버 장애 시 화면 판정 정지.

## 7. 넘겨준 판정 규칙과 시험 데이터
