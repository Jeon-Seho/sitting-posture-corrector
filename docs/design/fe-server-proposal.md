# FE 제안: 서버 판정 이전과 DevOps 연동

> 작성: 2026-10-11 · FE · 대상: DevOps(홍규), DB(유진), ML(지성)
> 확인 기준: `DevOps` 브랜치 `f27f778`(2026-10-10), `feature/repo-backend-db-v2` `fcc8ef7`(2026-10-11, 미병합), [실시간 계약 v1 초안](../../contracts/realtime/README.md)
> 시험 데이터: [`contracts/examples/frames/reference-rule-cases.json`](../../contracts/examples/frames/reference-rule-cases.json)
> 이 문서는 FE가 보낸 제안을 하나로 모은 것이다. 이미 반영·확인된 내용은 뺐다(git 이력에 남음). 관련: [ADR 0021](../decisions/0021-app-sends-information-server-judges.md), [FE 검토](fe-review.md)

## FE 전제

1. **판정과 라벨링은 서버가 한다.** 점수·상태·유형 판정과 학습용 정답 라벨은 서버(추론·판정·ML)가 만든다. 앱은 판정하지 않고 라벨도 붙이지 않는다. 서버 없이 쓰는 로컬 모드도 없앤다.
2. **데이터는 Kafka로 전달한다.** 앱 → 게이트웨이 → Kafka → 추론 → 판정 → Kafka → 게이트웨이 → 앱.
   **보낼 좌표의 관절·형식은 BE·ML이 요구하는 대로 따른다.** 4장의 FE 초안(`posture.frames.v1`)은 출발점일 뿐이다.
3. **서버는 거의 구축됐다고 보고, FE는 연결에 필요한 부분만 맞춘다.** Kafka 뒤쪽(추론 → 판정 → `posture.episodes.v1`)은 계약 v1대로 동작하므로 그대로 쓰고, 비어 있는 앱 쪽 끝(게이트웨이)은 FE가 만든다.

## 3. 게이트웨이 (FE 담당)

Kafka는 서버 PC 안에서만 열려 있다(9092는 `127.0.0.1`, 9094는 GPU PC만). 그래서 게이트웨이도 **서버 PC의 Compose 네트워크 안**에서
`kafka:19092`로 붙고, 브라우저는 게이트웨이의 WebSocket 포트 하나만 본다. 코드는 FE가 쓰고 서버 PC 배치는 DevOps와 같이 한다.

```
브라우저 ──WebSocket──▶ 게이트웨이 ──produce──▶ 좌표 토픽(Q2) ─▶ 추론 ─▶ 판정
   ▲                      │  consume ◀── posture.inference.v1 (관측: 화면 실시간 상태)
   └──────── push ────────┘  consume ◀── posture.episodes.v1 (decision·progress → alert)
```

하는 일: 로그인·세션 주인 확인(`hello`), 묶음 검사, 순번 중복 제거, Kafka 기록 뒤 `ack`, 세션별 결과 push,
`decision`에서 `alert` 만들기, 재연결 때 놓친 `decision` 재전송, 5초 진행 없음 → `stalled`.
WebSocket 메시지와 봉투는 [실시간 계약 v1](../../contracts/realtime/README.md)을 따르고 본문만 좌표로 바뀐다.
**게이트웨이는 판정하지 않는다.** 좌표를 바꾸거나 거르지 않고 그대로 Kafka에 넣는다.

1. **코드 위치(Q3):** 독립 서비스 `backend/realtime`(Spring Boot). DevOps Compose에 컨테이너 하나를 더하고 팀 API와 따로 배포한다.
2. **로그인 확인(Q4):** 브라우저는 팀 API의 로그인 쿠키(Spring Session)를 가진다. 게이트웨이가 그 쿠키로 `GET /auth/me`를 불러 사용자를 확인하고,
   세션 주인은 `GET /sessions/{id}/metadata`로 확인한다. Nginx가 `/api/v1/realtime`을 게이트웨이로 넘긴다(같은 출처).
3. **시험:** 단위 시험은 임베디드 Kafka(`spring-kafka-test`), 왕복 시험은 로컬 Docker Kafka로 먼저 한다. 추론이 좌표를 받기 전에는 지금 형식(`posture.features.v1`)의 합성 메시지를 쓴다.
   실제 왕복은 서버 PC에서 게이트웨이로 합성 세션을 흘려 `decision`·`progress`가 앱까지 오는지 본다(T-13).
4. **끊김:** 네트워크가 끊기면 앱은 "연결 끊김"을 화면을 막지 않게 띄우고, 좌표를 쌓아 두었다가 다시 연결되면 순번 그대로 다시 보낸다.

## 4. 입력: 좌표 프레임 (FE 초안 `posture.frames.v1`)

**0.5초에 1건. 그 안에 찍힌 프레임을 가공하지 않고 그대로 담는다.** 키는 `session_id`. 정해지면 계약 스키마로 만든다(Q2).

```json
{
  "sequence": 42,
  "start_ms": 21000,
  "end_ms": 21500,
  "phase": "running",
  "frames": [
    { "t_ms": 21012, "p": [[0.51234, 0.40211, 0.99], [0.52011, 0.38120, 0.98], "... 9개"] },
    { "t_ms": 21075, "p": null }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `sequence` | 세션 안 순번. 0부터 1씩 증가. 중복 제거·재전송에 쓴다 |
| `start_ms`, `end_ms` | 구간 `[start, end)`. 세션 시작 기준 ms, 보통 500ms 간격 |
| `phase` | `running` / `calibration`(보정) / `rest`(일시정지) / `away`(카메라 끊김) |
| `frames[].t_ms` | 프레임이 찍힌 시각. 세션 시작 기준 ms |
| `frames[].p` | 관절 9개의 `[x, y, visibility]`(아래 순서). 사람이 안 잡힌 프레임은 `null` |

| 순서 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| 관절 | 코 | 왼눈 | 오른눈 | 왼귀 | 오른귀 | 입 왼쪽 | 입 오른쪽 | 왼어깨 | 오른어깨 |
| MediaPipe 번호 | 0 | 2 | 5 | 7 | 8 | 9 | 10 | 11 | 12 |

- **좌표**: x, y는 영상 크기에 대한 0~1 비율(소수 5자리), visibility는 소수 2자리. y는 아래로 커진다. 보내는 좌표는 MediaPipe 원본이다.
- **영상 크기**(`width`, `height`)는 세션 시작 메시지에 한 번만 넣는다. 팀 카메라 전제로 640×480을 요청한다.
- **좌우**: 영상은 반전하지 않는다. 관절 좌우는 사용자 몸 기준이라 사용자 왼어깨가 화면 오른쪽(큰 x)에 있다.
- **visibility가 낮은 관절도 좌표는 온다.** 판정 가능 여부는 visibility로 정한다(5장).
- **프레임 수는 일정하지 않다.** 보통 0.5초에 약 8개, 느린 PC는 3~5개, 빠른 PC는 15개까지. 상한 30개. 시간 계산은 개수가 아니라 `t_ms`로 한다.
- **시각은 앱 시계 기준이다.** 지속 시간·3초 규칙·복귀 시간은 서버 수신 시각이 아니라 `t_ms`·`start_ms`·`end_ms`로 계산한다.
- **양**: 1건 약 2KB, 1명 1시간 약 10~15MB. 좌표는 HDFS에 적재한다. 좌표 전송 동의는 가입의 필수 조건이다(로컬 모드가 없어 동의 없이는 측정할 수 없다, ADR 0021).

`rest`·`away`는 판단이 아니라 사실이라 앱이 알린다. 메시지가 안 오는 것만으로는 네트워크 끊김과 구별할 수 없다.

| 상황 | 앱이 보내는 것 | DB 제외 사유 |
|---|---|---|
| 사용자가 일시정지 | `phase: "rest"`, `frames: []` | `PAUSE` |
| 카메라 입력이 끊김 | `phase: "away"`, `frames: []` | `MISSING` |

다시 시작하면 `running`으로 돌아간다. 카메라 끊김 뒤에는 사용자가 직접 재개한다. `rest`는 일시정지 전용이다.

## 5. 서버가 앱과 같은 결과를 내기 위한 판정 규칙

지금 앱 코드(`model/prototype/pose.ts`, `frontend/src/lib/returnSettle.ts`)의 규칙이다. 앱에서는 이 판정을 없애므로 서버가 넘겨받는다.
값은 실험으로 정한 임시값이며 의학적 기준이 아니다.

### 5.1 확인 방법

- 시험 데이터의 `frame_cases`·`sequence_cases`·`calibration_case`를 서버 구현에 넣고 `expected`와 비교한다(구조는 부록).
- 실수는 **절대 오차 1e-9 이내**로 비교한다. 같은 크기의 변화도 연산 때문에 마지막 자리가 다르다.
- 경계 비교(`> 0.15`, `>= 0.65`)는 **아래 식과 같은 연산 순서**로 계산한다. 다르면 사례 `head_turn_float_boundary`의 결과가 바뀐다.

### 5.2 판정 가능 검사와 특징값

코 N, 왼어깨 L, 오른어깨 R 중 하나라도 아래에 해당하면 **판정 불가**(특징값 없음)다.

| 조건 | 값 |
|---|---|
| 좌표나 visibility가 유한수가 아님 | |
| visibility | `< 0.65` 또는 `> 1` |
| 가장자리 | x 또는 y가 `< 0.02` 또는 `> 0.98` |
| 어깨 폭 `span = hypot((L.x − R.x)·W, (L.y − R.y)·H)` | `span < W · 0.1` |

```
cx = (L.x + R.x) / 2
cy = (L.y + R.y) / 2
head_x = (왼귀.x + 오른귀.x) / 2        # 두 귀 x가 유한수일 때. 아니면 N.x
head_gap         = (cy − N.y) · H / span
lateral_offset   = (head_x − cx) · W / span
shoulder_tilt    = (L.y − R.y) · H / span
quality          = min(N.vis, L.vis, R.vis)
head_turn_offset = (N.x − head_x) · W / span
```

귀는 visibility를 보지 않는다(사례 `ears_low_visibility_still_used`).

### 5.3 기준 자세(보정)

| 규칙 | 값 |
|---|---|
| 연속 시간 | 첫 프레임부터 3000ms 이상 |
| 최소 표본 | 판정 가능한 프레임 15개 이상 |
| 끊김 | 판정 불가 프레임이 하나라도 나오거나 프레임 간격이 1000ms를 넘으면 처음부터 다시 |
| 기준값 | **프레임마다 계산한 특징값 5개의 평균** |

보정마다 앱이 새 `calibration_uuid`를 만들고 `calibration_sec`(3.0)·`sample_count`와 함께 입구 API로 보낸다. 보정 프레임 원본은 `phase: "calibration"`으로 보내며 판정에는 쓰지 않는다.

**정할 것(8장 #1).** v4 회신은 "앱이 좌표 9개의 x·y 평균 18개를 보낸다"였다. 서버가 평균 좌표로 특징값을 다시 계산하면 앱과 값이 조금 다르고
(`calibration_case`: `head_gap` 0.75395 vs 0.75376, `shoulder_tilt` 0.00402 vs 0.00377), 기준의 `quality`도 알 수 없다.
특징값 계산은 판정 규칙이라 앱이 하지 않는다(ADR 0021). FE 제안: 앱은 평균 좌표 18개(DB 저장용)와 보정 프레임 원본을 보내고,
기준값을 평균 좌표로 계산할지 원본 프레임의 특징값 평균으로 계산할지는 서버가 정한다. 용어와 선택지는 8.1.

### 5.4 고개 돌림

```
head_turned = |current.head_turn_offset − baseline.head_turn_offset| > 0.15
```

- 현재·기준이 모두 유효(5.5 조건)할 때만 검사한다. 고개 돌림 프레임은 판정하지 않는다(`head_turn`).
- 0.15 이하는 그대로 판정한다. 실제 촬영(10/08)에서 자세 변화는 최대 0.06, 끝까지 돌린 고개는 0.15~0.4였다.

### 5.5 변화량과 점수

현재·기준 모두 특징값 4개(`head_gap`·`lateral_offset`·`shoulder_tilt`·`quality`)가 유한수이고 `0.65 ≤ quality ≤ 1`이어야 한다.

```
d_head  = current.head_gap       − baseline.head_gap
d_side  = current.lateral_offset − baseline.lateral_offset
d_tilt  = current.shoulder_tilt  − baseline.shoulder_tilt
score   = min(1, max(|d_head| / 0.22, |d_side| / 0.2, |d_tilt| / 0.03) · 0.7)
```

`score ≥ threshold`(기본 0.7, 사용자 0.5~0.95)이면 붕괴 후보다. DevOps `realtime.py`의 `score_feature_deltas`와 같은 식이다.

### 5.6 복귀 대기

판정 불가나 고개 돌림 뒤에는 사용자가 자세를 다시 잡는 중이라 잠시 판정하지 않는다(돌아오자마자 점수가 매겨지면 불쾌하다는 실사용 의견).

```
hold_until = −∞
프레임마다 (시간 순서대로):
  판정 가능          → judged = (t ≥ hold_until)
  판정 불가          → hold_until = max(hold_until, t + 3000); judged = false
  고개 돌림          → hold_until = max(hold_until, t + 1000); judged = false
```

- 보류는 **늘어나기만 한다**(사례 `turn_inside_unmeasurable_hold`). 보류 중 프레임은 바른 자세도 붕괴도 아니다.
- 3초인 이유: 2초로는 실제 촬영에서 자리를 잡는 약 0.7초 동안 붕괴가 찍혔다.

## 6. 판정 불가 시간 처리 (2026-10-08 결정, 서버가 처음 구현)

앱에도 없는 규칙이라 시험 데이터에 기대값이 없다. 아래 예시로 확인한다.

| 상황 | 서버 처리 |
|---|---|
| 판정 불가 **3초 미만** | 붕괴·복귀 시계를 **그 자리에 멈춘다.** 0으로 돌리지 않고 진행 중인 사건도 닫지 않는다 |
| 판정 불가 **3초 연속** | 측정을 멈추고 진행 중인 사건을 "끊김"(`recovered=false`)으로 닫는다. 시계는 0. 앱에 멈춤을 알린다("측정 멈춤 – 어깨가 보이게 앉아 주세요") |
| 멈춘 뒤 **0.5초 연속 판정 가능** | 자동 재개하고 새로 센다. 사용자가 버튼을 누르지 않는다 |
| `rest`·`away` | 진행 중인 사건을 끊김으로 닫고 시계를 0으로 |

- **고개 돌림과 복귀 대기 구간은 3초 연속에 세지 않는다.** 옆 모니터를 3초 넘게 보는 건 정상 행동이고, 손이 어깨를 잠깐 가린 것만으로 측정이 멈추면 안 된다.
- 이 구간들은 붕괴 시간에도 복귀 시간에도 넣지 않는다.

**확인용 예시** (구간 0.5초, 정책 3·3·60·0.7)

| 입력 | 기대 결과 |
|---|---|
| 붕괴 4개(2초) → 판정 불가 2개(1초) → 붕괴 2개(1초) | 마지막 구간에서 사건 확정(누적 3초). 실제 시각으로는 4초째 |
| 사건 진행 중 → 판정 불가 6개 미만 → 정상 6개 | 정상 6개째에 복귀 확정. 판정 불가는 복귀 시간에 안 들어감 |
| 사건 진행 중 → 판정 불가만 계속 | 3초째에 측정 멈춤, 사건 끊김. 복귀로 기록하지 않음 |
| `rest` 구간 뒤 `running` 붕괴 6개 | 6개째에 새 사건 확정. 멈춤 전 누적은 이어지지 않음 |

**DevOps v1 판정기(`f27f778`)와 남은 차이:** 판정 불가(`valid=false`) 구간이 하나만 와도 바로 사건을 끊고 누적을 0으로 돌린다. 코드 주석대로 `invalid_reason`이 생긴 뒤 D-23에서 바꿔 달라.

## 7. 서버가 앱에 돌려줄 것

화면은 서버 결과로만 바뀐다. WebSocket 메시지는 [실시간 계약 v1](../../contracts/realtime/README.md)을 따른다. 추가로 필요한 것:

| 항목 | 내용 |
|---|---|
| `observation.invalid_reason` (Q6) | `valid=false`일 때만 채우고 `true`면 `null`. 아래 표 |
| 측정 멈춤·재개 | 6장의 3초 연속 멈춤과 자동 재개를 앱이 알 수 있어야 한다 |
| `excluded_started`·`excluded_ended` | 제외 구간 경계 사건(DB `excluded_interval`). 앱은 받기만 하고 표시하지 않는다 |
| `alert` | 알림 켜기·끄기(`user_account.alert_enabled`)와 시간당 상한은 서버가 판단한다. 앱은 받으면 띄우기만 한다 |

| `invalid_reason` | 뜻 | 앱 안내 |
|---|---|---|
| `unmeasurable` | 판정 불가(가림·visibility 부족·화면 밖·사람 없음) | "자세를 확인할 수 없어요" |
| `head_turn` | 고개 돌림(5.4) | "고개를 돌린 동안은 판정하지 않아요" |
| `settling` | 복귀 대기(5.6) | "자세를 다시 잡는 중이에요" |

DB `exclusion_reason`(`PAUSE`·`MISSING`·`ABSENCE`·`UNMEASURABLE`, BR-52 우선순위)은 저장용 구간 사유이고 이 값은 화면 안내용이라 따로 둔다.
`head_turn`·`settling` 구간은 DB에 `UNMEASURABLE`로 저장한다.

### 8.1 여러 프레임을 무엇으로 보내나 (#1·#2, 2026-10-12 FE 정리, 미정)

카메라는 초당 약 16장을 찍는다. 보정 3초 동안 약 48장, 측정 중 0.5초마다 약 8장이 나온다.
이 여러 장을 **앱이 어떤 형태로 서버에 보낼지**가 이 질문이다. 앱은 판정하지 않으므로(ADR 0021) 선택지는 모두 **좌표(정보)**를 어떻게 보내느냐이고,
점수·판정은 어느 경우든 서버가 계산한다.

용어:

- **좌표 18개 평균**: 관절 9개 각각의 x를 여러 장에 걸쳐 평균하고, y도 평균한 값(9 × 2 = 18개).
  예: 왼어깨 x가 48장에서 0.6100, 0.6102, 0.6098 … 이면 그 평균 하나. 계산은 단순 산술 평균이고 판정 규칙이 들어가지 않는다.
  서버는 이 18개로 특징값(머리 높이·좌우 치우침·어깨 기울기·고개 돌림)을 **한 번** 계산한다. V2.1 `baseline_posture`가 이 형식이다.
- **특징값 평균**: 장마다 특징값을 먼저 계산(5.2 식: 어깨 폭으로 나누기 등)한 뒤, 그 특징값들을 평균한 값. 지금 앱 보정이 이 방식이다.
  특징값 식은 판정 규칙의 일부라 **앱이 계산하면 ADR 0021과 맞지 않는다.** 앱이 보낸다면 이 방식은 빠진다. 서버가 원본 프레임으로 계산할 때만 쓸 수 있다.
- 두 방식의 차이: 특징값 식에 나눗셈(어깨 폭)이 있어 "평균한 뒤 계산"과 "계산한 뒤 평균"이 조금 다르다.
  시험 데이터 `calibration_case`에서 `head_gap` 0.75395 vs 0.75376, `shoulder_tilt` 0.00402 vs 0.00377이고, 점수로 바꾸면 최대 약 0.006(`0.00025 ÷ 0.03 × 0.7`)이다. threshold 0.7에 비해 작다.

| 선택지 | 보정 (기준 자세) | 측정 (0.5초마다 1건) |
|---|---|---|
| **평균값** | 좌표 18개 평균을 보낸다(입구 API → DB). 특징값은 서버가 이 평균으로 계산 | 0.5초 안 프레임의 관절별 좌표 평균 1장을 보낸다 |
| **특정값** | 대표 프레임 1장(예: 마지막 장 또는 관절별 중앙값)을 보낸다 | 대표 프레임 1장을 보낸다 |
| **모든 값** | 보정 프레임 원본 전체를 보낸다. 기준값 계산 방식(좌표 평균 / 특징값 평균)은 서버가 정한다 | 프레임 원본 전체를 보낸다(4장 초안) |

선택지별 고려할 점:

| | 장점 | 단점 |
|---|---|---|
| **평균값** | 작다. 보정은 DB 형식(18개)과 같다 | 측정에서는 고개를 돌린 장·손에 가려진 장이 평균에 섞여 **가짜 치우침**이 생긴다. 어느 장을 뺄지는 판단이라 앱이 거를 수 없다. visibility 평균도 같이 보내야 서버가 판정 가능 여부를 알 수 있다 |
| **특정값** | 가장 작다 | 한 장의 흔들림(관절 추정 오차 약 0.005)이 그대로 들어간다. 나머지 장은 버려져 재처리·ML에 쓸 수 없다 |
| **모든 값** | 정보 손실이 없다. 서버·ML이 규칙을 바꿔도 다시 계산할 수 있다(ADR 0021의 목적). 연구용 CSV와 같은 속도라 학습·서비스 데이터가 맞는다 | 가장 크다(1건 약 2KB, 9장 참고). 서버가 여러 장을 관측 1건으로 합치는 규칙을 정해야 한다 |

FE 의견:

- **측정은 모든 값**(4장 초안 그대로)을 권한다. 평균은 가짜 치우침 때문에, 특정값은 정보 손실 때문에 ADR 0021의 목적과 맞지 않는다.
- **보정은 좌표 18개 평균을 DB 저장용으로 보내고, 보정 프레임 원본도 함께 보낸다**(`phase: "calibration"`). 기준값을 무엇으로 계산할지는 서버가 정한다.
- 측정을 모든 값으로 보내면 **서버가 0.5초 안 여러 장을 관측 1건으로 합치는 방법**은 서버·ML이 정한다.
  관측을 장마다 내면 판정기 쪽 Kafka(`posture.inference.v1`)가 다시 초당 약 16건이 되므로 0.5초에 1건으로 합치는 편이 맞다.
- 정해지면 FE가 그 방식으로 0.5초 단위 `sequence_cases`를 시험 데이터에 추가한다.

## 9. 서버 부담 (동시 50명, 하루 8시간 추정)

| 항목 | 특징값 전송(지금) | 좌표 전송(바뀐 뒤) |
|---|---|---|
| 메시지 | 0.5초에 1건, 수백 바이트 | 0.5초에 1건, 약 2KB |
| Kafka 유입량 | 수십 KB/s | 약 200KB/s |
| 서버 계산 | 0.5초당 점수 1번 | 초당 약 800프레임 검사·특징값(계산은 가볍다) |
| 저장 | MySQL에 결과만 | HDFS에 좌표 약 5GB/일 추가 |

실제 부담은 구현·운영이다: 5장 처리 단계, 세션별 상태 보관(기준값·복귀 대기·판정 불가 연속 시간, 재시작 뒤에도 이어지게),
3초 규칙과 자동 재개, `invalid_reason`, HDFS 적재·동의 철회 삭제·보존, 서버 장애 시 화면 판정 정지.

## 부록. 시험 데이터

`sequence_cases`는 지금 앱의 구간 규칙을 따른다. 앱은 **이웃한 두 프레임 사이 `[이전 t, 현재 t)`를 구간 하나**로 만든다(약 60ms).

| 규칙 | 값 |
|---|---|
| 첫 프레임 | 다음 구간의 시작점으로만 쓴다 |
| 구간 품질 | 두 끝 프레임이 모두 `judged`면 `good`, 아니면 `poor` |
| 구간 점수 | `good`이면 현재(끝) 프레임의 변화량·점수 |
| 프레임 간격 > 1000ms | 구간을 만들지 않고 측정을 멈춘다(`paused_at_ms`) |

| 키 | 내용 |
|---|---|
| `constants` | 이 문서의 값 |
| `baseline` | 기준 자세 좌표 한 장과 그 특징값. `frame_cases`는 이 기준과 비교한다 |
| `frame_cases[]` | 좌표 한 장 → `features`, `observed`(`measurable`·`unmeasurable`·`head_turn`), `deltas`, `score` |
| `sequence_cases[]` | 시간 순서 프레임 → 프레임별 `judged`, 구간(`good`/`poor`, 점수), `paused_at_ms` |
| `calibration_case` | 보정 16장 → 앱 기준값과 평균 좌표로 계산한 값(5.3 비교용) |

앱 코드로 만들었고 앱 시험(`referenceRuleCases.test.ts`)이 매번 같은지 확인한다. 다시 만들기: `frontend`에서 `UPDATE_RULE_CASES=1 npx vitest run referenceRuleCases`.
