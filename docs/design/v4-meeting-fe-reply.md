## 전제 (결정됨)

앱은 관절 좌표 같은 **정보만** 보낸다.
점수, 붕괴 유형(머리/좌우), 고개 돌림, 판정 가능 여부, 복귀 대기 같은 **판단은 전부 서버가** 한다.
앱에서 라벨을 붙이면 나중에 규칙·모델을 개선할 때 과거 데이터를 다시 계산할 수 없기 때문이다.
**서버 부담이 커지는 것을 알고 정한 결정이다.** 늘어나는 부담은 [아래](#서버-부담-이-결정으로-늘어나는-것)에 정리했다.

이 결정은 [데이터 플랫폼 경계](data-platform-boundary.md)의 "좌표 미전송" 원칙과 실시간 계약 초안의 "좌표를 넣지 않는다" 규칙을 바꾼다.
2026-10-11 [ADR 0021](../decisions/0021-app-sends-information-server-judges.md)로 남기고 두 문서에 변경 안내를 붙였다.
같은 날 앱의 판정 라벨(상태·유형)과 로컬 모드도 모두 없애기로 했다.

## 안건 2: Kafka 메시지 1건의 단위

**답: 0.5초에 1건. 그 안에 0.5초 동안 찍힌 프레임을 가공하지 않고 그대로 담는다.**

### 메시지 1건에 담는 내용

```json
{
  "sequence": 42,
  "start_ms": 21000,
  "end_ms": 21500,
  "phase": "running",
  "frames": [
    { "t_ms": 21012, "p": [[0.51234, 0.40211, 0.99], [0.52011, 0.38120, 0.98], "... 9개"] },
    { "t_ms": 21075, "p": null }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `sequence` | 세션 안 순번. 0부터 1씩 증가. 중복 제거·재전송에 쓴다 |
| `start_ms`, `end_ms` | 구간 `[start, end)`. 세션 시작 기준 ms, 보통 500ms 간격 |
| `phase` | `running` / `calibration` / `rest`(일시정지) / `away`(카메라 끊김) (안건 5·6 참고) |
| `frames[].t_ms` | 프레임이 찍힌 시각. 세션 시작 기준 ms |
| `frames[].p` | 관절 9개의 `[x, y, visibility]`를 고정 순서로 담는다. 사람이 안 잡힌 프레임은 `null` |

- **관절 순서 (MediaPipe 번호)**: 코 0, 왼눈 2, 오른눈 5, 왼귀 7, 오른귀 8, 입 왼쪽 9, 입 오른쪽 10, 왼어깨 11, 오른어깨 12.
- **소수점**: x와 y는 소수 5자리, visibility는 소수 2자리.
- **화면 크기**(`width`, `height`)는 세션 시작 메시지에 한 번만 넣는다. 좌표가 0~1 비율이라 실제 거리 계산에 필요하다.
  V2.1 DB는 640×480 고정을 전제로 화면 크기 컬럼을 지웠다. 2026-10-11: 팀 카메라(640×480 지원)를 전제로 그대로 두고,
  HDFS 메타 정보 추가는 따로 제안하지 않는다.

### 이렇게 정한 이유

- DevOps가 측정한 한계(구간마다 보내면 동시 4~5명)는 메시지 **개수** 문제다. 0.5초에 1건이면 개수는 줄고 정보는 그대로다.
- **평균을 내지 않는 이유**: 0.5초 안에 고개를 돌린 프레임이나 손에 가려진 프레임이 섞이면 평균이 가짜 치우침을 만든다. 어떤 프레임을 버릴지도 판단이라 서버 몫이다.
- ML이 받는 서버 데이터가 지금 연구용 csv와 같은 프레임 속도가 된다. 학습 데이터와 서비스 데이터가 어긋나지 않는다.

### 유의사항

- **프레임 수는 일정하지 않다.** 보통 0.5초에 약 8개(초당 약 16)이지만 느린 PC는 3~5개, 빠른 PC는 15개까지 나온다. 시간 계산은 프레임 개수가 아니라 `t_ms`로 한다. 상한은 30개로 둔다.
- **좌우 방향**: 영상은 좌우 반전하지 않는다. MediaPipe의 left/right는 사용자 몸 기준이고, 화면 x가 커질수록 사용자의 왼쪽이다.
- **visibility가 낮은 관절도 좌표는 온다.** MediaPipe는 가려진 관절도 위치를 추정해서 준다. visibility로 판정 가능 여부를 정한다(지금 기준 0.65).
- **시각은 앱 시계 기준이다.** 지속 시간·3초 규칙·복귀 시간은 서버 수신 시각이 아니라 `t_ms`·`start_ms`·`end_ms`로 계산한다. 그래야 네트워크 지연이 판정에 섞이지 않는다.
- **양**: 1건 약 2KB, 1명 1시간 약 10~15MB. 저장은 MySQL이 아니라 HDFS로 간다.

## 안건 5: 실시간 계약 v1 확정

**답: 초안의 틀(토픽, 봉투, `session_id` 키, `ack`·`progress`·`decision`)은 그대로 두고 아래만 고쳐서 확정한다. DLQ 규칙 추가에 동의한다.**

### 고칠 곳

| # | 지금 초안 | 바꾼 뒤 |
|---|---|---|
| 1 | "랜드마크·좌표는 어떤 메시지에도 넣지 않는다" | "가입 때 좌표 수집에 동의한 사용자만 좌표를 보낸다" |
| 2 | `features` 본문 = 특징 변화량(입력 v2) | 좌표 프레임 묶음(안건 2 형식). 계약 버전을 올린다 |
| 3 | WebSocket `features.items` 1~30개 | 그대로 둔다. 평소 1개씩, 재연결 때 밀린 구간 재전송에 쓴다. Kafka에는 1개씩 나눠 넣는다 |
| 4 | `phase`: `running`, `rest`, `away` | `calibration` 추가 |
| 5 | `observation`: `valid`, `collapse_probability`, `deviation_type` | 판정하지 않은 이유 `invalid_reason`(`unmeasurable` / `head_turn` / `settling`) 추가 |
| 6 | (없음) | 처리 못 한 메시지는 `posture.dlq`로 넘기고 다음 메시지를 처리한다 |

### 새로 생기는 서버 단계

```
좌표 프레임 → [판정 가능 검사 → 특징값 계산 → 기준 대비 점수·유형 → 고개 돌림 → 복귀 대기] → 관측 → CEP
```

지금 앱의 `model/prototype/pose.ts`, `frontend/src/lib/returnSettle.ts`가 하는 일이다. 서버로 옮길 규칙:

| 규칙 | 지금 값 |
|---|---|
| 판정 가능 | 코·귀·어깨 visibility 0.65 이상, 화면 가장자리 2% 안쪽 |
| 특징값 | 머리 높이(코–어깨선), 좌우 치우침(**귀 중간점** − 어깨 중심), 어깨 기울기, 고개 돌림(코 − 귀 중간점). 모두 어깨 너비로 나눈다 |
| 점수 | `min(1, 0.7 × max(|Δ머리|/0.22, |Δ치우침|/0.2, |Δ기울기|/0.03))`. 임계값 0.7(사용자 설정 0.5~0.95) |
| 고개 돌림 | 기준 대비 돌림 변화가 0.15를 넘으면 판정하지 않는다 |
| 복귀 대기 | 판정 불가 뒤 3초, 고개 돌림 뒤 1초 동안 판정하지 않는다 |
| 좌우 | 사용자 본인 기준. 치우침 변화량이 양수면 `left_lean` |

FE가 이 규칙 문서와 합성 시험 데이터(입력 좌표 → 기대 결과)를 넘긴다. 서버 구현이 앱과 같은 결과를 내는지 이 데이터로 확인한다.

### 보정(기준 자세)

> 2026-10-11 다시 열림: 평균 좌표 18개로 서버가 특징값을 다시 계산하면 앱(프레임별 특징값의 평균)과 값이 조금 다르고, visibility가 없어 기준 품질을 알 수 없다.
> 계산 방식은 [규칙 문서](server-rule-spec.md) 3장에서 정한다. 아래는 회의 당시 회신이다.

- **앱이 보정 동안의 좌표 9개 × x·y 평균 18개를 계산해 입구 API로 보낸다**(V2.1 `baseline_posture`). 평균은 판정이 아니라 정보 요약이다.
  함께 보내는 값: `calibration_uuid`, `calibration_sec`(3.0), `sample_count`. 0~1 밖 좌표가 있으면 앱이 보정 실패로 처리한다.
- 보정 프레임 원본은 재처리용으로 `phase: "calibration"`을 붙여 Kafka→HDFS에 보낸다. 판정에는 쓰지 않는다.
- 서버는 판정할 때 기준 좌표를 DB/Redis에서 읽어 특징값을 계산한다. Kafka 보정 처리(D-35)는 필요 없다.
- `baseline_id`는 지금처럼 앱이 보정마다 새 UUID로 만들고, 서버는 이 ID로 기준값을 찾는다. 재보정하면 새 ID로 다시 보낸다.

### 유의사항

- **화면 반응이 늦어진다.** 화면 상태가 서버 결과로만 바뀌므로 0.5초 묶음에 처리 시간이 더해져 약 0.5~1초 늦게 반응한다. 판정이 3초 지속 기준이라 큰 문제는 없다.
- **네트워크가 끊기면 화면 판정이 멈춘다.** 앱은 "연결이 끊겼어요"를 화면을 막지 않게 띄우고 재연결 뒤 밀린 구간을 재전송한다.
  2026-10-11: 앱 판정을 없애므로 로컬 미리보기 판정은 하지 않는다. 카메라 화면·관절 표시는 계속 보인다.
- **동의**: 2026-10-11 가입 때 동의를 받는 것으로 정했다(동의문은 FE). 동의 저장 위치(`user_consent`)는 DB에 요청 중이다.
- `invalid_reason`이 없으면 앱이 "고개를 돌린 동안은 판정하지 않아요", "자세를 다시 잡는 중이에요" 같은 안내를 띄울 수 없다.

## 안건 6: 판정 불가 처리 세부

| # | 질문 | FE 답 | 비고 |
|---|---|---|---|
| ① | 중복 구간 제거 | **필수로 동의** | 앱은 재연결 때 같은 `sequence`를 다시 보낸다. 같은 세션의 같은 순번은 한 번만 반영한다 |
| ② | 사건 지속 시간 기록 | **실제 경과는 필수, 붕괴로 본 시간은 ML이 결정** | 앱 화면(`SessionEvents.tsx`)은 실제 경과 시간만 쓴다. 붕괴로 본 시간(`deviation_sec`)은 분석용이라 FE에는 필요 없다 |
| ③ | 정상 1구간이면 붕괴 누적 0 | **0으로 동의** | 지금 앱 판정(`machine.ts`)도 정상 1번이면 0으로 돌린다 |
| ④ | LSTM 후보 기준 | ML 담당 | |
| ⑤ | `poor` 30초 서버 안전장치 | **필요 없어진다.** 3초 규칙을 서버가 직접 한다 | 아래 참고 |
| ⑥ | 카메라 끊김 때 전송 | **보낸다.** 카메라 끊김 `away`, 일시정지 `rest` | 아래 참고 |

### ⑤ "판정 불가 3초 연속 → 측정 멈춤"은 서버 규칙

앱이 판정 가능 여부를 판단하지 않으므로 이 규칙도 서버로 옮긴다. 앱이 판정 불가 때문에 `rest`를 보내는 일은 없어지고(`rest`는 사용자 일시정지 전용), 30초 안전장치도 필요 없다.

| 상황 | 서버 처리 |
|---|---|
| 판정 불가 3초 미만 | 붕괴·복귀 시계를 **그 자리에 멈춘다.** 0으로 돌리지 않고 진행 중인 사건도 닫지 않는다 |
| 판정 불가 3초 연속 | 측정을 멈추고 진행 중인 사건을 "끊김"으로 닫는다. 시계는 0. 앱에 멈춤 상태를 알린다 |
| 멈춘 뒤 0.5초 연속 판정 가능 | 자동 재개하고 새로 센다 |

**꼭 지킬 점**

- **고개 돌림과 복귀 대기 구간은 3초 연속에 세지 않는다.** 옆 모니터를 3초 넘게 보는 건 정상 행동이라, 세면 측정이 계속 멈춘다.
- 복귀 대기를 세면 손이 어깨를 잠깐 가린 것만으로 대기 3초가 더해져 측정이 멈춘다.
- 이 구간들은 붕괴 시간에도 복귀 시간에도 넣지 않는다.

### ⑥ 앱이 보내는 `away`와 `rest`

- **카메라 입력이 1.5초 넘게 끊기면** 앱이 그 사이 구간을 `phase: "away"`, `frames: []`로 보낸다. DB 제외 사유 `MISSING`.
- **사용자가 일시정지를 누르면** `phase: "rest"`, `frames: []`로 보낸다. DB 제외 사유 `PAUSE`.
- 이건 판단이 아니라 사실이라 앱이 알린다. 메시지가 안 오는 것만으로는 서버가 네트워크 끊김과 구별할 수 없다.
- 서버는 `away`·`rest`를 제외 구간으로 보고 진행 중인 사건을 "끊김"으로 닫는다.
- 다시 시작하면 `running`으로 돌아간다. 카메라 끊김 뒤에는 지금처럼 사용자가 직접 재개한다.

## 서버 부담: 이 결정으로 늘어나는 것

판정을 서버로 모으면서 아래 부담이 새로 생긴다. 회의에서 담당과 일정을 함께 정해야 한다.

### 처리량·저장량 (동시 50명, 하루 8시간 기준 추정)

| 항목 | 지금 (특징값 전송) | 바뀐 뒤 (좌표 전송) |
|---|---|---|
| 메시지 수 | 1명당 0.5초에 1건 | 같다 |
| 메시지 크기 | 수백 바이트 | 약 2KB (약 5~10배) |
| Kafka 유입량 | 약 수십 KB/s | 약 200KB/s |
| 서버 계산 | 0.5초당 점수 1번 | 프레임마다 검사·특징값·고개 돌림 → 초당 약 800프레임 (계산 자체는 가볍다) |
| 저장 | MySQL에 결과만 | HDFS에 좌표 약 5GB/일 추가. MySQL은 결과만이라 같다 |

계산과 전송은 감당할 수 있는 수준이다. 실제 부담은 아래 **구현·운영 쪽**이다.

### 구현·운영 부담

1. **새 처리 단계 구현.** 판정 가능 검사, 특징값, 점수, 고개 돌림, 복귀 대기를 서버(추론 서비스 Python 권장)에 새로 만든다. 앱 규칙과 결과가 같은지 합성 시험 데이터로 맞춰야 한다.
2. **세션별 상태 보관.** 기준값, 복귀 대기 타이머, 판정 불가 연속 시간, 직전 프레임을 세션마다 들고 있어야 한다. 서버를 재시작하거나 다른 인스턴스로 넘어가도 이어져야 하므로 Redis 등에 저장해야 한다.
3. **보정 처리.** 기준값 저장(입구 API)과 판정 때 기준 좌표 조회가 서버 일이 된다. 평균 계산은 앱이 한다.
4. **3초 판정 불가 규칙과 자동 재개.** 지금 앱이 맡기로 한 규칙이 서버로 온다(안건 6 ⑤).
5. **화면 안내의 근거 제공.** `invalid_reason`을 채워서 앱에 돌려줘야 한다.
6. **HDFS 적재와 보존.** 좌표 저장, 동의 철회 시 삭제, 보존 기간 만료 삭제가 필요하다.
7. **규칙 유지보수.** 임계값(0.15, 0.65, 0.22/0.2/0.03 등)을 바꿀 때 서버에서 바꾸고 재처리한다. 대신 좌표가 남아 있어 과거 데이터에 새 규칙을 다시 적용할 수 있다. 이것이 이 결정의 목적이다.
8. **장애 영향 확대.** 서버가 멈추면 화면 판정도 멈춘다. 지금은 앱이 혼자 판정할 수 있다.

## FE가 회의 뒤 할 일

1. 0.5초 좌표 묶음 전송: 순번, `ack` 기반 재전송, 재연결
2. 기준 좌표 평균 18개 전송(입구 API), 보정 프레임(`calibration`)·`away`·`rest` 전송
3. 서버 결과(`observation`, `progress`, `decision`)로 화면·알림 구동
4. 가입 동의 화면, 설정의 철회 토글, 측정 화면의 "좌표 미전송" 문구 수정
5. 서버로 넘길 규칙 문서와 합성 시험 데이터 작성
6. FE 연동 시험(T-13) 일정 잡기
