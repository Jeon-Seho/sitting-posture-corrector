# 소셜 로그인 쉽게 이해하기 (BE·DB 담당용)

> 2026-11-11 작성. 자세한 표·환경변수는 [인계 문서](social-login-password-reset-handoff.md), 정확한 API는 [계약](../../contracts/accounts.v2.md)을 본다. 이 문서는 "왜 이렇게 했는지"를 쉬운 말로 설명한다.

## 1. 한 줄 요약

로그인 화면에 **Discord · 카카오 · Google · GitHub** 둥근 버튼 4개를 둔다. 지금은 **Discord만 실제로 동작**하고, 나머지 셋은 흐리게 보이며 누르면 "준비 중" 안내가 뜬다. 서버와 DB는 네 개를 모두 받을 수 있게 미리 만들어 두었다. 그래서 나중에 제공자를 하나 더 켤 때는 **작은 연결 파일 하나와 설정값만** 더하면 된다.

## 2. 소셜 로그인이 뭐예요? (비유)

놀이공원 입구를 떠올리면 된다.

- **비밀번호 로그인:** 우리 매표소에서 직접 표를 확인한다.
- **소셜 로그인:** 손님이 "Discord 회원증 있어요"라고 하면, 우리는 그 회원증이 진짜인지 **Discord 창구에 직접 물어본다.** Discord가 "이 사람은 우리 회원 12345번이 맞아요"라고 답하면 들여보낸다.

우리는 Discord 비밀번호를 **절대 보지 않는다.** Discord가 알려 준 "회원 번호(12345)"만 우리 계정에 붙여 둔다.

## 3. 실제로 일어나는 일 (5단계)

1. 사용자가 Discord 버튼을 누른다 → 앱이 서버에 "Discord 로그인 시작할게요"라고 말한다.
2. 서버가 **일회용 확인표**(state·PKCE)를 만들어 서버 메모리에 10분간 보관하고, Discord 동의 화면 주소를 돌려준다.
3. 사용자가 Discord에서 "허락"을 누르면, Discord가 사용자를 우리 서버의 **callback 주소**로 돌려보낸다. 이때 일회용 코드가 함께 온다.
4. 서버가 확인표가 맞는지 보고, 코드를 Discord에 보내 "이 사람 누구예요?"라고 묻는다 → **회원 번호 + 확인된 이메일**을 받는다.
5. 회원 번호로 `social_identity` 표를 찾는다.
   - 있으면 → 그 계정으로 로그인한다.
   - 없으면 → 약관·프로필을 받는 가입 화면으로 보낸다.

주소창에는 로그인 토큰을 싣지 않는다. 앱은 원래 쓰던 refresh 쿠키 방식으로 로그인 상태를 받는다.

## 4. 왜 같은 이메일이어도 자동으로 합치지 않아요?

누군가 Discord 쪽 이메일을 남의 주소로 바꿔 둘 수 있다면, 자동으로 합칠 경우 **남의 PoseGood 계정에 들어가게 된다.** 그래서 같은 이메일 계정이 이미 있으면 `link-required` 상태로 멈춘다. 이 경우 사용자가 비밀번호로 먼저 로그인한 뒤, 설정에서 **직접** Discord를 연결해야 한다.

## 5. 서버 구조: "공통 길 + 제공자별 어댑터"

콘센트와 여행용 어댑터를 떠올리면 된다. 콘센트(공통 길)는 하나이고, 나라(제공자)마다 어댑터만 바꿔 끼운다.

| 부분 | 파일 | 하는 일 |
| --- | --- | --- |
| 공통 길(주소) | `SocialController` | `/v2/auth/social/{provider}/login · link · callback`, `DELETE /{provider}` |
| 공통 규칙 | `SocialLoginService` | 확인표 검사, 자동 연결 금지, 가입·연결·해제, 마지막 로그인 수단 보호 |
| 제공자 목록 | `SocialProviders` | 화면 순서 `discord, kakao, google, github`. 어댑터가 있고 설정이 켜진 것만 사용 |
| 어댑터 | `SocialProviderClient` (인터페이스), `DiscordClient` (구현) | 제공자마다 다른 딱 두 가지: ① 동의 화면 주소 만들기 ② 코드를 "회원 번호 + 확인된 이메일"로 바꾸기 |

### BE 담당: 새 제공자(예: Google)를 켜는 방법

1. `GoogleClient implements SocialProviderClient`를 `@Component`로 만든다. `id()`는 `"google"`이다.
2. `application.properties`에 `posegood.auth.google.client-id / client-secret / redirect-uri`를 추가한다. 값은 환경변수로만 넣는다.
3. `SchemaVerifier`의 "소셜이 켜졌는지" 판단에 그 제공자 설정을 더한다. 지금은 Discord client-id만 본다.
4. 앱 쪽 `discordAuthorizeUrl`처럼, 돌아온 동의 화면 주소가 그 제공자 도메인인지 검사하는 함수를 추가한다.
5. 단위 시험에 그 제공자의 사용자 응답 해석을 추가한다.

경로, 공통 규칙, DB는 **고칠 필요가 없다.**

제공자마다 미리 알아 둘 점:

- **카카오:** 이메일을 받으려면 카카오 비즈 앱 전환·검수가 필요할 수 있다. 이메일이 없으면 지금 규칙상 `email-required`로 가입이 막힌다. 켜기 전에 정책을 정해야 한다.
- **Google:** `email_verified=true`일 때만 이메일을 쓴다. 회원 번호는 `sub` 값이다.
- **GitHub:** 이메일이 비공개일 수 있다. `/user/emails`에서 `verified=true`이고 `primary`인 주소만 쓴다.

## 6. DB 담당: 할 일

표 두 개를 만든다(제안 V2.7). SQL 원문은 [인계 문서](social-login-password-reset-handoff.md)에 있다.

1. **`social_identity`** — "이 PoseGood 계정 = 저 제공자의 몇 번 회원" 연결표.
   - 같은 제공자의 같은 회원은 **한 계정에만** 붙는다(UNIQUE provider+subject).
   - 한 계정은 제공자마다 **하나만** 붙는다(UNIQUE account+provider).
   - `provider` 허용 목록은 이번에 **네 개 모두**(`DISCORD, KAKAO, GOOGLE, GITHUB`) 넣는다. 그래서 제공자를 켤 때마다 마이그레이션을 다시 할 필요가 없다.
   - 이메일·이름·토큰은 저장하지 않는다. 회원 번호만 저장한다.
2. **`password_reset_token`** — 비밀번호 재설정 링크의 "해시값"만 저장한다(아래 7절).

표가 없어도 서버는 켜진다. 기능이 꺼져 있으면 표를 읽지 않기 때문이다. 순서는 **표 적용 → 환경변수 → 기능 켜기**다. 되돌릴 때는 반대로 기능을 먼저 끄고 표를 지운다.

## 7. 덤: 비밀번호 찾기는 왜 링크예요?

비밀번호를 메일로 보내면, 메일함을 누가 엿보는 순간 그대로 들킨다. 임시 비밀번호도 메일에 평문으로 남는 것은 마찬가지다. 그래서 **30분짜리 일회용 링크**를 보내고, 사용자가 새 비밀번호를 직접 정하게 한다. DB에는 링크 원문이 아니라 **해시값**만 저장하므로, DB가 새어도 링크를 다시 만들 수 없다. 비밀번호를 바꾸면 다른 기기의 로그인도 모두 끊는다.
