# 소셜 로그인 쉽게 이해하기 (BE·DB 담당용)

> 2026-11-16 갱신. 기존 계정에 Discord를 연결하는 과정을 쉽게 설명합니다. 이메일 인증·비밀번호 찾기까지 한 번에 보려면 [쉽게 읽는 인수인계](email-account-handoff.md)를 먼저 읽어 주세요. 표·설정은 [기술 인계](social-login-password-reset-handoff.md), 정확한 API는 [계약](../../contracts/accounts.v2.md)에 있습니다.

## 1. 한 줄 요약

**기존 계정에 Discord를 연결하면 계정 하나에 로그인 방법이 두 개가 됩니다.**
이메일로 들어가든 Discord로 들어가든 같은 계정과 자세 기록을 사용해요.

로그인 화면에는 Discord·카카오·Google·GitHub 버튼이 있어요. 현재 서버 연결 코드는 Discord에 준비돼 있고, 카카오·Google·GitHub는 준비 중 안내를 보여 줍니다. Discord도 운영 설정을 켜야 사용할 수 있으며, 이번 작업에서 실제 외부 인증까지 확인한 것은 아닙니다.

## 2. 소셜 로그인이 뭐예요? (비유)

놀이공원 입구를 떠올리면 된다.

- **비밀번호 로그인:** 우리 매표소에서 직접 표를 확인한다.
- **소셜 로그인:** 손님이 "Discord 회원증 있어요"라고 하면, 우리는 그 회원증이 진짜인지 **Discord 창구에 직접 물어본다.** Discord가 "이 사람은 우리 회원 12345번이 맞아요"라고 답하면 들여보낸다.

우리는 Discord 비밀번호를 **절대 보지 않는다.** Discord가 알려 준 "회원 번호(12345)"만 우리 계정에 붙여 둔다.

## 3. 실제로 일어나는 일 (5단계)

1. 사용자가 Discord 버튼을 누른다 → 앱이 서버에 "Discord 로그인 시작할게요"라고 말한다.
2. 서버가 **일회용 확인표**(state·PKCE)를 만들어 서버 메모리에 10분간 보관하고, Discord 동의 화면 주소를 돌려준다.
3. 사용자가 Discord에서 "허락"을 누르면, Discord가 사용자를 우리 서버의 **callback 주소**로 돌려보낸다. 이때 일회용 코드가 함께 온다.
4. 서버가 확인표가 맞는지 보고, 코드를 Discord에 보내 "이 사람 누구예요?"라고 묻는다 → **회원 번호 + 확인된 이메일**을 받는다.
5. 회원 번호로 `social_identity` 표를 찾는다.
   - 있으면 → 그 계정으로 로그인한다.
   - 연결은 없지만 같은 이메일의 기존 계정이 있으면 → 기존 계정 확인과 연결 승인 화면으로 보내요.
   - 연결도 같은 이메일의 기존 계정도 없으면 → 약관·프로필을 받는 새 가입 화면으로 보내요.

주소창에는 로그인 토큰을 싣지 않는다. 앱은 원래 쓰던 refresh 쿠키 방식으로 로그인 상태를 받는다.

## 4. 왜 같은 이메일이어도 자동으로 합치지 않아요?

이메일이 같다는 사실만으로 기존 계정의 주인이라고 확정하지 않아요.
다른 로그인 방법을 붙이면 앞으로 그 방법으로 기존 기록을 열 수 있기 때문에, 계정의 주인이 직접 허락하는 단계가 필요합니다.

1. “이미 가입된 계정이 있어요”라고 알려 줘요.
2. 기존 PoseGood 계정의 비밀번호를 확인해요.
3. “Discord 계정을 연결할까요?”라고 한 번 더 물어요.
4. 사용자가 **연결 승인하고 로그인**을 누르면 연결하고 로그인해요.

비밀번호 확인을 통과했다고 바로 연결하는 것은 아니에요. 마지막 승인 버튼이 있어야 합니다.
비밀번호를 잊었다면 확인 화면에서 **비밀번호 찾기**를 이용할 수 있어요.

### 이메일이 다를 때는 어떻게 하나요?

기존 PoseGood 계정으로 로그인한 뒤 **프로필 설정에서 Discord 연결**을 시작하면 돼요.
현재 로그인한 계정에 Discord 회원 번호를 붙이므로 두 이메일이 같을 필요는 없어요.
기존 가입 이메일은 그대로 두고, Discord 이메일은 연결 표에 저장하지 않습니다.

기존 계정으로 로그인하지 않고 다른 이메일의 Discord로 바로 시작하면 새 가입이 안내될 수 있어요.
서버는 두 계정이 같은 사람의 것인지 알 수 없기 때문입니다. 이미 따로 만든 계정을 자동으로 합치는 기능은 없어요.

## 5. 서버 구조: "공통 길 + 제공자별 어댑터"

콘센트와 여행용 어댑터를 떠올리면 된다. 콘센트(공통 길)는 하나이고, 나라(제공자)마다 어댑터만 바꿔 끼운다.

| 부분 | 파일 | 하는 일 |
| --- | --- | --- |
| 공통 길(주소) | `SocialController` | `/auth/social/{provider}/login · link · callback`, `DELETE /{provider}` |
| 공통 규칙 | `SocialLoginService` | 확인표 검사, 자동 연결 금지, 가입·연결·해제, 마지막 로그인 수단 보호 |
| 제공자 목록 | `SocialProviders` | 화면 순서 `discord, kakao, google, github`. 어댑터가 있고 설정이 켜진 것만 사용 |
| 어댑터 | `SocialProviderClient` (인터페이스), `DiscordClient` (구현) | 제공자마다 다른 딱 두 가지: ① 동의 화면 주소 만들기 ② 코드를 "회원 번호 + 확인된 이메일"로 바꾸기 |

### BE 담당: 새 제공자(예: Google)를 켜는 방법

1. `GoogleClient implements SocialProviderClient`를 `@Component`로 만든다. `id()`는 `"google"`이다.
2. `application.properties`에 `posegood.auth.google.client-id / client-secret / redirect-uri`를 추가한다. 값은 환경변수로만 넣는다.
3. `SchemaVerifier`의 "소셜이 켜졌는지" 판단에 그 제공자 설정을 더한다. 지금은 Discord client-id만 본다.
4. 앱 쪽 `discordAuthorizeUrl`처럼, 돌아온 동의 화면 주소가 그 제공자 도메인인지 검사하는 함수를 추가한다.
5. 단위 시험에 그 제공자의 사용자 응답 해석을 추가한다.

공통 경로·연결 규칙과 기존 제공자 목록은 재사용할 수 있어요. 제공자별 정책 차이와 기존 계정 연결·가입·해제 시험도 함께 확인해 주세요.

제공자마다 미리 알아 둘 점:

- **카카오:** 이메일을 받으려면 카카오 비즈 앱 전환·검수가 필요할 수 있다. 이메일이 없으면 지금 규칙상 `email-required`로 가입이 막힌다. 켜기 전에 정책을 정해야 한다.
- **Google:** `email_verified=true`일 때만 이메일을 쓴다. 회원 번호는 `sub` 값이다.
- **GitHub:** 이메일이 비공개일 수 있다. `/user/emails`에서 `verified=true`이고 `primary`인 주소만 쓴다.

## 6. DB 담당: 할 일

**기존 계정 행은 유지하고 연결 행을 추가합니다.** 예를 들어 PoseGood 계정 42번에 Discord 회원 12345번을 붙인다면 다음과 같아요.

| 표 | 연결 후 모습 |
| --- | --- |
| `user_account` | 기존 PoseGood 계정 42번을 그대로 유지 |
| `social_identity` | 계정 42번과 Discord 회원 12345번을 연결하는 행 1개 추가 |

연결 표의 `user_account_id`가 계정 표의 번호를 가리켜요. 이것이 외래키(FK)입니다.
다음 Discord 로그인에서는 **제공자 이름 + Discord 고유 회원 번호**로 연결 행을 찾고, 그 행이 가리키는 계정으로 들어갑니다.

필요한 두 표는 DB V2.7에 정의돼 있어요. 운영 DB에 적용됐는지 확인해 주세요. SQL과 적용 안내는 [기술 인계](social-login-password-reset-handoff.md)에 있습니다.

1. **`social_identity`** — "이 PoseGood 계정 = 저 제공자의 몇 번 회원" 연결표.
   - 같은 제공자의 같은 회원은 **한 계정에만** 붙는다(UNIQUE provider+subject).
   - 한 계정은 제공자마다 **하나만** 붙는다(UNIQUE account+provider).
   - `provider` 허용 목록은 이번에 **네 개 모두**(`DISCORD, KAKAO, GOOGLE, GITHUB`) 넣는다. 그래서 제공자를 켤 때마다 마이그레이션을 다시 할 필요가 없다.
   - 이메일·이름·토큰은 저장하지 않는다. 회원 번호만 저장한다.
2. **`password_reset_token`** — 비밀번호 재설정 링크의 "해시값"만 저장한다(아래 7절).

표가 없어도 서버는 켜진다. 기능이 꺼져 있으면 표를 읽지 않기 때문이다. 순서는 **표 적용 → 환경변수 → 기능 켜기**다. 되돌릴 때는 반대로 기능을 먼저 끄고 표를 지운다.

## 7. 덤: 비밀번호 찾기는 왜 링크예요?

비밀번호를 메일로 보내면, 메일함을 누가 엿보는 순간 그대로 들킨다. 임시 비밀번호도 메일에 평문으로 남는 것은 마찬가지다. 그래서 **30분짜리 일회용 링크**를 보내고, 사용자가 새 비밀번호를 직접 정하게 한다. DB에는 링크 원문 대신 **대조용 지문값(해시)**을 저장해요. 사용자가 받은 링크의 지문이 저장된 것과 맞는지 확인하는 방식입니다.
새 비밀번호는 두 번 입력하고, 기존 비밀번호와 같은 값이면 다시 정하도록 안내해요.
재설정하면 로그인을 계속 갱신하는 권한과 열려 있는 측정 연결을 끊어요. 이미 발급된 짧은 로그인 권한은 만료까지 남기 때문에 모든 요청이 즉시 차단되는 것은 아닙니다.
