# 실제 서버 연결을 위한 부서별 지침서

> **이전 작업 보존본:** 이 문서의 구현·검증 수치·미완료 항목은 6a2f765 기준입니다. 현재 JWT 통합 상태와 실행 지침은 [2026-10-29 인계서](frontend-jwt-handoff-2026-10-29.md)를 따릅니다. 아래 과거 결과를 현재 브랜치의 검증 결과로 해석하지 않습니다. 아래 `check-browser` 통과 요구는 도구 삭제로 폐기했으며, 현재 기본 검사와 필요한 수동 서버 점검은 [품질 기준](../quality.md)을 따릅니다.

기준일: 2026-10-27. **로컬 임시 서버 연결 시험 완료와 팀 운영 서버 연결 완료는 다르다.**
현재 작업본은 이전 인증 계약 기반이다. 새 서버와 연결하려면 프론트 인증·저장 설계를 고치고 서버 접속 환경을 맞춰야 한다.
상세 문제·코드 근거·완료 기준은 [설계 검토 R1~R9](../audits/2026-10-27-frontend-design-review.md)를 따른다.

## 10/29 재부팅 후 재확인

이 항목이 아래 10/27 접속 실패 이력을 갱신한다.

- `bdp@192.168.0.104` SSH 접속 성공. 서버에 web(127.0.0.1:8088), io-api(127.0.0.1:8090), io-inference, gateway가 실행 중이다.
- SSH 로컬 전달 `127.0.0.1:8088` → 서버 `127.0.0.1:8088`을 다시 열고 이 PC에서 확인했다.
- 화면 `/`: HTTP 200. `/api/health`: HTTP 200, `{"status":"ok","storage":"mysql"}`.
- `/api/v2/auth/me`: HTTP 401 UNAUTHENTICATED. 쿠키 없는 `POST /api/v2/auth/refresh`도 HTTP 401, login expired 응답.
  이는 로그인 API까지 통신된 증거이며 일반 계정 로그인 성공의 증거는 아니다.
- 공개 `https://api.posegood.site/health`와 `/api/v2/auth/me`는 여전히 HTTP 530 / Cloudflare 1033이다.
- 서버 설정·DB·계정을 변경하지 않았다. 앱의 최신 인증 구현 통합, 로그인·WS 측정·저장 검증은 아직 필요하다.
- 터널 실행 명령: `ssh -N -L 127.0.0.1:8088:127.0.0.1:8088 bdp@192.168.0.104`.
  이 터널은 SSH 프로세스가 종료되거나 PC를 재부팅하면 다시 열어야 한다.

## 10/27 후속 실측과 수정

- 최신 원격 develop은 `6e768a4`(PR #69)로 FE JWT 구현까지 합쳐졌다. 현재 작업본의 통합은 아직 하지 않았다.
- 공개 API `/health`와 `/api/v2/auth/me`는 다시 HTTP 530 / Cloudflare 1033을 반환했다.
- 사용자 확인 주소 `192.168.0.104`, 계정 `bdp`로 SSH 인증 및 로컬 8088 전달에 성공했다.
  하지만 원격 `127.0.0.1:8088`은 connection refused였다. 원격 `ss -ltn`에서 8088·8090 리스너가 없고,
  `docker ps`에는 api-server(8080), inference-service(8000), Kafka·Redis·HDFS·Spark만 있었다.
  즉 SSH 연결은 성공했으나 로그인용 web/io-api 연결은 실패했다. 실제 계정 로그인·WS·저장은 시험할 수 없었다.
- 서버 담당은 올바른 저장소/커밋·DB V2.6·JWT 설정을 확인한 뒤 web/io-api를 준비하고 8088 경로를 알려준다.
  현재 실행 중인 8080 처리 서비스를 계정 API 대신 쓰지 않는다. 서버 기동·설정 변경은 이번에 수행하지 않았다.
- 점검용 SSH 터널은 종료했다. 인증 비밀값은 파일·문서에 보관하지 않았다.
- 현재 프론트에서는 중간 측정/미저장 결과를 계정별 localStorage에 보관하도록 변경했다.
  기존 sessionStorage 자료는 검증 후 복사하고, 복사 성공 뒤 기존 키를 정리한다. 충돌·손상·저장 실패 때는 원본을 보존한다.
- 서버가 같은 결과 저장을 확인하면 재시도 자료와 같은 ID의 기존 표시용 사본을 지운다.
  실패하면 보존하고 같은 본문으로 재시도한다. 서버 기록 목록에 미저장 결과나 오래된 로컬 사본을 덮어쓰지 않는다.
- 시작/종료 시각은 수정 버전이 아니다. 시간 크기로 승자를 고르지 않고 서버 응답의 ID·결과 일치를 검증한다.
  과거 결과를 재시도해도 화면의 ‘오늘’을 과거 날짜로 바꾸지 않는다. 자정 갱신 정책은 별도 미결이다.
- 측정 중 로그아웃은 측정 화면으로 안내하고 중단한다. 종료·저장 확인 후 다시 로그아웃할 수 있다.
  결과 저장 중에도 로그아웃을 막는다. 강제 종료 후 자동 복구의 운영 계약과 JWT 통합은 별도다.

이하 표와 기존 검증 수치는 최초 인계 이력이다. 최신 진행은 [계획 0058](../plans/completed/0058-frontend-durable-result-handoff.md)을 확인한다.

후속 수정 검증: 프론트 412개·타입/빌드, 브라우저 36개, 문서 검사 통과.
브라우저는 현재 작업본의 이전 인증 서버로 시험했으며 최신 JWT 서버·운영 연결의 증거는 아니다.

## 3. 프론트 담당

1. 최신 develop과 `feature/frontend-auth-token`의 인증 구현을 대조한다. 현재 UI·가계정·PiP·기록 개선은 보존하면서 인증 모듈을 하나로 통합한다(R1).
2. REST에 Bearer와 계정 식별자, WS hello에 access token을 붙인다. refresh 쿠키용 credentials는 유지한다.
3. 토큰 갱신 중복, 늦은 응답, 로그아웃 후 갱신, 다른 탭 계정 변경을 시험한다. 토큰은 영속 브라우저 저장소에 보관하지 않는다.
4. R2~R5의 영속 복구·서버 정본 우선·종료 절차·서버 날짜를 구현한다. 미확인 결과는 서버 저장 완료와 구분한다.
5. R6의 앱 접속 방식을 결정하고 실제 EXE에서 검증한다. R7~R9의 탈퇴 정리·과거 통계 표시·가계정 자료 경계를 정리한다.
6. `check-frontend` 및 최신 서버의 `check-browser`를 통과시킨다. 기존 성공 수치를 새 계약 검증으로 재사용하지 않는다.

현재 작업본의 서버 모드 선택은 `VITE_SERVER_ACCOUNTS=true`다. 이 값만 바꾸어 운영 배포하지 않는다.

## 4. 백엔드 담당

1. 실제 시험·운영 API의 커밋과 지원 계약을 공유한다. ‘REST v2’만으로 인증 호환 여부를 판단하지 않는다.
2. JWT 응답·refresh·로그아웃·비밀번호 변경·탈퇴·WS hello를 FE와 같은 계약으로 확인한다.
   만료된 access token, 철회된 refresh token, 계정 전환은 서로 구분해 시험한다.
3. B1 같은 registration_id 재시도, S1 같은 세션 ID 재시도, R1 `{today, records}`의 날짜·조회 범위·정렬을 확인한다.
4. 앱 종료/네트워크 유실 뒤 서버 세션 종료와 복구 조회 방법을 FE에 전달한다. 미확인 종료 자료의 재제출을 일반 완료 기록으로 받는지 추측하지 말고 계약으로 확정한다.
5. T1 과거 일별 통계·R1b 상세 조회·이메일 인증/비밀번호 재설정은 별도 후속으로 상태와 응답 예제를 공유한다.
6. 자정 세션 처리, 동의 문서 버전, 측정불가 5분 종료 활성화 여부를 FE·기획과 합의한다.

완료 증거: API SHA, 최신 계약 링크, 합성 계정 기반 REST/WS 결과, BE 검사 결과. CORS는 DevOps와 함께 실제 출처로 확인한다.

## 5. DB 담당

1. 실제 DB의 현재 버전을 확인한다. 새 서버 목표는 V2.6이다. V2.5라는 기존 인계 설명은 이전 시험 환경 기준이다.
2. 최신 develop의 `database/README.md`, `database/migrations/016_create_refresh_token.sql`,
   `database/schema/schema_V2_6.sql`을 기준으로 선행 마이그레이션과 적용 순서를 검토한다.
3. 기존 DB에는 전체 schema 파일을 덮어쓰지 않는다. 격리 시험 DB에서 백업·변경·복원과 기존 계정/세션/기록 보존을 먼저 확인한다.
4. refresh token 교체·철회·사용자 관계·제약과 API 기동 검사를 확인한다. API가 자동으로 테이블을 만든다고 가정하지 않는다.
5. 배포 담당에게 적용 버전·시각·성공/실패·복구 방법을 전달한다. 운영 적용 시점은 배포 담당과 조율한다.

완료 증거: 민감값 없는 마이그레이션 결과, 기존 데이터 보존 검사, 최신 API 기동 및 합성 인증 검사.

## 6. DevOps·배포 담당

1. Cloudflare 1033 원인을 서버에서 확인한다. cloudflared 연결 상태·로그·대상 서비스 주소를 점검하고,
   nginx까지 연결되는지 확인한다. 도메인 DNS만 정상이어도 터널이 연결된 것은 아니다.
2. 대상은 인증 경계인 nginx/io-api 경로다. 인증 없는 내부 처리 서비스 포트를 공개 API 대상으로 연결하지 않는다.
3. `/api/`를 API의 `/`로 전달하고 `/api/v2/realtime`의 WebSocket Upgrade·시간 제한을 확인한다.
4. 실제 배포 compose의 DB 초기화가 V2.6인지, JWT 비밀값(32바이트 이상)을 안전하게 주입하는지 확인한다.
   실행마다 바뀌는 임시 키를 운영에서 사용하지 않는다. 값 자체는 공유하지 않는다.
5. HTTPS에서 Secure refresh 쿠키와 선택한 앱 출처를 확인한다. `app.posegood.site` → `api.posegood.site`의
   credentials 요청과 Authorization·X-PoseGood-User-Id 헤더의 preflight를 허용한다. WS Origin 검사도 별도로 확인한다.
6. `tools/platform/io_api_smoke.py`·`ws_realtime_smoke.py`·DB 초기화 스크립트의 최신 JWT/V2.6 대응을 확인한다.
   참고 브랜치 `codex/repo-jwt-kafka-checkpoint`에 관련 변경이 있으므로 최신 기반과 중복·누락을 대조한다.
7. FE 배포는 원본 저장소 develop과 Vercel이 보는 포크 develop이 다를 수 있다. 실제 배포 SHA와 환경 변수를 확인한다.

완료 증거: 내부 API health, 외부 API 도달, CORS/쿠키/WS 시험, 배포 SHA, Compose 시험 및 복원 결과.
nginx `/health` 200만으로 DB/API 전체 정상이라고 보고하지 않는다.

## 7. 처리·ML 담당

1. 현재 경로가 API 내부 판정인지 Kafka 경유인지 실제 배포 설정·코드로 확인한다. 준비용 환경 변수가 있다는 것만으로 전환 완료로 보지 않는다.
2. 좌표·관측·사건·요약의 버전과 세션 ID/순번/시간 단위를 공유한다. 누락·지연·중복 때 정상 판정을 만들지 않는다.
3. FE/BE와 같은 합성 자료로 순서·휴식·측정 불가·지속 이탈·회복을 확인한다.
4. 학습된 LSTM 연결·실제 모델 성능은 별도 검증한다. 규칙 기반 시험 통과를 학습 모델 품질 증거로 쓰지 않는다.

완료 증거: 실제 사용 경로·버전, 합성 계약 시험, 지연/누락 처리 결과. 기본 인증 연결의 선행 조건과 모델 교체 후속 작업을 구분한다.

## 8. 기획·QA 담당

- 기획: 자정에 세션을 나누는지, 미저장 결과 보유 기간, 로그아웃 중 종료 실패 안내,
  동의 문구/버전, 데스크톱의 운영 화면 출처를 확정한다. 기존 동의를 새 버전으로 조용히 바꾸지 않는다.
- QA: 가입 → 로그인 → 자세 등록 → 측정/휴식/회복 → 종료 → 기록 → 새로고침을 확인한다.
- 예외: 토큰 만료·갱신 실패·계정 변경·API 재시작·소켓 유실·앱 강제 종료·저장 응답 유실·캐시 충돌·자정·과거 기록 재시도.
- 실제 장치: USB 카메라 분리·절전 복귀·장시간 사용·패키징 앱 재시작. 합성 카메라 결과와 별도로 기록한다.
- 가계정: admin/1234가 서버 권한을 만들지 않고, 일반 서버 계정 자료와 섞이지 않는지 확인한다.

## 9. 접속 방법

### 같은 서버의 화면을 SSH 터널로 보기

서버 담당자가 web/io-api를 준비한 후, 전달받은 SSH 계정·호스트로 실행한다.

```sh
ssh -N -L 8088:127.0.0.1:8088 <SSH계정>@<서버호스트>
```

브라우저는 `http://localhost:8088`로 접속한다. 화면·API가 같은 출처이며 localhost는 카메라 개발에 쓸 수 있다.
호스트·계정·실제 web 포트는 담당자가 제공한다. 과거 문서의 LAN IP를 현재 서버 주소로 확정하지 않는다.

### 현재 프론트 작업본을 로컬 API에 붙이기

**R1 해결 후 호환 API로 시험할 때** 사용한다. 아래 명령은 서버를 기동하지 않는다.
현재 Vite 프록시는 `127.0.0.1` HTTP 대상만 허용한다. 원격 API는 먼저 SSH로 로컬에 전달한다.

```powershell
cd C:\GoodPose\develop\frontend
$env:VITE_SERVER_ACCOUNTS = 'true'
$env:POSEGOOD_API_URL = 'http://127.0.0.1:8090'
$env:POSEGOOD_API_PREFIX = ''
Remove-Item Env:VITE_API_BASE_URL -ErrorAction SilentlyContinue
Remove-Item Env:VITE_REALTIME_URL -ErrorAction SilentlyContinue
npm run dev
```

8090은 API 직접 접속(`/v2/...`), nginx 8088에 프록시하면 API_PREFIX는 `/api`다.
Vite가 표시하는 로컬 화면 주소를 사용한다. 프록시는 서버를 대신 만들거나 인증 차이를 해결하지 않는다.

### 운영 웹

FE 빌드의 API 주소는 `VITE_API_BASE_URL=https://api.posegood.site`다.
현재 작업본은 추가로 `VITE_SERVER_ACCOUNTS=true`가 필요하다. WS 기본 주소는 `wss://api.posegood.site/api/v2/realtime`가 된다.
Vite 변수는 빌드 시 반영되므로 바꾸면 다시 빌드한다. R1~R6·터널·쿠키·출처 검증 전에는 이 설정으로 배포하지 않는다.
