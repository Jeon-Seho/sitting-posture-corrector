# 서버 영구 저장과 인증

- 상태: MySQL·이메일/비밀번호 선택과 계정·내구 저장 구현. 실제 MySQL·Compose 전체 게이트를 통과했다.
- 날짜: 2026-10-01
- 근거: 초기 서버 연결 설계 후 사용자가 DB 전체 구현과 MySQL·이메일/비밀번호를 선택했다.
- 결정: [ADR 0014](../decisions/0014-mysql-persistence-and-accounts.md), [Compose ADR 0015](../decisions/0015-compose-and-deployment.md)
- 계약: [계정·저장 API](../../contracts/accounts.v1.md), [특징/관측/사건](../../contracts/README.md)

## 구현 경계

기존 로컬·메모리 개발 모드는 유지한다. Compose에서는 영구 모드를 활성화하여 서버 인증 세션과
프로필·설정·기록·측정·처리 hash/관측·outbox·확인 요약을 MySQL에 저장한다.
인증한 서버 주체의 사용자 ID로 모든 조회·변경을 제한한다. 다른 사용자 측정은 404다.
브라우저 이름·body 사용자값·보조 사용자 헤더를 소유권의 근거로 사용하지 않는다.

비밀번호는 BCrypt로 저장하고 변경 시 모든 기존 인증을 철회한다. CSRF와 HttpOnly/SameSite cookie를 적용한다.
가입의 service-v1 보관 선택은 연구·학습 동의가 아니다. 원 영상·좌표·원본 변화량·원문 비밀번호를 DB에 넣지 않는다.
자세 등록의 연구 CSV는 사용자가 내려받는 별도 자료이며 서비스 계정에 자동 업로드하지 않는다.

## 처리와 복구

1. 계정별 MySQL 잠금으로 처리·설정·삭제 경쟁을 직렬화하고 소유권/동결 조건을 확인한다.
2. 요청 hash와 최초 추론 관측·outbox를 CEP 호출 전에 같은 짧은 트랜잭션으로 내구 저장한다.
3. 확인 관측을 고정 policy로 재생해 CEP 상태를 맞추고 원 미확인 관측을 전달한다.
4. CEP 응답의 식별자·policy·수용 범위를 검증하여 입력 완료·사건·snapshot을 함께 갱신한다.
5. 종료 시각도 먼저 저장하고 원 시각으로 재시도한다. 삭제된/종료된 CEP 엔진은 내구 cleanup으로 정리한다.

HTTP 대기 동안 DB 행 트랜잭션을 유지하지 않는다. 같은 sequence/같은 본문은 중복 집계하지 않으며
다른 본문은 충돌이다. API나 CEP 재시작으로 빈 세션을 과거 상태라고 표시하지 않는다.
재생한 사건 ID·통계가 DB 확인 범위와 다르면 복구 실패다. 과거 알림은 화면에 다시 전달하지 않는다.

추론 결과가 내구 저장되기 전 장애라면 재호출할 수 있다. 저장 후에는 원 관측을 사용한다.
현재 규칙 모델은 고정 식별자이며 학습 가중치 배포를 도입하면 식별자/자료 호환성 계약을 추가해야 한다.
개발 관측 10,000건 제한은 유지한다. 이는 운영 보존 기간이나 대규모 처리 성능을 확정한 값이 아니다.

## 프론트와 자료 삭제

계정 자료는 인증 후 서버에서 읽는다. 최종 기록을 localStorage에 복제하지 않는다.
재시도 본문·기준과 중단 자료는 UUID별 sessionStorage에만 두어 같은 탭·같은 사용자로 복구한다.
401/계정 변경은 카메라·UI·전송을 중단하고 다른 계정으로 미확인 본문을 넘기지 않는다.
탭을 닫은 뒤 활성 측정 검색·기기 간 기준 복구는 현재 제공하지 않는다.

서버 기록은 실제 확인했던 DB snapshot과 통계·사건이 같아야 한다. 날짜는 서버 측정 시각으로 정규화한다.
기록 삭제는 연결된 측정 자료를, 탈퇴는 사용자 전체와 인증 세션을 삭제하며 CEP 정리를 내구 저장한다.
다운로드 CSV·백업·미래 분석 저장소는 별도 삭제 경계다. 자동 보존 기간이나 법적 충족 여부는 추정하지 않는다.
