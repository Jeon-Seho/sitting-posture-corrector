## 배경

일별 통계(T1)는 Spark J2가 매일 00:00(KST)에 전날치를 만든다. 그래서 서버만 보면 오늘 측정은 다음 날에야 기록·달력의 합산에 들어간다.
10/14에는 「오늘 합산은 그리지 않는다」로 정했지만, 10/22 팀장이 오늘 화면도 채우기로 정했다.

## 결정

1. **오늘 목록·요약·달력의 오늘 칸·기간 그래프의 오늘 값은 앱이 이 기기에 모은 서버 결과로 계산한다.** 어제까지는 T1(통계)·R1·R1b(목록·상세)를 쓴다. 같은 날짜를 서버와 로컬에서 겹쳐 더하지 않는다. 오늘·어제는 KST로 나눈다.
2. 모으는 것은 측정 종료 때 서버가 확인한 요약·사건(R1과 같은 형식, `server.view` = SessionView)이다. 같은 세션 UUID는 덮어쓴다. 앱이 자세를 다시 판정하지 않는다(ADR 0021).
3. **이 복사는 기록 화면이 R1·T1을 읽게 된 뒤에도 남긴다.**
4. **로컬 기록은 계정과 상관없이 localStorage 키 하나(`posegood.v2.records`)에 둔다.** 계정별로 나누지 않는다.
5. 한 PC·한 브라우저에서 다른 계정으로 로그인하면 앞 계정의 오늘 기록이 함께 보이는 것은 **알려진 한계**로 팀 문서([연동 명세 4.5](../design/api-ws-spec.md#45-기록통계-r1r1br3t1-be-다음-주-범위) 「팀 참고」)에만 적는다. 사용자 안내 문구는 두지 않는다.

## 이유

- 오늘 측정이 다음 날에야 합산에 보이면 「오늘 얼마나 했는지」를 볼 곳이 없다. 서버에 오늘 통계를 따로 만들지 않고, 앱이 이미 받은 결과를 모으면 서버 변경 없이 채울 수 있다.
- 보통 PC 한 대를 한 사람이 쓴다. 키를 계정 ID별로 나누면 기록을 읽고 쓰는 곳(처음 불러오기, 측정 종료 저장, 탈퇴 때 지우기, 시험 데이터 준비, 저장값 검사)마다 로그인 응답의 계정 ID를 넘겨야 하고, 이미 저장된 기록을 어느 계정 것으로 볼지도 정해야 한다. 드문 경우를 위해 복잡해지는 것은 맞지 않다(10/25 FE).

## 결과

- 서버 DB·T1에는 영향이 없다. 섞여 보이는 것은 그 PC의 오늘 화면뿐이다.
- 기록·달력 화면을 서버로 바꿀 때(lellon0403, 계획 0023 3단계) 과거만 R1·T1로 바꾸고 오늘 집계 코드는 남긴다.
- 문제가 되면 키를 `posegood.v2.records.<user_id>`처럼 나누면 된다. `user_id`는 로그인(A3)·`me`(A4) 응답에 이미 있어 새로 저장할 것은 없다.

## 4. 자정을 넘긴 측정의 KST 날짜별 보관 (옛 ADR 0033, 2026-10-26)

> **서버가 KST 자정에 측정을 끊게 되면([ADR 0029](0029-midnight-cut-and-server-time.md)) 측정 하나는 하루 안에 있어 이 절은 필요 없어진다.** 그때 이 절과 코드(`useSessionPersistence.ts` `observe`의 날짜 나누기)를 지운다([계획 0059](../plans/active/0059-slim-realtime-results-over-api.md) 3번). 그 전까지와 끊기 전 기록에 쓰인다.

### 결정

한국 시간(Asia/Seoul, UTC+09:00) 00시를 날짜 경계로 사용한다. 자정에 카메라·판정 엔진·세션 ID·알림 누적을 초기화하지 않는다. 원 세션은 연속으로 유지하고 로컬 중간 기록과 종료 기록의 선택 필드 `days`에 각 날짜의 측정분을 따로 저장한다.

각 항목은 날짜·원 세션 기준 시작/끝 offset·전체/유효/정상 시간·그날 새로 확정된 사건 ID·그날의 사건별 알림 횟수를 보관한다. V3는 로컬 엔진이 없어 측정 중 받은 서버 누적 요약(`progress`의 `summary`)을 `ready.started_at`부터 나눈다(`useSessionPersistence.ts` `observe`). 원 서버 snapshot은 수정하지 않는다. API/DB의 세션을 새로 만들거나 서버 일별 배치의 규칙을 바꾼 것이 아니다.

기록·달력·기간 통계·오늘 요약은 같은 날짜별 투영을 사용한다. 사건이 자정을 넘으면 두 날짜의 상세에서 이어진 상태를 볼 수 있으나 사건 발생 수는 확정된 날짜에 한 번만 센다. 재알림은 실제 관측된 날짜에 센다. 전날부터 이어진 사건으로 그날의 발생 간격을 임의로 짧게 만들지 않는다.

자정 이후의 checkpoint에도 전날 측정분을 보관하고, 측정 도중 지난 날짜를 열면 완료된 날짜 부분을 볼 수 있다. 저장 실패 시 기존 저장 오류/재시도를 유지한다. 날짜별 합계와 원 세션 합계가 다르거나 날짜/구간이 손상된 자료는 읽기·쓰기를 거부한다. 저장용 원본을 표시용 투영으로 덮어쓰지 않는다.

### 호환성과 한계

`days`가 없는 과거 종료 기록은 원본을 유지한다. 과거에 합계만 저장된 기록은 날짜별 정상/측정 불가 시간을 복원할 수 없으므로 비율로 나누지 않는다. `days`가 없는 이전 중간 기록도 날짜별 값을 추정하지 않는다. 기존 키와 원 세션·서버 snapshot 형식은 유지한다.

실제 DB의 날짜별 영구 행/배치 처리는 앱의 로컬 보관과 별개다. 이 보관은 서버의 원 세션을 임의로 분할해 API에 제출하지 않는다.

### 검증

합성 자료로 자정·UTC offset·소수 tick·재시도/복구·정상/측정 불가·사건/재알림·전체 합계 보존을 검증한다. 실제 React와 Chrome의 합성 카메라로 자정 전 시작 → 자정 후 계속 → 종료 저장 → 두 날짜 조회 경로를 검증하며 실제 영상을 사용하지 않는다.
