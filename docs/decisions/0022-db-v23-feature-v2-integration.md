# ADR 0022: DB V2.3에 현재 특징 v2 프론트를 연결

- 상태: accepted
- 날짜: 2026-10-13
- 근거: 사용자의 백엔드·프론트·DB 정합성 구현 요청과 「현재 프론트가 사용하는 특징 v2 API를 유지하며 연동 완성」 선택
- 범위: feature/repo-backend-db-v2의 현재 계정 앱
- 앱 쪽 변경(2026-10-21, FE): 「특징 v2·실시간 v1 유지」와 「로컬 프로토타입의 15개 기준」은 서버를 먼저 돌려 보려고 섞은 임시 상태였다(BE 10/15).
  앱은 실시간 v2(`/v2/realtime` 좌표 구간, [ADR 0025](0025-app-always-measures-on-server.md))와 앱이 낸 관절 평균의 B1 등록(20개 이상, [ADR 0026](0026-baseline-average-by-app-b1.md))으로 바뀌었다. DB V2.3을 정본으로 둔 결정은 그대로다

## 결정

DB V2.3을 정본으로 두고 삭제된 컬럼을 백엔드에서 제거한다. DB 스키마를 되돌리거나 별도 저장 테이블을 추가하지 않는다.
계정·기준 등록·세션 생성은 [HTTP v2](../../contracts/accounts.v2.md)로 전환한다. 특징/관측 v2와 실시간/판정 v1은 유지한다.
[ADR 0021](0021-app-sends-information-server-judges.md)의 좌표 스트림·Kafka 전환은 이번 구현에 포함하지 않는다.

기준 등록을 측정과 분리한다. 완료 시각을 고정해 재시도하고 매번 새 기준 행을 추가한다. 세션은 원래 기준 FK를 보존한다.
계정 모드의 등록은 DB 요구대로 유효 좌표 표본 20개 이상을 기다린다. 기존 로컬 프로토타입의 15개 기준은 유지한다.
DB가 보관하는 평균 좌표를 기준 특징의 정본으로 사용한다. 등록 응답과 재조회에서 같은 계산을 적용하여
특징 평균과 좌표 평균의 비선형 차이 때문에 재로그인 전후 판정이 달라지는 것을 방지한다.
실제 영상 종횡비로 재구성하며 장치·해상도를 DB에 새로 저장하지 않는다. 카메라 구도가 바뀌면 다시 등록해야 한다.

현재 프론트 `alerts_on`은 DB의 세션 알림 원본 `sound_alert_enabled`에 대응시킨다. 기본값 false를 그대로 쓴다.
실제 음향 재생 허용은 브라우저 기기 상태다. 알림 시도는 설정과 관계없이 기록하며 전달 성공으로 주장하지 않는다.
가입 동의 5종과 선택 동의를 실제 행으로 저장하고 나이·직업을 nullable로 연결한다.

DB가 없앤 종료 원인·알림 전달 여부를 추정해 원래 값처럼 복원하지 않는다. 회복 시각과 종료 시각으로 사건을 재구성하며
v2의 저장된 기록 확인은 서버 종료·요약의 존재를 뜻한다. 재시작으로 잃은 관측 시간은 MISSING으로 제외한다.

## 검증과 한계

실제 MySQL V2.3·FastAPI·계정 브라우저로 가입→기준 등록→특징 판정→종료→기록을 검증한다.
`make check-browser`는 2026-10-14부터 develop과 같이 프론트 팀의 앱 시나리오(`tools/browser/scenarios.mjs`)를 실행한다.
API가 로그인 필수 v2라서 첫 서버 판정 세션에서 실패한다. 프론트 연결 전까지의 상태와 할 일은 [계획 0027](../plans/active/0027-frontend-backend-v2-connection.md)에 있다.
계정 UI 시나리오(`tools/browser/accounts.mjs`)는 `check-compose`에서만 실행한다. 기존 단위 테스트의 로컬 판정·복구·대화상자 검증은 유지한다.
진행 중 상태는 API 단일 인스턴스 메모리다. HDFS, Kafka, 학습 모델, 약관 개정 재동의 화면은 별도 작업이다.
