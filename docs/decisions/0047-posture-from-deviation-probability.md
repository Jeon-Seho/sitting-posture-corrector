# ADR 0047: 자세 모델의 이탈 확률을 서버가 좋음/나쁨으로 나눈다

- 상태: 채택 (BE 2026-10-30, 10/31 번호를 0045에서 0047로 옮기고 ML 2클래스 결정에 맞춤). ML 결정 [ADR 0045](0045-base-deviation-first.md)(첫 목표는 기준·이탈 2클래스)를 따르는 서비스 쪽 결정이다. ML 확인에 따라 바뀔 수 있다. 학습 모델은 아직 없고 서비스는 [ADR 0020](0020-single-api-decision-engine.md) 3절 규칙 점수를 쓴다.
- 관련: [ADR 0045](0045-base-deviation-first.md)(기준·이탈 2클래스 먼저, 스트레칭 보류), [ADR 0043](0043-base-deviation-stretch-collection.md)(기준·이탈·스트레칭 3클래스 — 다음 단계), [ADR 0038](0038-ml-rebuild-scope.md)·[ML 재설계 G4](../ml/rebuild-plan.md#출력-점수-3클래스-softmax-2026-10-29-사용자-결정), [ADR 0020](0020-single-api-decision-engine.md)(판정 엔진·특징·점수), [ADR 0021](0021-app-sends-information-server-judges.md)(판정 불가 신호), [계획 0084](../plans/active/0084-server-3s-frame-batch-inference.md)(프레임마다 판정, `observation` 4.0)

## 배경

- 지금 서비스(2026-10-31)는 학습 모델이 아니라 규칙 점수(`reference-feature-rule-v1`, ADR 0020 3절)를 쓴다. 추론 서버는 프레임마다 0~1 점수 하나를 `collapse_probability`로 내고, 서버가 `threshold`(기본 0.7)로 좋음/나쁨 두 가지로 나눈다. 스트레칭을 따로 구별하지 않는다.
- ML은 처음 학습 모델을 **기준·이탈 2클래스**로 만든다(ADR 0045, 10/31). `p(이탈)`을 서비스의 `collapse_probability`로 쓰고, n초 지속 판단은 서버 시간 규칙에 맡긴다. 스트레칭 클래스(ADR 0043의 3클래스)는 기준·이탈이 잘된다고 판단한 뒤 다시 넣는다.
- 계획 0084로 서버가 프레임마다 판정한다. 앱에 보내는 `observation` 4.0은 `posture`(`good`·`bad`·`null`)와 이탈 확률만 담는다.

## 결정

### 1. 서비스가 받는 모델 출력은 프레임마다 `p(이탈)` 하나다

- 추론 서버는 프레임마다 `collapse_probability = p(이탈)`을 낸다(추론 응답 v3). 규칙 점수·2클래스·나중의 3클래스 모두 이 값 하나로 받으므로 계약은 그대로다. 기준·스트레칭 확률은 계약에 넣지 않는다.
- 2클래스 단계의 모델은 스트레칭을 구별하지 못해 기지개·팔 뻗기가 이탈로 알림될 수 있다(ADR 0045 한계). 스트레칭을 다시 넣으면 스트레칭 확률이 높을 때 `p(이탈)`이 낮아져 알림이 나지 않는다(ML 재설계 G4).

### 2. `posture`는 서버가 `threshold`로 나눈 `good`·`bad`다

- `collapse_probability ≥ threshold`(계정 정책, 기본 0.7)이면 `bad`, 아니면 `good`. 비교는 API 판정 엔진(`engine/DecisionRules.java`)만 한다. 추론 서버는 확률만 낸다.
- 이름은 `good`·`bad`로 정했다(10/30 BE). ML 라벨과의 대응은 `bad` = 이탈 확률이 경계 이상, `good` = 그 밖(기준, 나중에는 스트레칭 포함)이다.
- 「좋음/나쁨」은 서비스 표시 이름이다. 뜻은 「알림을 보낼 자세인가」(ADR 0043 1번)이며 의학적 정상·바른 자세 판정이 아니다.

### 3. 판정 불가는 모델 클래스가 아니다

- 판정 불가는 모델 **앞**의 품질 검사에서 거른다: 앱의 `valid:false` 신호(ADR 0021 6절), 판정 가능 검사·고개 돌림(ADR 0020 3절, 계획 0084에서 추론 서버로 옮김), `rest`·`away` 구간.
- 걸린 프레임은 모델에 넣지 않고 `invalid_reason`(`unmeasurable`·`head_turn`)으로 보내며 판정 시간(`valid_ms`)에서 뺀다.
- 근거: 루트 불변 기준 「낮은 측정 품질은 `unmeasurable`이다」, ML 재설계 G4 「측정 불가는 확률로 표현하지 않는다」.

### 4. `threshold`는 학습 모델에 맞춰 다시 정한다

- 지금 0.7은 규칙 점수(ADR 0020 3절)의 값이고 보정된 확률이 아니다.
- 학습 모델을 붙일 때 ML이 학습·검증 참여자 자료만으로 다시 맞춘다. 시험 참여자 자료로 튜닝하지 않는다. 그 전까지 규칙 모델과 0.7을 그대로 쓴다.

### 5. 이탈 종류(`deviation_type`)는 학습 모델로 바꿀 때 뺀다 — 보류

- 학습 모델(2클래스·3클래스)은 이탈 종류를 내지 않는다(ADR 0043 2번).
- 실시간 `observation` 4.0에서는 이미 뺐다(계획 0084 9번). `decision`·`alert`·추론 응답 v3의 `deviation_type`은 학습 모델로 바꿀 때 **삭제한다**(B안, 10/30 BE). 시점이 정해지지 않아 **보류**하며, 그때까지 지금 규칙 모델의 종류를 그대로 보낸다. 함께 바꿀 곳은 계획 0084 「남은 질문」에 있다.

## 정하지 않은 것

- **짧은 가림 유지 규칙**(ML 재설계 「짧은 가림 유지 규칙」, BE 구현 요청): 얼굴만 판정 불가일 때 2초까지 직전 값을 유지하고 타이머를 멈추는 예외. BE 검토 중(10/30). 받으면 3절의 `head_turn` 처리와 `observation`의 판정 불가 표시가 바뀐다.
- **스트레칭 중 시간 규칙**: 타이머 정지·한도와 계약 표현. 스트레칭 판정을 다시 넣을 때 정한다(ADR 0045, ADR 0043 「남은 결정」).
- **입력**: 프레임 계약(`posture.frames.v1`, 9점 x·y)에는 팔·z가 없다. 스트레칭 구분(팔 좌표)이나 상대 z를 쓰려면 프레임 계약을 바꿔야 한다. ML 점검이 제안한 어깨폭 비율·어깨 중심 y는 추론 v3가 9점 x·y를 그대로 받으므로 계약 변경 없이 추론 서버에서 계산할 수 있다.

## 결과

- 계약 변경 없음: 추론 v3·`observation` 4.0이 이미 이 결정의 모양이다. DB 변경 없음(이탈 종류는 저장하지 않는다, T-36 `collapse_type` 보류).
- 학습 모델을 붙일 때 바꿀 문서: [제품 범위](../product-spec.md)의 후보 라벨 4종, [ADR 0020](0020-single-api-decision-engine.md) 3절 「유형」, [계약 안내](../../contracts/README.md)의 `deviation_type`, [backlog](../plans/backlog.md) 9행.

## 이력

- 2026-10-30: BE 제안(초안 번호 0043, 이진 출력·판정 불가 분리·라벨 합치기·`threshold` 재조정).
- 2026-10-30: develop에 ML ADR 0043(3클래스, 10/29 채택)이 들어와 번호를 0045로 옮기고 3클래스에 맞춰 고쳤다. 라벨 합치기 표는 ML이 동작 이름 라벨을 없애 뺐다. `posture` 이름 `good`·`bad` 확정(BE). 짧은 가림 규칙은 BE 검토 중.
- 2026-10-31: develop에 ML ADR 0045(기준·이탈 2클래스 먼저, 스트레칭 보류)가 들어와 번호가 겹쳐 0047로 옮겼다. 첫 학습 모델을 2클래스에 맞추고, 지금 서비스는 규칙 점수 하나를 good·bad로 나눈다는 점을 배경에 적었다. 결정 1~5는 그대로다.
