동작별로 파일당 3회, 합계 6회다. 라벨은 `guided_task_not_ground_truth`이며 실제 수행 시작·끝의 정답이 아니다.

## 다른 브랜치 문서의 변경

`develop`에는 `docs/ml`과 ML ADR(0032~0042)이 없다. 10/27 ADR 정리(32개→13개)는 FE·BE 기준이다.
ML에 영향을 주는 변경은 다음과 같다.

- 앱은 특징값을 계산하지 않는다(ADR 0021). 서비스 입력은 9점(MediaPipe 0,2,5,7,8,9,10,11,12) x·y·visibility 프레임이다. z는 없다.
- 서버 `FrameFeatures`가 머리-어깨 간격·좌우 치우침·어깨 기울기 3개(`legacy3`)를 계산해 `/v2/infer`에 보낸다.
  현재 어깨폭으로 나누므로 크기·화면 위치 변화는 지워진다. 판정 불가 프레임은 `p: null`이고 `calibration` phase는 빠졌다.
- 모델명·특징 버전은 내부 관리용이며 화면에 표시하지 않는다. 재현은 코드·설정 기록으로 구분한다.
- 서비스 추론은 여전히 무상태 규칙(`reference-feature-rule-v1`)이다. 세션 ID가 없어 시계열 모델을 바로 연결할 수 없다.

## 점검 방법

스크래치 스크립트로 프레임 특징 19개를 만들었다. `legacy3`, 2D 형태·배치(어깨폭 비율, 어깨 중심 y 등),
image z, world z·y의 상대값이다. `neutral`은 바퀴 안의 기준 대기, 나머지 네 클래스는 `hold` 구간이다.
복귀·이동 구간은 뺐다. 분류는 표준화 + Logistic Regression(B1 해당)이며 프레임 무작위 분할은 하지 않았다.

## 결과(집계)

### 시도별 재현성

각 시도의 유지 구간 중앙값에서 직전 기준 대기의 중앙값을 뺐다. 6회 중 같은 방향이 나온 횟수와 평균이다.

| 동작 | 2D 주 신호 | z 신호 |
| --- | --- | --- |
| 머리 내밀기 | 머리-어깨 간격 −0.19(6/6), 어깨 중심 +12px 아래(6/6) | world 코-어깨 z −2.1cm(6/6), world 코 z −3.0cm(6/6) |
| 고개 숙임 | 머리-어깨 간격 −0.57(6/6) | world 코 z −21.5cm(6/6), world 귀-어깨 z −5.4cm(6/6) |
| 몸통 접근 | 어깨폭 +138px(6/6) | image 코-어깨 z −0.41(6/6). world 상대 z는 약함 |
| 어깨 올리기 | 어깨 중심 −53px 위(6/6), 어깨폭 −25px(6/6) | world 코-어깨 z −1.7cm(6/6). image z는 거의 없음 |

z는 모든 동작에서 변한다. 머리 내밀기의 world 상대 z는 2~3cm로 작지만 6회 모두 같은 방향이었다.
처음의 전체 기준 비교에서는 회차 사이 흔들림에 묻혀 작게 보였다.

### 분류 성능(1초 창, balanced accuracy, 우연 수준 0.20)

| 입력 | 파일 A→B | 파일 B→A | 두 파일 합쳐 바퀴 하나 빼기(6그룹) |
| --- | --- | --- | --- |
| `legacy3` 3특징 | 0.54 | 0.33 | 0.55 |
| `legacy3` + 어깨폭 비율 + 어깨 중심 y | — | — | **0.93** |
| 2D 형태만(배치 제외) | — | — | 0.77 |
| 2D 형태+배치 | 0.89 | 0.39 | 0.93 |
| 2D + world z | 0.79 | 0.39 | 0.93 |
| world z만 4특징 | — | — | 0.81 |
| image z만 4특징 | — | — | 0.76 |

B→A가 낮은 원인은 진폭 범위였다. B의 동작이 더 커서, 3회만으로 학습하면 A의 작은 동작이 대부분 머리 내밀기로 예측됐다.
두 회차를 함께 학습하면 해결됐다. 2D+world z의 남은 오류는 기준↔다른 동작 32창, 머리 내밀기→기준 9창이다.

## 이진 알림 판정 — `/dev` 5개 값 기준

목표는 "알림을 보낼 동작인가"의 이진 분류다. 입력은 `/dev`가 화면에 보이는 값과 같은 식
([`observationComparison.ts`](../../../model/prototype/observationComparison.ts))이다.
머리–어깨 간격·얼굴 세로 길이·어깨 높이·어깨폭(기준 어깨폭 대비 %)과 world 코–어깨 상대 z다.
현재 추론 서버는 이 값을 받지 않고 이전 3특징만 받는다. 아래는 서버 계약을 바꾼다는 전제의 점검이다.

네 동작 유지(1)와 기준 대기(0)를 1초 인과 창(직전 약 8프레임 중앙값)으로 나눴다.

| 입력 | A→B | B→A | 두 파일 바퀴 하나 빼기 |
| --- | --- | --- | --- |
| 2D 4개 | 0.87 | 0.89 | 0.89 |
| 2D 4개 + 상대 z | 0.88 | 0.86 | **0.91** |
| 머리–어깨 간격만 | 0.75 | 0.70 | 0.80 |
| 상대 z만 | 0.89 | 0.85 | 0.90 |

상대 z 하나만으로 0.90이다. 네 동작 모두 코가 어깨보다 카메라 쪽으로 나와(기준 어깨폭의 −3~−10%) 이진 판정에 유용하다.

### 서버 시간 규칙을 붙인 재생

전체 타임라인을 1초 창 분류 → ADR 0020 규칙(이탈 3초 연속 시 알림, 정상 3초 연속 시 복귀)에 그대로 흘렸다.

| 평가 | 알림이 난 시도 | 기준 대기·복귀 중 오알림 | 유지 시작 대비 알림 시각 |
| --- | --- | --- | --- |
| A로 학습 → B 재생 | 12/12 | 0 | 대부분 −0.5~2.3초 |
| B로 학습 → A 재생 | 10/12 | 0 | 대부분 −0.9~1.9초 |
| 두 파일 바퀴 하나 빼기 | 22/24 | 0 | 중앙값 0.8초 |

음수는 수동 모드에서 유지 안내 전에 이미 자세를 잡은 경우다. B→A에서 놓친 2회는 A의 몸통 접근이다.
A는 다가가며 머리–어깨 간격이 커졌고(+19%) B는 몸을 낮췄다(어깨 높이 −35%). 같은 동작도 수행 방식이 달랐다.
두 방식을 함께 학습하면 하나만 남았다. 변화량의 절댓값을 쓰는 변형은 더 나빴다(9~11/12, 오알림 2).

### 상대 z 의존도 점검

상대 z 하나로 0.90이 나온 것을 다시 확인했다. 계산 버그나 분할 누수는 찾지 못했다.

- 계산식은 `/dev`와 같다: (코 z − 양어깨 평균 z) ÷ 등록 world 어깨폭 × 100.
- 표준화는 학습 fold 안에서만 맞췄다. 평가 그룹은 (파일, 바퀴) 단위라 겹친 창이 학습·평가에 함께 들어가지 않는다.
- 기준 대기 구간의 시간 흐름에 따른 일관된 drift는 없었다(시도별 중앙값 −3.5~+5.3%, 방향이 일정하지 않음).

대신 평가 구성이 z에 유리했다.

- 네 동작 모두 상대 z가 같은 방향으로 줄었다(중앙값 −3.4~−9.7%). 어깨 올리기처럼 코가 앞으로 나올 이유가 약한 동작도 −5~−6%였다.
  MediaPipe world z는 측정값이 아니라 단안 영상에서 추정한 값이므로, 기준과 다른 모양 전반에 반응하는 신호일 수 있다.
- 0 클래스가 복귀 직후 가만히 있는 기준 자세뿐이다. "기준에서 벗어났는가"만 맞히면 되므로, 아무 방향으로나 변하는 신호가 높게 나온다.
- 기준 대기의 상대 z 범위가 넓다(파일 A의 10~90% 구간 −5.0~+9.2%). 평소 작업 자료가 들어오면 z 단독 판정은 오알림이 늘 가능성이 크다.
- 13점 영상 x·y로 상대 z를 선형 예측하면 파일 교차 R² 0.31 / −0.13이다. 2D의 단순 재표현은 아니지만 비선형 관계는 배제하지 못했다.
- 2D 4개에 z를 더한 이득은 작다(바퀴 빼기 0.89→0.91).

판단: 지금 0.90은 쉬운 0 클래스 때문에 부풀었을 가능성이 높다. z는 2D 보조 입력 후보로만 두고,
평소 작업 구간과 다른 사람 자료로 z를 넣은 경우와 뺀 경우를 비교한 뒤 채택한다.

### 일시 동작

이 자료에는 1~2초 일상 동작(화면 보기, 마시기 등) 과제가 없다. 그래서 일시 동작을 걸러내는지는 검증할 수 없다.
관찰된 것은 이동·대기 중 3초 미만 이탈 13회가 시간 규칙으로 걸러졌다는 것뿐이다(최장 2.4초).
분류기는 한 순간의 모양만 본다. 같은 모양의 짧은 동작과 지속 자세를 가르는 것은 서버의 3초 규칙이다.
3초를 넘는 일시 동작(예: 5초 휴대폰 보기)을 빼려면 해당 동작을 따로 녹화해 0으로 라벨링하고 시간 규칙과 함께 평가해야 한다.

### 일시 동작을 개별 라벨 없이 다루는 후보

일시 동작은 종류가 너무 많아 하나씩 라벨링하는 방식은 채택하지 않는다(사용자 판단, 2026-10-29). 후보는 다음과 같다. 모두 미구현이다.

1. **정지 게이트:** 이탈 누적 시간을 자세가 멈춰 있을 때만 센다. 1초 동안 2D 4개 값의 변화폭(기준 어깨폭 대비 %)으로 판단한다.
   유지 구간은 변화폭 5% 미만이 93~99%였고, 동작으로 옮겨 가는 대기 구간은 58~66%였다.
   게이트 8%에서는 알림 22/24와 오알림 0이 그대로였고 알림만 약 1초 늦어졌다(중앙값 0.8→1.8초). 5%는 21/24, 3%는 17/24다.
   실제 마시기·기지개 같은 동작에서의 효과는 이 자료로 검증하지 않았다.
2. **알려진 이탈 방향과 맞을 때만:** 목표 네 동작의 변화 방향만 학습한다. 어느 방향과도 맞지 않는 변화는 알림 대신 판정 보류로 둔다.
3. **가림·고개 돌림을 이탈로 세지 않기:** 손이 입·코를 가리거나 고개를 돌리면 이탈 타이머에 넣지 않는다.
   그대로 `valid=false`로 내면 점수 0·UNMEASURABLE 시간이 되어 화면에 측정 불가가 자주 뜬다.
   develop 서버는 이미 고개 돌림만 있는 구간을 `head_turn` 판정 불가로 낸다.
   **채택(2026-10-29):** 짧은 가림은 직전 확률을 유지하고 타이머만 멈추며, 2초를 넘을 때만 측정 불가로 처리한다.
   명세는 [재설계 계획의 짧은 가림 유지 규칙](../rebuild-plan.md#짧은-가림-유지-규칙-2026-10-29-사용자-결정-be-구현-요청)에 있다.
   비교한 다른 안은 가림 정도를 분류기 입력에 넣어 확률을 낮추는 방식이었다. 가린 채 나쁜 자세를 유지하면 놓칠 수 있어 채택하지 않았다.
4. **크기별 지속시간:** 크게 벗어나면 3초, 조금 벗어나면 더 오래 지속해야 알린다. 또는 최근 N초 중 이탈 비율로 판단한다.
5. **틀린 알림만 표시:** 평소 작업 중 오알림이 나면 사용자가 버튼으로 표시하고, 그 구간만 "알림 아님" 자료로 모은다.

### 정상 자세 분류

- 등록 기준이 있을 때: 등록 구간 0%, 복귀 구간 2~3%만 이탈로 판정됐다. "등록한 자세로 돌아왔다"는 잘 구별한다.
- 등록 없이 절대값만 쓸 때: 바퀴 빼기 0.89~0.90이지만 파일 교차는 0.58~0.90으로 흔들렸다.
  한 사람·같은 카메라 자료라 다른 사람이나 다른 구도에서 등록 없이 정상을 판정할 근거는 없다.
- 여기서 정상은 사용자가 등록한 기준이다. 해부학적으로 올바른 자세라는 뜻이 아니다([판정 한계](../measurement-limits.md)).

## 판단

- **데이터를 모으면 모델로 쓸 가능성이 있다.** 의도한 네 동작은 단순 선형 분류기로도 분리됐다.
  필요한 것은 큰 모델이 아니라 강도·회차를 고루 담은 자료다. 지금 2개로는 진폭 범위가 부족하다.
- **서비스 `legacy3`만으로는 부족하다(0.55).** 어깨폭 비율과 어깨 중심 y를 더하면 0.93이다.
  두 값은 서버가 이미 받는 9점 x·y에서 계산할 수 있지만, 추론 입력 계약(`inference-request.v2`)을 바꿔야 한다.
- **z는 이 자료에서 2D 위에 추가 이득이 없었다(0.93→0.93).** 단독으로는 0.81로 정보가 있다.
  작은 머리 내밀기에서 z가 2D를 보완할지는 미확인이다. z를 쓰려면 프레임 계약에 z를 추가해야 한다.
- **LSTM은 아직 필요 근거가 없다.** 1초 창 중앙값의 무상태 분류로 충분했다. 지속시간 판정은 서버 시간 엔진이 맡는다.

## 모델로 쓰기 위해 모을 자료

같은 날 후속 결정으로 라벨을 기준·이탈·스트레칭 3클래스로 바꾸고 동작 이름 과제를 없앴다
([ADR 0043](../../decisions/0043-base-deviation-stretch-collection.md)). 위 결과는 이전 v3 네 동작 자료의 점검이다.

- 이탈의 크기·방식을 매번 바꾼다. 두 파일의 크기·방식 차이가 교차 실패의 직접 원인이었다. 알림 경계 근처의 작은 이탈이 특히 필요하다.
- 앉은 채 스트레칭을 별도 클래스로 모은다. 팔꿈치·손목·손 좌표가 구분의 핵심이다.
- 다른 시간·카메라 재설치 회차. 기간이 짧으므로 의도적으로 나눠 측정한다.
- 오알림 확인용 평소 작업 구간. 현재 `/dev`는 안내가 끝나면 카메라를 끄므로 이 구간을 기록하지 못한다(아래 남은 한계).
- 실제 수행 시작·끝 표시. 안내 라벨만으로는 정답 시각이 없다.
- 주기 10Hz 유지 여부. 지금은 7~8Hz다.

### `/dev` v4로 모으는 방법 (2026-10-29 구현)

- 시작 창에서 진행 모드(수동 권장), **바퀴 수**(1·3, 기본 1), **바퀴 안 순서 섞기**(기본 켬)를 고른다.
- 한 바퀴는 기준 → 이탈 자세(측정 5초) → 기준 복귀 → 앉은 채 스트레칭(측정 8초) → 기준 복귀다. 자동 1바퀴는 약 27초다.
- 리플레이 JSON은 `observation-keypoint-replay-v2`이며 원래 인덱스 0..22 좌표와 `plan`을 담는다. 기존 v1 파일도 불러온다.
- 안내를 마치면 카메라가 꺼지고 기록도 끝난다. (앞서 "안내 뒤에도 `completed`로 계속 기록된다"고 적은 것은 코드 확인 오류였다.)
- 실행 하나당 최대 6,000프레임이다. 1바퀴 실행에서는 한도에 닿지 않는다.

한 사람의 앉기 1회 진행안(미검증 제안): 카메라 고정 → 1바퀴 실행을 6회 반복(실행마다 기준 새로 등록) →
실행마다 이탈 종류·크기를 바꾸고, 2~3회는 알림 경계 근처로 작게 한다 → JSON을 저장소 밖이나 `data/`에 저장한다.

학습 코드는 새로 만든다. 기존 `mediapipe_lstm.py`는 미래 좌표 회귀용이라 쓰지 않는다.
새 경로는 리플레이 JSON 읽기 → 사람·회차 분할 → 특징 계산 → 규칙(B0)과 3클래스 softmax(B1) → 시간 규칙 재생 평가 → 추론 서버용 내보내기다.

### 최소 모델 시험에 필요한 양 (팀원 6명 기준 추정)

목표는 "처음 보는 사람에게도 동작하는가"를 사람 하나 빼기(6 fold, 5명 학습)로 확인하는 최소 시험이다. 정확도 주장용 양이 아니다.

| 단위 | 1인당 | 6명 합계 |
| --- | --- | --- |
| 앉기(카메라를 치우고 다시 설치) | 2회(다른 날 또는 같은 날 오전·오후) | 12회 |
| 앉기마다 1바퀴 실행 | 6회(수동 기준 약 9분) | 72회 |
| 이탈 유지 시도 | 12회 | 72회 |
| 스트레칭 유지 시도 | 12회 | 72회 |
| 녹화 시간 | 약 20분 | 약 2시간(병렬 가능) |

- 근거: 현재 2개 파일에서는 학습에 없던 크기·방식이 나오면 놓쳤다. 그래서 실행마다 이탈을 바꾼다.
  앉기 2회는 같은 사람의 재설치 편차를 보기 위한 최소다. 같은 앉기 안의 실행끼리는 독립 표본이 아니다.
- 이 양으로 할 수 있는 것: 사람 하나 빼기의 3클래스·알림 판정 정확도, 놓친 알림, 스트레칭 오알림, 팔 좌표·z 포함 여부 비교.
  할 수 없는 것: 신뢰구간이 좁은 정확도, 팀 밖 사용자 일반화, 평소 작업 중 오알림률(평소 작업 기록 경로가 없음).

[재설계 계획](../rebuild-plan.md)의 순서(L0/G0 → G1 수집 형식 → G3 B0/B1)는 그대로 따른다.
이번 결과는 G0 관측 확인 자료이며, 같은 사람·같은 날의 의도적 동작이므로 실제 사용 정확도가 아니다.

## 남은 한계

- `/dev`에 평소 작업(자유 작업) 구간을 기록하는 단계가 없다. 오알림률을 보려면 안내 뒤 자유 작업 단계를 추가해야 한다. 미구현.
- 실제 좌표 파일 `model/temp/`는 `.gitignore`에 없다. 저장소 밖이나 무시되는 `data/`로 옮겨야 한다.
- 기존 학습기(`mediapipe_lstm.py`)는 이 형식을 읽지 못한다. importer가 필요하다(ADR 0041과 같음).
- 바퀴 단위 분할도 같은 날·같은 사람이라 서로 상관된다. 다른 날 시험 전에는 일반화 근거가 아니다.
- 점검 스크립트는 저장소에 넣지 않았다. 본 구현은 계획 0052의 G1~G3 순서로 새로 만든다.
