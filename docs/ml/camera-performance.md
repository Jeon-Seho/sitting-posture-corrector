# 카메라 지연과 모델 비교

2026-10-14. `/dev`의 성능 측정은 자세 판정 정확도 평가와 분리한다.

## 측정 방법

`/dev` 하단 **성능 측정 · 모델 비교**에서 두 가지 실험을 실행한다.

1. **현재 측정 20초 분석**: 실제 웹캠 측정을 시작하고 기준 등록을 마친 후 실행한다.
   MediaPipe 추론, 개발 세션 후처리, LSTM·룰 계산, React 렌더링, 관측 간격을 구분한다.
   시작 시 집계만 초기화하며 기준 자세와 세션은 초기화하지 않는다.
   탭을 숨기거나 카메라·세션이 중단되면 부분 결과로 끝낸다. 백그라운드 대기를 완료된 20초 측정으로 표시하지 않는다.
2. **Lite · Full · Heavy 비교**: 측정 종료 후 얼굴과 양어깨를 보이며 실행한다.
   6초 동안 24개 프레임을 메모리에 모으고, 세 모델 × GPU/CPU를 두 회차 비교한다.
   두 번째 회차는 순서를 뒤집는다. 각 설정의 4회 워밍업과 모델 초기화는 추론 통계에서 제외한다.
   모든 설정이 같은 프레임과 촬영 시각 간격을 사용한다. 비교 후 영상·좌표를 해제한다.

비교할 로컬 모델은 `node frontend/scripts/prepare-benchmark-assets.mjs`로 준비한다.
Google 공식 float16 v1 파일의 SHA-256을 `frontend/model-variants.json`과 비교한다.
일반 자산 준비(`predev`/`prebuild`)는 서비스용 Heavy와 개발용 Full을 준비하며, 위 비교 명령은 Lite까지 준비한다.
모델 파일은 Git 제외 경로 `frontend/public/mediapipe/`에 있고, 추가 npm 의존성은 없다.

## 수치 해석

| 항목 | 뜻과 한계 |
| --- | --- |
| MediaPipe 좌표 추출 | 동기 SDK 호출부터 결과 반환까지의 시간. 초기화·촬영·최종 화면 표시는 별도다. |
| 좌표 후처리 전체 | 개발 세션 구도·규칙·LSTM·자동 수집·상태 예약. 아래 하위 시간을 포함한다. |
| LSTM·룰 계산 | 시계열 실험 엔진 호출 시간. LSTM이 준비되지 않은 구간도 포함되므로 실제 예측 준비 상태를 함께 확인한다. |
| 화면 상태 전달 | React 상태 변경 예약과 데이터 복사. React 렌더링이나 화면 그리기 시간이 아니다. |
| React 렌더링 | 개발 빌드 Profiler의 actualDuration. 브라우저 layout·paint는 제외하며 일반 생산 빌드에서는 제공되지 않을 수 있다. |
| 오버레이 그리기 | 공통 카메라 canvas 경로만. `/dev` SVG·React 화면 비용 전체를 뜻하지 않는다. |
| 실제 프레임 간격 | 추론 시작 시각 사이 간격. 추론 + 후처리 + 스케줄 대기를 포함한다. |
| JSON의 captureToConsumer | 이 구현에서 frame.timeMs는 추론 시작 시각이다. 여기서 소비자 전달까지의 시간이며 센서 노출부터 화면 표시까지의 지연이 아니다. |
| 추가 스케줄 지연 | 예정된 타이머 시각보다 늦게 콜백에 진입한 시간. 운영체제 부하·메인 스레드 작업 등이 섞인다. |
| 13점 관측률 | 얼굴·귀·양어깨의 현재 앱 품질 검사를 통과한 비율. 자세 교정 정확도가 아니다. |
| 좌표 변화 | 연속 유효 프레임의 어깨 중심·폭 정규화 3D 좌표 차이. 실제 움직임을 포함하므로 순수 검출 떨림으로 단정하지 않는다. |

계측은 bounded 집계만 남긴다. 카메라 루프 통계는 최근 300개, 세션 통계는 최근 600개
호출의 p50/p95/평균/최댓값이다. 세션의 count/total은 초기화 이후 누적값으로 구분한다.
20초 분석도 프레임 속도에 따라 전체 구간보다 짧은 최근 창의 통계일 수 있다.
서로 포함 관계인 처리 시간이나 서로 다른 표본의 p95를 합산하지 않는다.
센서 노출·브라우저 영상 디코드·화면 최종 paint를 합한 전체 지연은 이번에 직접 측정하지 않았다.

## GPU 확인

선택한 delegate와 실제 SDK 초기화에 성공한 delegate를 따로 기록한다.
`auto`만 GPU 실패 시 CPU로 전환하며 원인을 남긴다. 비교 실험의 명시적 GPU 실패는
실패 그대로 표시한다. CPU로 몰래 전환한 값을 GPU 결과라고 기록하지 않는다.

GPU 초기화에 전달한 **동일한 canvas WebGL2 context**의 renderer/vendor/version을 읽는다.
SwiftShader·llvmpipe 등은 소프트웨어 렌더러로 표시한다. 브라우저가 장치 정보를 가리면
미확인으로 남긴다. 실제 GPU 경로의 성공과 GPU 사용률(%)은 서로 다른 증거다.

## 지연 개선 선택지

일반 서비스는 기존 Heavy + GPU 우선과 `legacy` 대기를 유지한다.
`/dev`의 기본은 **Full + GPU 우선 + responsive**다. 모델·delegate·대기 정책을 다음 카메라 연결 전에 선택할 수 있다.

- `legacy`: 기존 추론 시간의 두 배를 목표 간격으로 사용하고 tick마다 33ms를 기다린다.
- `responsive`: 이미 소비한 시간을 간격에서 빼고, 후처리 뒤 최소 8ms를 양보한다.
  GPU 최대 30 FPS, CPU 최대 20 FPS 상한과 단일 추론·새 비디오 프레임 조건을 유지한다.
  8ms는 개발 실험용 스케줄 값이며 장치 전체에 최적이라고 검증된 수치가 아니다.

저품질 관측·시간 누락 정책을 완화해 FPS나 알림 성공률을 높이지 않는다.
작은 모델은 실제 입력에서 관측 품질을 함께 확인한 뒤 선택한다. Worker 이동은 별도 구조 변경이며
현재 구현은 동기 추론의 대기 정책과 모델 선택을 비교할 수 있도록 한다.

## 실제 결과

### 환경과 범위

2026-10-14, Apple M1, macOS 27.0, Codex 내장 Chromium 155, 실제 웹캠 640×480,
`@mediapipe/tasks-vision` 1.0.1, float16 v1. WebGL renderer는
`ANGLE (Apple, ANGLE Metal Renderer: Apple M1, Unspecified Version)`이었다.
GPU 초기화 성공·softwareRenderer=false·CPU fallback 없음까지 확인했다. GPU 사용률(%)은 측정하지 않았다.
React Profiler가 켜진 개발 빌드이며 실측 중 테스트·빌드는 실행하지 않았다.

### 같은 입력으로 세 모델·두 실행 장치 비교

6.08초 동안 모은 같은 24프레임, 설정당 2회차 × 24개 추론. 아래는 회차별 값이며 합쳐 계산한 백분위가 아니다.
모델 초기화와 4회 워밍업을 제외했다. 2회차는 실행 순서를 뒤집었다.

| 모델 | 장치 | p50 1회 / 2회 (ms) | p95 1회 / 2회 (ms) | 13점 입력 유효율 |
| --- | --- | ---: | ---: | ---: |
| Lite | GPU | 10.7 / 11.2 | 15.2 / 13.6 | 100% / 100% |
| Lite | CPU | 24.9 / 24.8 | 25.6 / 25.7 | 100% / 100% |
| Full | GPU | 11.9 / 12.0 | 13.6 / 13.5 | 100% / 100% |
| Full | CPU | 39.0 / 39.1 | 41.5 / 41.4 | 100% / 100% |
| Heavy | GPU | 34.4 / 33.0 | 36.9 / 35.8 | 100% / 100% |
| Heavy | CPU | 154.9 / 154.9 | 247.6 / 157.3 | 100% / 100% |

이 짧은 정면 클립에서 Full은 Heavy보다 훨씬 짧은 추론 시간으로 같은 입력 유효율을 보였다.
Lite와 Full의 속도 차이는 약 1ms였다. Full을 개발 기본으로 택했으나 **정확도 우위가 입증된 것은 아니다**.
좌표 변화 p95는 GPU Lite 0.0379, Full 0.0229, Heavy 0.0318이었다. 실제 움직임을 포함하므로
이를 순수 떨림·랜드마크 오차로 보고하지 않는다. 가림·역광·측면·여러 참여자는 별도 평가가 필요하다.
별도의 초기 실행은 테스트/타입 검사와 일부 겹쳐 시간 비교에서 제외하고, 위 비교를 다시 수행했다.

### 실제 앱에서 20초 전후 측정

| 설정 | 관측 프레임 / 측정 초 | 전체 평균 FPS | 추출 p50 / p95 (ms) | 관측 간격 p50 / p95 (ms) |
| --- | ---: | ---: | ---: | ---: |
| Heavy GPU + 기존 대기 | 255 / 20.005 | 12.7 | 34.3 / 54.7 | 69.0 / 123.2 |
| Heavy GPU + 단축 대기 | 299 / 20.023 | 14.9 | 49.0 / 74.8 | 62.7 / 97.2 |
| Full GPU + 단축 대기 | 545 / 20.019 | 27.2 | 18.8 / 25.4 | 35.4 / 45.5 |
| Full GPU + 단축 대기 재확인 | 470 / 20.032 | 23.5 | 24.2 / 32.2 | 44.9 / 62.5 |

Full 행의 추론·간격 통계는 최근 300개, FPS는 전체 545개에서 계산했다. 서로 다른 시각에 촬영한
전후 비교이므로 완전히 동일한 입력·장치 부하를 통제한 비교는 아니다. 같은 Heavy도 두 실측 사이
추론 시간이 달라졌으므로 속도 변화 전체를 대기 정책만의 효과라고 주장하지 않는다.
사용자 동작 관찰 후의 재확인에서도 기존보다 빨랐지만 첫 Full 측정보다 느렸다. 이때 React p50/p95는
7.5/12.8ms였다. 세션 길이·화면 상태·부하를 통제한 원인 분해는 하지 않았으며 27.2 FPS만 대표값으로 고르지 않는다.

기존 측정의 LSTM·룰 단계는 p50 0.9ms / p95 1.7ms, React 렌더링은 3.8 / 5.3ms였다.
가장 큰 비용은 **Heavy 좌표 추출과 추론 시간에 비례한 대기**였다. 최종 Full 실측의 LSTM·룰 단계는
0.1 / 1.3ms, React는 4.9 / 7.9ms였다. LSTM은 10Hz로 호출되므로 매 카메라 프레임에서 추론하는 것은 아니다.
단계별 p95는 합산하지 않는다. 지금의 주된 병목을 Mac 성능 부족이나 LSTM 하나로 단정할 근거는 없다.

모델별 실제 속도와 LSTM 예측 정확도는 별개다. 정상 프로파일에는 실제 `poseModelId`를 보존하고,
선택 모델과 다른 프로파일 또는 출처가 없는 과거 프로파일은 적용하지 않는다. 수집 중 추출기가 바뀌면
자동 수집 구간을 분리하고 수동 수집을 중단한다. [ADR 0031](../decisions/0031-developer-camera-performance.md).

[좌표 없는 집계 JSON](measurements/camera-performance-2026-10-14.json)에 회차별 시간·장치·통계를 보존했다.
실제 프레임·랜드마크·참여자 코드는 포함하지 않는다. 별도로 [촬영·수집·모델 공백 감사](live-keypoint-audit.md)를 기록했다.
